Part I · Software Design

Goals of Good Software Design

A software design is not a drawing — it is a set of decisions that determine whether a system will survive contact with reality or collapse under its own weight.

When engineers speak of "good design," they are not speaking of aesthetic elegance in the way a graphic designer might. They are speaking of something far more consequential: the structural quality of a system that determines how easily it can be built, tested, understood, modified, and maintained over its entire lifespan. The design phase sits between requirements analysis and coding, and its outputs — architectural diagrams, module specifications, interface definitions, data structures — become the blueprint from which all downstream work proceeds. A flawed design does not merely produce a flawed product; it produces a product whose flaws are expensive to discover and prohibitively expensive to correct. This is why Boehm's cost-of-change curve shows that fixing a design error discovered during maintenance costs fifty to two hundred times more than fixing it during design itself.

The goals of good software design form an interconnected constellation rather than a simple checklist. Correctness means that the design faithfully implements every requirement — functional and non-functional — specified in the requirements document. A design that omits a security requirement or misinterprets a business rule is incorrect regardless of how elegant its architecture appears. Completeness ensures that all scenarios, edge cases, and interfaces are addressed; an incomplete design forces developers to make architectural decisions during coding, which is precisely where such decisions are most dangerous. Efficiency demands that the design avoids wasteful consumption of memory, processing time, and network bandwidth, though the appropriate level of efficiency depends entirely on context — a trading system and a student portal have wildly different performance requirements.

Beyond correctness and completeness, good design pursues qualities that pay dividends across the software's entire lifecycle. Flexibility (also called adaptability) is the ease with which the design can accommodate changes in requirements without requiring wholesale restructuring. Since requirements inevitably change — and Indian software service companies see this with particular intensity — flexibility is not a luxury but a survival trait. Modularity decomposes the system into discrete, self-contained units that can be developed, tested, and maintained independently; we will examine this in great detail when discussing structured design. Reusability means designing components general enough to serve in other systems or other contexts within the same system, thereby amortising development cost. Maintainability — perhaps the most economically significant goal — encompasses how easily the system can be understood, diagnosed, and repaired by developers who did not originally build it. Since maintenance typically consumes sixty to eighty percent of total software cost, a design that is difficult to maintain is a design that is expensive to own.

Finally, good design must be testable. If a design produces modules so tightly intertwined that they cannot be tested in isolation, or so poorly documented that testers cannot determine expected behaviour, then the design has failed regardless of its other virtues. Each of these goals — correctness, completeness, efficiency, flexibility, modularity, reusability, maintainability, and testability — can be evaluated independently, but they function as a system. Improving one at the expense of others is a tradeoff that must be made consciously, with full awareness of the consequences.

"The purpose of software engineering is to control complexity, not to create it." — Pamela Zave

Design Strategies & Methodologies

Software design has evolved through several fundamentally different philosophical approaches, each reflecting a different answer to the question: what is the primary organising principle around which we structure a system? The three great paradigms — data-oriented, function-oriented, and object-oriented — each privilege a different aspect of the problem domain, and understanding their differences is essential both for exam writing and for genuinely grasping why modern design looks the way it does.

Data-oriented design (also called data-driven design) begins with the data. The designer first identifies the data structures the system must manage, determines their relationships, and then derives the functions that operate on those structures. This approach traces its intellectual lineage to Michael Jackson's Jackson Structured Programming (JSP) and Jackson System Development (JSD) methods from the 1970s and 1980s. The core insight is deceptively simple: data structures are more stable over time than processing logic. A bank's account records change their structure far less frequently than the business rules governing interest calculation. By anchoring the design to stable data, the resulting system tends to be more resilient to requirement changes. Data-oriented design uses tools like Entity-Relationship diagrams, Data Flow Diagrams (DFDs), and data dictionaries to model the information landscape before deriving procedural structure from it.

Function-oriented design (or function decomposition) takes the opposite starting point. It begins by identifying the major functions the system must perform and then decomposes each function into progressively smaller, more manageable sub-functions until each sub-function is simple enough to implement directly. This is the philosophy behind Structured Design as practised by Yourdon and Constantine in the 1970s. The system is viewed as a transformation pipeline: input data flows through a hierarchy of functions that transform it into output. DFDs are the primary modelling tool, and the transition from analysis to design involves converting DFDs into Structure Charts through a process called transform analysis or transaction analysis. The strength of this approach is its intuitive alignment with how humans naturally think about processes — first what must be done, then how to decompose it. Its weakness is that data structures tend to be secondary concerns, which can lead to systems where data is passed awkwardly between functions that don't naturally share it.

Object-oriented design (OOD) attempts a synthesis. It identifies the real-world entities in the problem domain — customers, accounts, transactions, vehicles — and models each as an object that bundles both data (attributes) and behaviour (methods) into a single coherent unit. Objects communicate through message passing, and relationships between real-world entities are modelled through inheritance, aggregation, and association. OOD emerged in the 1980s with languages like Smalltalk and C++, and its dominance was cemented by the UML standardisation effort in the 1990s. The advantage of OOD is its natural correspondence with the problem domain: when you model a "BankAccount" object, it directly mirrors the real-world concept, making the design more intuitive and the system easier to reason about. The disadvantage — particularly for students encountering it for the first time — is that the identification of appropriate objects, their responsibilities, and their collaborations requires significant design skill and judgement.

Data-Oriented Software Design

Data-oriented design deserves more detailed treatment because it is frequently examined and frequently misunderstood. The central thesis, articulated most clearly by Michael Jackson, is that the structure of a program should mirror the structure of the data it processes. If a file consists of a header record followed by a sequence of detail records followed by a trailer record, then the program that processes that file should consist of three corresponding phases: one that reads the header, a loop that reads details, and one that processes the trailer. This structural correspondence between data and program is not merely a convenience — it is a design principle that reduces the space of possible errors by making the program's structure predictable and inspectable.

In practice, data-oriented design proceeds through a characteristic sequence of steps. First, the designer constructs an entity-relationship model that identifies all data entities, their attributes, and the relationships between them. Next, data flow diagrams are drawn to show how data moves through the system and is transformed by processes. The data dictionary provides precise definitions for every data item. Finally, the design derives program structure from data structure using Jackson's structure diagrams, which depict the sequential, iterative, and selective composition of data items. The program structure is then annotated with the operations that must occur at each component. This approach is particularly effective for batch processing systems, file conversion utilities, and report generators — domains where data structure is well-defined and stable. It is less naturally suited to interactive, event-driven systems where the flow of control depends on user actions rather than data structure.

The benefits of data-oriented design include strong alignment with data models, natural suitability for data-intensive applications, high maintainability when data formats change (since the program structure adapts automatically), and clear traceability from requirements to code. The drawbacks include difficulty handling complex control flow, limited applicability to real-time and interactive systems, and the overhead of maintaining structural correspondence when the data model itself is complex or evolving. Modern practitioners often combine data-oriented thinking with object-oriented design, using data models as the foundation for class hierarchies.

Structured Design — Structure Charts, Coupling & Cohesion

Structured design, as formulated by Larry Constantine and Edward Yourdon in the 1970s, remains the most exam-critical topic in this unit. It provides the conceptual vocabulary — coupling, cohesion, modularity — that underpins all subsequent design thinking.

Structure Charts

A structure chart is a hierarchical diagram that depicts the modular decomposition of a software system. Where a Data Flow Diagram shows what the system does (the functional perspective), a structure chart shows how the system is organised into modules (the architectural perspective). The chart consists of rectangular boxes representing modules, connected by arrows that indicate calling relationships — the calling module sits above the called module in the hierarchy. Along the connecting lines, small arrows annotated with data names show what data is passed between modules (data couples), and small diamond-headed arrows indicate control flags (boolean values that influence the behaviour of the called module).

The transformation from DFD to structure chart follows two principal strategies: Transform Analysis and Transaction Analysis. In transform analysis, used when a DFD shows a clear linear flow from input to processing to output, the designer identifies the central transform (the essential processing logic), designates it as the root module, and creates subordinate modules for input, processing, and output branches. In transaction analysis, used when a DFD shows a single input that can trigger multiple different processing paths (like a menu-driven system), the designer creates a dispatcher module at the top that analyses the incoming transaction type and dispatches it to the appropriate handler module. Real systems typically require a combination of both strategies: transaction analysis at the top level to handle different user commands, with transform analysis within each transaction handler to structure the processing pipeline.

Coupling

Coupling measures the degree of interdependence between two modules. When module A calls module B, they are coupled — but the strength of that coupling determines how a change in one module propagates to the other. The goal of good design is to achieve the loosest possible coupling between modules, because loosely coupled modules can be modified, tested, and replaced independently. The coupling spectrum, from tightest (worst) to loosest (best), comprises six levels that every student must know thoroughly.

Content Coupling is the tightest and most pathological form. It occurs when one module directly references or modifies the internal data of another, or when one module branches into the middle of another (e.g., a goto into another module's code). Content coupling means that changing the internal implementation of one module can silently break the other. It violates the fundamental principle that modules should interact only through well-defined interfaces.

Common Coupling (also called global coupling) occurs when two modules share the same global data area — a global variable, a shared file, or a common database table accessible to all modules. Every module that reads or writes the shared data is coupled to every other such module, because any one of them can change the data without the others' knowledge. Common coupling creates subtle bugs that are extremely difficult to trace, because the source of an erroneous value in the shared data could be any one of many modules.

External Coupling arises when two modules share an externally imposed data format, communication protocol, or device interface. For example, two modules that both read data from the same sensor using a specific protocol are externally coupled. This form is less harmful than common coupling because the shared element is typically stable, but it still means that a change in the external constraint forces changes in both modules.

Control Coupling occurs when one module passes a control flag (a boolean or enumerated value) to another module that influences its internal logic. For example, module A calls module B with a parameter mode = "sort_ascending", which causes B to execute a different code path. The problem is that module A must know the internal structure of B's decision-making to use this flag appropriately — it is an abstraction leak.

Stamp Coupling (also called data-structure coupling) occurs when modules share a composite data structure (a record, object, or array), but each module uses only part of it. Module A passes an entire "Employee" record to module B, but B only needs the employee's name. This is wasteful and creates unnecessary dependency: if the Employee structure changes, module B is affected even though the fields it actually uses remain unchanged.

Data Coupling is the loosest and best form. It occurs when modules communicate only through parameters that are individual data items (scalars, simple values) — exactly the data the called module needs, no more and no less. Data coupling produces the most independent, testable, and maintainable modules. This is why every software engineering textbook recommends data coupling as the target: it minimises the surface area of interaction between modules to the absolute minimum required by their functional relationship.

Cohesion

If coupling measures the connections between modules, cohesion measures the unity of purpose within a module. A highly cohesive module does one thing and does it well — all of its internal elements (data, functions, processing steps) contribute to a single, well-defined purpose. A module with low cohesion is a grab-bag of unrelated functionality, the kind of module that accumulates "utility functions" and "helper methods" that have no coherent relationship to each other. The cohesion spectrum, from weakest to strongest, comprises seven levels.

Coincidental Cohesion (weakest) — the module's elements have no meaningful relationship to each other. They were grouped together arbitrarily, perhaps because they shared a few lines of code or because the programmer was in a hurry. A module called "Miscellaneous Utilities" that contains string formatting, database connection, and email sending is coincidentally cohesive.

Logical Cohesion — the module's elements perform similar (but not identical) functions and are selected at runtime by a control flag. A module that performs "all input operations" — reading from file, reading from keyboard, reading from network — selected by a parameter is logically cohesive. The problem is that the module contains code for all variants even when only one is used, increasing complexity and reducing clarity.

Temporal Cohesion — the module's elements are related by the time at which they execute. A module called "Initialise System" that opens files, clears memory, sets counters to zero, and establishes network connections is temporally cohesive: these actions are unrelated in function but must all happen at startup.

Procedural Cohesion — the module's elements are related by the sequence in which they execute, even though they operate on different data. A module that "reads input, then validates it, then writes to log" has procedural cohesion because the sequence matters, but the elements don't share a data focus.

Communicational Cohesion — the module's elements operate on the same data. A module that calculates the average and maximum of a set of scores is communicationally cohesive: both operations work on the same data set, even though they produce different results.

Sequential Cohesion — the output of one element serves as the input to the next. A module that "reads data, sorts it, then writes the sorted data" is sequentially cohesive: the three steps form a pipeline where each depends on the previous.

Functional Cohesion (strongest) — every element in the module contributes to the execution of a single, well-defined function. A module that calculates the square root of a number, or that sorts an array, or that validates an email address is functionally cohesive. This is the ideal: it produces modules that are easy to name (if you can't give a module a clear, short name, it probably lacks functional cohesion), easy to test (one function means one set of test cases), and easy to reuse (a single-purpose module can be applied wherever that function is needed).

Exam Tip: When asked about coupling and cohesion in the same question, always emphasise their inverse relationship. Higher cohesion within modules naturally leads to lower coupling between them, because a module focused on a single purpose exposes fewer interfaces and requires fewer connections to other modules.

The relationship between coupling and cohesion is not merely correlative — it is causal. When a module is functionally cohesive, it has a single well-defined purpose, which means it requires a small, focused set of inputs and produces a small, focused set of outputs. This narrow interface automatically reduces coupling to other modules. Conversely, when a module has coincidental cohesion, it performs multiple unrelated tasks, each of which requires different data and interacts with different external modules, maximising coupling. This is why experienced designers focus on achieving high cohesion first: coupling improves as a natural consequence.

Modular Structure & Packaging

Modularity is the architectural expression of the ancient engineering principle "divide and conquer." A modular system is decomposed into discrete modules, each of which encapsulates a specific piece of functionality behind a clean interface. The module hides its internal implementation details (information hiding, as David Parnas articulated in 1972) and exposes only what other modules need to know to use it. This separation of interface from implementation is what makes large systems tractable: no developer needs to understand the entire system at once, only the interfaces of the modules they interact with directly.

Good modular design follows several principles. Each module should have a single, well-defined responsibility (high cohesion). Modules should interact through the smallest possible interface (low coupling). The number of modules should be appropriate for the system's size — too few modules means each is overly complex; too many means excessive interface overhead. Module size should be manageable: research suggests that modules between 50 and 200 lines of code are optimal for comprehension, though this varies by language and complexity.

Packaging extends modularity to the next organisational level. Related modules are grouped into packages (or subsystems) that can be developed, tested, and deployed as coherent units. In Java, packages group related classes. In large systems, packages correspond to architectural layers or subsystems. The rules for good packaging mirror those for good modules: packages should have high internal cohesion (the classes within a package should be closely related) and low external coupling (dependencies between packages should be minimised and well-defined). The Acyclic Dependencies Principle states that the dependency graph between packages should contain no cycles — if package A depends on B, and B depends on C, then C must not depend on A. Cyclic dependencies make systems extremely difficult to build, test, and release independently.

Object-Oriented Design

Object-oriented design models the software system as a collection of collaborating objects, each of which is an instance of a class that bundles data (attributes) with the operations (methods) that manipulate that data. The four pillars of OOD — Encapsulation, Inheritance, Polymorphism, and Abstraction — form the conceptual foundation that distinguishes it from function-oriented design.

Encapsulation is the bundling of data and methods into a single unit (class) with controlled access. The internal state of an object is hidden from the outside world; access is only through public methods. This is the object-oriented equivalent of information hiding. Inheritance allows a new class (subclass) to inherit the attributes and methods of an existing class (superclass), adding or overriding only what is different. This promotes code reuse and models "is-a" relationships: a SavingsAccount is a BankAccount with additional interest calculation behaviour. Polymorphism (meaning "many forms") allows objects of different classes to be treated as objects of a common superclass, with each class providing its own implementation of a shared method. When you call shape.draw(), a Circle draws itself differently from a Square, even though both are Shapes. Abstraction focuses on the essential characteristics of an object relative to the observer's perspective, hiding irrelevant detail. An abstract class "Shape" defines that all shapes have an area, without specifying how to calculate it.

The fundamental difference from function-oriented design is philosophical. Function-oriented design asks "What does the system do?" and decomposes by function. Object-oriented design asks "What does the system know and who is responsible for what?" and decomposes by entity. In function-oriented design, data flows between functions; in OOD, objects send messages to each other. This difference has profound implications for maintainability: when a real-world entity changes (say, the rules governing bank accounts change), an OOD system requires modification primarily in the BankAccount class, whereas a function-oriented system might require changes across multiple functions that process account data.

Top-Down & Bottom-Up Approaches

The top-down and bottom-up approaches represent two fundamentally different strategies for decomposing a complex system into manageable components, and understanding their distinction — along with the conditions under which each is appropriate — is one of the most reliably examined topics in this unit.

Top-down design begins at the highest level of abstraction: the system as a whole. The designer starts with a single module that represents the entire system and progressively decomposes it into sub-modules, each of which handles a portion of the system's functionality. Each sub-module is further decomposed until the leaf-level modules are simple enough to implement directly. This approach mirrors how we naturally explain complex processes — starting with the big picture and filling in details. The classic example is designing a payroll system: start with "Process Payroll," decompose into "Calculate Salary," "Deduct Taxes," "Generate Payslip," and continue subdividing each. Top-down design produces a clear hierarchical structure and is easy to plan and manage because the architecture is visible from the start.

Bottom-up design starts from the lowest level: the fundamental components and utilities that the system will need. The designer identifies basic, reusable building blocks (data access functions, string utilities, mathematical calculations, communication primitives) and assembles them into progressively larger, more complex components. A bottom-up approach to a payroll system might start by building "Tax Calculation Library," "Date Utility Module," and "Database Access Layer," then combine them into "Employee Record Manager," and finally assemble the complete system from these composed units. Bottom-up design naturally produces reusable components and is well-suited to systems where low-level utilities and algorithms are the primary technical challenge.

In practice, most industrial software development uses a combination of both approaches, sometimes called "middle-out." The high-level architecture is designed top-down (to ensure the system meets its requirements), while the low-level utilities and libraries are designed bottom-up (to maximise reuse and leverage existing components). The two approaches meet in the middle, where top-down decomposition reaches the level of detail where bottom-up components can be directly used.

Key Concept — Stubs and Drivers

When testing top-down designs, lower-level modules that haven't been built yet are replaced by stubs — simplified dummy implementations that return predefined values. When testing bottom-up designs, upper-level modules that haven't been built yet are replaced by drivers — test harnesses that call the lower modules with test inputs and verify their outputs. Both stubs and drivers are scaffolding that enables incremental testing of partially completed systems. This distinction is frequently tested in exams and should be clearly defined in any answer about top-down vs. bottom-up testing.

Design Patterns

Design patterns, as catalogued by the "Gang of Four" (Gamma, Helm, Johnson, Vlissides) in their 1994 book, are reusable solutions to commonly occurring design problems. They are not finished designs that can be directly transformed into code; they are templates for solving problems that can be adapted to specific contexts. Understanding the three categories of design patterns — Creational, Structural, and Behavioral — provides a vocabulary for discussing design solutions and their tradeoffs.

Creational patterns deal with object creation mechanisms, attempting to create objects in a manner appropriate to the situation. The Singleton pattern ensures that a class has only one instance and provides a global point of access to it (useful for database connections or configuration managers). The Factory Method pattern defines an interface for creating objects but lets subclasses decide which class to instantiate. The Abstract Factory pattern provides an interface for creating families of related objects without specifying their concrete classes. The Builder pattern separates the construction of a complex object from its representation, allowing the same construction process to create different representations.

Structural patterns concern how classes and objects are composed to form larger structures. The Adapter pattern converts the interface of a class into another interface that clients expect, enabling classes with incompatible interfaces to work together. The Decorator pattern attaches additional responsibilities to an object dynamically, providing a flexible alternative to subclassing for extending functionality. The Facade pattern provides a simplified interface to a complex subsystem, reducing dependencies between the client and the subsystem. The Proxy pattern provides a surrogate or placeholder for another object to control access to it.

Behavioral patterns are concerned with communication between objects and the assignment of responsibilities. The Observer pattern defines a one-to-many dependency between objects so that when one object changes state, all its dependents are notified and updated automatically (this is the foundation of event-driven programming and reactive systems). The Strategy pattern defines a family of algorithms, encapsulates each one, and makes them interchangeable, allowing the algorithm to vary independently from the clients that use it. The Template Method pattern defines the skeleton of an algorithm in a method, deferring some steps to subclasses, allowing subclasses to redefine certain steps of the algorithm without changing its structure.

Part II · Architecture

Architecture Styles

An architectural style is a recurring structural organisation — a proven arrangement of components and connectors — that constrains design decisions and provides system-level properties. Choosing the right architecture is the most consequential design decision in any software project.

Layered Architecture

Layered architecture organises the system into a stack of layers, each of which provides a set of services to the layer above it and uses services from the layer below. The most familiar example is the OSI seven-layer networking model, but layered architecture appears everywhere: operating systems (hardware → kernel → system calls → applications), enterprise applications (database → data access → business logic → presentation), and web applications (database → server → API → UI). The defining rule is that each layer only interacts with the layer immediately adjacent to it (strict layering) or with any lower layer (relaxed layering). A layer never calls upward to the layer above it.

The primary advantage of layered architecture is separation of concerns: each layer can be developed, tested, and maintained independently. Changes to the database layer (replacing MySQL with PostgreSQL) should not affect the business logic layer, and changes to the UI (switching from web to mobile) should not affect the business rules. The disadvantage is performance overhead: every request must traverse multiple layers, each adding a small processing delay. The other risk is the "sinkhole anti-pattern," where a layer does nothing but pass requests to the next layer, adding complexity without value.

For a Library Automation System (LIBSYS), the layers might be: Layer 1 (Presentation) — Web interface, search bar, book display, member login screens; Layer 2 (Business Logic) — Search engine, borrowing rules, fine calculation, reservation management; Layer 3 (Data Access) — Database queries, book record retrieval, member record updates; Layer 4 (Database) — MySQL or PostgreSQL database storing books, members, transactions.

Repository Architecture

Repository (or data-centred) architecture centres the system around a shared data repository that all components access. Subsystems do not communicate directly with each other; instead, they read from and write to the shared repository, and changes in the repository trigger actions in components that have registered interest. This is the architecture of choice for systems where multiple components must operate on the same data: compilers (the central repository is the symbol table and intermediate code), IDEs (the repository is the project file system), and database-centric applications. The advantage is that components are loosely coupled (they interact through data, not directly), and new components can be added easily as long as they understand the repository format. The disadvantage is that the repository becomes a single point of failure and a performance bottleneck, and the shared data model constrains all components.

Client-Server Architecture

Client-server architecture distributes the system between service requesters (clients) and service providers (servers). Clients send requests to servers, which process them and return responses. In a two-tier architecture, the client communicates directly with a database server. In a three-tier architecture, an application server sits between the client and the database server, handling business logic. In an n-tier architecture, additional layers (web servers, API gateways, microservices) are inserted between the client and the database. For a Film Library system, the architecture might include: a web-based client (browser) that sends search and reservation requests, an application server that processes film search logic, manages user accounts, and enforces borrowing rules, and a database server that stores the film catalogue, member records, and transaction history.

Part III · Measurement & Metrics

Software Metrics Overview

A software metric is a quantitative measure of a software attribute — size, complexity, quality, productivity, or any other property that can be counted, calculated, or estimated. Metrics matter because they transform subjective opinions ("this code feels messy") into objective, comparable measurements ("this module has a cyclomatic complexity of 23, which exceeds the recommended threshold of 10"). Without metrics, project management reduces to guesswork, quality assessment reduces to intuition, and process improvement has no baseline against which to measure progress.

Software metrics are broadly classified into three categories. Product metrics describe characteristics of the software product itself: size (lines of code, function points), complexity (cyclomatic complexity, Halstead's metrics), reliability (mean time between failures), and maintainability (coupling, cohesion measures). Process metrics describe characteristics of the development process: defect density, productivity (function points per person-month), and cycle time. Project metrics describe characteristics of the project: cost, schedule, team size, and effort distribution. For this unit, we focus on product metrics, specifically size-oriented measures and complexity measures.

Halstead's Software Science

Maurice Halstead proposed in 1977 that software could be measured using simple counts of operators and operands in a program, without requiring subjective judgement or external context. The insight is that a program's fundamental complexity is determined by its vocabulary (the number of distinct symbols it uses) and its length (the total number of symbols), from which derived measures like volume, difficulty, and effort can be calculated mathematically. This approach treats a program as a linguistic construct — a sequence of symbols drawn from a finite vocabulary — and applies information-theoretic measures to quantify its complexity.

Base Measures

n₁ = number of distinct operators (keywords, symbols like +, -, *, /, =, if, while, for, etc.)
n₂ = number of distinct operands (variables, constants like x, y, 42, MAX, etc.)
N₁ = total number of operators in the program (every occurrence counted)
N₂ = total number of operands in the program (every occurrence counted)

Derived Measures — Formulas

Program Vocabulary: n = n₁ + n₂
Program Length: N = N₁ + N₂
Estimated Length: N̂ = n₁ × log₂(n₁) + n₂ × log₂(n₂)
Volume: V = N × log₂(n)
Difficulty: D = (n₁ / 2) × (N₂ / n₂)
Effort: E = D × V
Time to Program: T = E / 18 seconds
Delivered Bugs: B = V / 3000

The intuition behind these measures is worth understanding for exam answers. Volume measures the information content of the program — a program with more symbols and a larger vocabulary has more information content and is therefore more complex. Difficulty measures how hard the program is to write or understand: it increases when the number of distinct operators is high (many different operations) and when operands are used frequently relative to the number of distinct operands (heavy reuse of a few variables, which makes the code harder to trace). Effort represents the total mental effort required to develop or understand the program, measured in elementary mental discriminations. Time converts effort into seconds, based on Halstead's empirically derived Stroud number of 18 (the number of elementary mental discriminations a human can make per second). Bugs estimates the number of delivered defects, based on the observation that programmers introduce roughly one error per 3000 units of volume.

Worked Example

Consider the following simple program:

while (f > 0) {
    c = c + 1;
    f = f - 1;
}

Step 1 — Count distinct operators (n₁): while, >, =, +, - → n₁ = 5

Step 2 — Count distinct operands (n₂): f, 0, c, 1 → n₂ = 4

Step 3 — Count total operators (N₁): while(1) + >(1) + =(2) + +(1) + -(1) → N₁ = 6

Step 4 — Count total operands (N₂): f(3) + 0(1) + c(2) + 1(1) → N₂ = 7

Function Point Analysis

Function Point (FP) analysis, developed by Allan Albrecht at IBM in 1979, measures software size from the user's perspective by counting the functional capabilities the system provides, independent of the programming language or technology used. This language-independence is the key advantage of function points over lines-of-code measures: a system that provides 500 function points of functionality is 500 function points whether it is implemented in C, Java, or Python, whereas the same system might be 5,000 lines in C and 3,000 lines in Python.

Function point analysis counts five types of function, each classified by complexity (Simple, Average, Complex) and weighted accordingly:

Function TypeDescriptionSimpleAverageComplex
External Inputs (EI)Data entering the system (forms, input screens)346
External Outputs (EO)Data leaving the system (reports, messages)457
External Inquiries (EQ)Queries that produce immediate output (search)346
Internal Logical Files (ILF)Data stored within the system (databases, files)71015
External Interface Files (EIF)Data referenced from external systems5710

The Unadjusted Function Point (UFP) count is the sum of (weight × count) for each function type. Next, fourteen General System Characteristics (GSC) are rated on a scale of 0 to 5, assessing factors like data communications, distributed processing, performance, heavily used configuration, transaction rate, online data entry, end-user efficiency, online update, complex processing, reusability, installation ease, operational ease, and multiple sites. The sum of these ratings gives the Value Adjustment Factor (VAF) = 0.65 + 0.01 × Σ(Fᵢ), where each Fᵢ is rated 0 to 5. The final Function Point count is: FP = UFP × VAF.

Function points are valuable for estimation because historical data allows organisations to correlate FP counts with effort (person-months), cost, and defect density. An organisation might know from experience that it delivers 15 FP per person-month, which allows it to estimate that a 300 FP project will require approximately 20 person-months. The primary criticism of FP analysis is its subjectivity: different analysts may classify the same function differently, leading to different counts. However, standardisation efforts by organizations like IFPUG have reduced this variability significantly.

"You cannot control what you cannot measure." — Tom DeMarco

Cyclomatic Complexity

McCabe's Cyclomatic Complexity is the single most frequently examined metric in this unit. It measures the number of independent paths through a program's control flow and directly predicts the minimum number of test cases required for complete branch coverage.

Thomas McCabe proposed in 1976 that the structural complexity of a program could be quantified by analysing its Control Flow Graph (CFG) — a directed graph where nodes represent processing statements or groups of statements, and edges represent the flow of control between them. Decision points (if, while, for, case) create branches in the graph, and the cyclomatic complexity V(G) counts the number of linearly independent paths through the graph — the minimum number of paths that, when combined, can produce every possible path through the program.

Three Methods to Calculate Cyclomatic Complexity

Method 1: V(G) = E − N + 2P
where E = number of edges, N = number of nodes, P = number of connected components (usually P = 1 for a single program, so V(G) = E − N + 2)

Method 2: V(G) = Number of decision nodes + 1
where a decision node is any node with two or more outgoing edges (if, while, for, case, &&, ||)

Method 3: V(G) = Number of regions in the CFG + 1
where a region is an enclosed area bounded by edges in the graph (including the outer region)

A cyclomatic complexity of 1 means the program is a straight line with no decisions — trivial. A value of 10 or below is generally considered acceptable for a single module. Values above 10 indicate increasing complexity and risk; values above 20 suggest the module should be refactored. The beauty of cyclomatic complexity is its direct practical application: V(G) tells you exactly how many test cases you need for complete branch coverage, and it tells you how many independent paths a code reviewer must examine.

Solved PYQ — Code Snippet 1

if (a > b)
    c = 3;
else
    c = 5;
c = c * c;

Figure 4 — Control Flow Graph for Code Snippet 1: V(G) = 4 − 4 + 2 = 2

Solution: Nodes (N) = 4, Edges (E) = 4, P = 1. V(G) = E − N + 2P = 4 − 4 + 2 = 2. By Method 2: 1 decision node (node 1) + 1 = 2. Independent paths: Path 1 → 2 → 4; Path 2 → 3 → 4. Two test cases required for branch coverage.

Solved PYQ — Code Snippet 2

while (x != y) {
    if (x > y)
        x = x - y;
    else
        y = y - x;
}
return x;

Solution: Nodes: 1 (while condition), 2 (if condition), 3 (x = x − y), 4 (y = y − x), 5 (return x). Edges: 1→2 (while true), 1→5 (while false), 2→3 (if true), 2→4 (if false), 3→1 (loop back), 4→1 (loop back). N = 5, E = 6. V(G) = 6 − 5 + 2 = 3. By Method 2: 2 decision nodes (while, if) + 1 = 3. Independent paths: (1, 2, 3, 1, 5), (1, 2, 4, 1, 5), (1, 5).

Solved PYQ — Code Snippet 3

int i, j, k;
for (i=0; i<=N; i++)
    p[i] = 1;
for (i=2; i<=N; i++) {
    k = p[i];
    j = i;
    while (a[p[j-1]] > a[k]) {
        p[j] = p[j-1];
        j--;
    }
    p[j] = k;
}

Solution: This is insertion sort. Decision nodes: for loop 1 (i<=N), for loop 2 (i<=N), while loop (a[p[j-1]] > a[k]). Three decision nodes. V(G) = 3 + 1 = 4. Independent paths: (1) First for loop executes normally, (2) Second for loop with while loop never executing, (3) Second for loop with while loop executing once, (4) Second for loop with while loop executing multiple iterations.

Solved PYQ — Code Snippet 4 (Python)

def check_number(num):
    if num > 0:
        print("Positive")
    elif num == 0:
        print("Zero")
    else:
        print("Negative")
    if num % 2 == 0:
        print("Even")
    else:
        print("Odd")

Solution: Decision nodes: if num > 0 (node with two branches: true to "Positive", false to elif check), elif num == 0 (decision node with two branches: true to "Zero", false to "Negative"), and if num % 2 == 0 (decision node with two branches). Total decision nodes = 3. V(G) = 3 + 1 = 4. Verification with E − N + 2: Nodes = 9 (entry, if, Positive, elif, Zero, Negative, if-odd, Even, Odd, exit — roughly 9), Edges = 11. V(G) = 11 − 9 + 2 = 4. Independent paths: (1) num > 0, even; (2) num > 0, odd; (3) num == 0, even; (4) num < 0, odd (and additional combinations — the key point is V(G) = 4).

Exam Strategy — Cyclomatic Complexity Problems

Step 1: Draw the Control Flow Graph carefully, numbering each node.
Step 2: Count nodes (N) and edges (E).
Step 3: Apply V(G) = E − N + 2.
Step 4: Verify with Method 2: count decision nodes + 1.
Step 5: State the independent paths explicitly.
Step 6: Interpret: "V(G) = X means X test cases are needed for branch coverage."

Part IV · Development

Development — Language, Coding & Documentation

Selecting a Programming Language

The choice of programming language is a design decision with consequences that ripple through every phase of the project. It affects development speed, runtime performance, team availability, maintainability, library ecosystem, and long-term cost. The selection should be driven by a systematic evaluation of project requirements against language capabilities, not by developer preference or fashion.

The criteria for language selection fall into several categories. Application domain is often the primary driver: embedded systems favour C or C++ for their low-level hardware access and minimal runtime overhead; web applications favour JavaScript/TypeScript (frontend) and Python/Java/Node.js (backend); data science favours Python and R; mobile development favours Kotlin (Android) and Swift (iOS). Performance requirements determine whether a compiled language (C, C++, Rust, Go) or an interpreted language (Python, Ruby) is appropriate — trading execution speed for development speed. Team expertise is a practical constraint: a team fluent in Java will be more productive in Java than in Haskell, regardless of Haskell's theoretical advantages for the problem domain. Ecosystem maturity — the availability of libraries, frameworks, tools, and community support — can make or break productivity; a language without good testing frameworks, build tools, and debugging support will slow the team regardless of its elegance. Maintainability considerations favour languages with strong type systems (Java, TypeScript), clear syntax (Python), and established coding conventions. Platform constraints may mandate specific languages: Android development requires Java or Kotlin; iOS development requires Swift or Objective-C; browser-based applications require JavaScript.

Coding Guidelines

Coding guidelines (also called coding standards or coding conventions) are a set of rules and recommendations that govern how source code is written within a project or organisation. They exist because code is read far more often than it is written — a typical line of code is written once but read dozens of times during code reviews, debugging, maintenance, and extension. The primary purpose of coding guidelines is not to constrain creativity but to ensure that all code in a project looks and behaves predictably, making it easier for any team member to understand any part of the codebase.

Good coding guidelines address: Naming conventions — how variables, functions, classes, and constants are named (e.g., camelCase for variables, PascalCase for classes, UPPER_SNAKE for constants); Indentation and formatting — tab vs. spaces (and how many), line length limits, brace placement; Comment conventions — when to comment, what style to use (Javadoc, docstrings, inline comments), how to document complex algorithms; Error handling — how exceptions are caught, logged, and propagated; Code structure — maximum function length, maximum nesting depth, file organization; and Language-specific best practices — avoiding deprecated features, using idiomatic constructs, following the principle of least surprise.

Code Documentation

Documentation is the bridge between the programmer's intention and the reader's understanding. Code documentation is classified into two fundamental types:

AspectInternal DocumentationExternal Documentation
LocationEmbedded within the source codeSeparate from source code (external files)
ExamplesComments, docstrings, annotations, meaningful variable/function namesUser manuals, design documents, API reference guides, README files, wikis
AudienceDevelopers and maintainers who read the codeUsers, system administrators, new team members, stakeholders
PurposeExplain what the code does, why specific decisions were made, how complex algorithms workExplain how to install, configure, use, and troubleshoot the software
MaintenanceUpdated when code changes (ideally simultaneously)Updated with each release; risk of becoming outdated
AdvantagesAlways visible alongside code; less likely to be lost; encourages good coding habitsAccessible to non-programmers; can include diagrams, tutorials, and examples
DisadvantagesCan clutter code if overused; may become misleading if not maintainedMay drift out of sync with code; requires separate maintenance effort

Internal documentation, when done well, transforms opaque code into self-explanatory prose. The most powerful form of internal documentation is not comments but meaningful naming: a variable called elapsedTimeInDays requires no comment, while one called d requires extensive explanation. When names are insufficient, well-crafted comments explain why something is done (the design rationale), not what is done (which the code itself should make clear). A comment that says // increment counter above a line that says counter++ is worse than no comment at all — it adds noise without value. A comment that says // Using binary search because data is always sorted by insertion order explains a design decision that is invisible from the code alone.

External documentation encompasses all written materials that accompany the software but live outside the source code. User manuals explain how to operate the software from the end-user's perspective. System design documents describe the architecture, data models, and interface specifications. API reference guides document the public interfaces of libraries and services with parameter descriptions, return values, exceptions, and usage examples. README files provide quick-start instructions for developers joining the project. The risk with external documentation is that it diverges from the actual software over time, especially in fast-moving projects — which is why modern development practices favour automatically generated documentation (like Javadoc or Sphinx) that extracts documentation from annotated source code, keeping internal and external documentation synchronised.
