Section 1

What Is a Compiler?

Understanding the bridge between human thought and machine execution

At its most fundamental level, a compiler is a program that reads a program written in one language — the source language — and translates it into an equivalent program in another language — the target language. In the vast majority of practical cases that a computer science student will encounter, the source language is a high-level programming language such as C, Java, or Pascal, and the target language is a low-level language such as assembly code or machine code that a particular processor can directly execute. This definition, while correct, barely scratches the surface of what makes compilers one of the most intellectually rich and practically significant areas in all of computer science. The act of compilation is not a simple word-for-word substitution; it is a profound transformation that must preserve the meaning, the semantics, of the original program while restructuring it entirely into a form that a fundamentally different kind of entity — a digital circuit — can interpret.

The reason compilers exist at all is rooted in a basic ergonomic reality: human beings think in terms of abstractions, structures, variables, loops, and mathematical expressions, whereas computers operate on binary voltage patterns that correspond to instructions in a processor's instruction set. Writing machine code by hand is not merely tedious; it is error-prone to the point of impossibility for any program of meaningful complexity. The compiler serves as an indispensable translator in this gap, allowing the programmer to express intent in a notation that is close to natural mathematical and logical reasoning, and then systematically converting that intent into precise mechanical steps. Without compilers, the entire edifice of modern software — operating systems, web browsers, mobile applications, scientific simulations — would simply not exist.

Formal Definition: A compiler is a program that reads a source program written in a high-level language and translates it into a functionally equivalent target program, typically in assembly language or machine language, while reporting any errors detected during the translation process.

It is important, especially at the university level, to distinguish a compiler from an interpreter. While both process high-level language programs, they do so in fundamentally different ways. A compiler translates the entire source program into a target program before execution begins; the target program then runs independently. An interpreter, by contrast, processes the source program line by line or statement by statement, executing each instruction as it goes, without ever producing a standalone target program. The practical consequences are significant: compiled programs generally run faster because the translation overhead is paid once, upfront, and the resulting machine code executes natively on the hardware. Interpreted programs, on the other hand, offer greater flexibility for debugging and interactive development, since there is no separate compilation step. Many modern systems, such as Java, use a hybrid approach — compiling to an intermediate bytecode and then interpreting or just-in-time compiling that bytecode.

Analogy: Think of a compiler as a professional translator who takes an entire novel written in French and produces a complete English edition. The reader then reads the English book independently. An interpreter, by contrast, is like a live translator sitting between two people in a conversation, converting each sentence as it is spoken. The compiled version takes longer to prepare but reads faster; the interpreted version starts immediately but proceeds more slowly.

In exams, when asked to define a compiler, always mention: (1) it translates source language to target language, (2) it preserves the semantics (meaning) of the source, (3) it reports errors, and (4) the target is typically assembly or machine code. Mentioning the compiler-vs-interpreter distinction earns additional marks in 5-mark and 10-mark questions.

Analysis of a Source Program

Deconstructing a program at multiple levels of abstraction

When a compiler encounters a source program, it does not simply read it as a flat stream of characters. Instead, it decomposes the program through a sequence of increasingly abstract analyses, each of which uncovers a different layer of structure. Understanding these layers of analysis is essential to understanding why a compiler is divided into the phases that it is, and each layer corresponds to a different kind of question the compiler asks about the program.

The first level of analysis is lexical analysis, where the compiler examines the raw character stream and groups characters into meaningful units called tokens. Consider the statement position := initial + rate * 60. At the character level, this is just a sequence of twenty-seven characters (including spaces). Lexical analysis recognizes that position is an identifier, that := is an assignment operator, that initial is another identifier, that + is an arithmetic operator, that rate is an identifier, that * is a multiplication operator, and that 60 is a numeric literal. The spaces between tokens are generally discarded as whitespace, which serves only to delimit tokens. This process of chunking characters into tokens is analogous to how a reader of English text groups individual letters into words, ignoring the spaces between them.

The second level is syntax analysis (or parsing), where the compiler examines the sequence of tokens and determines whether they form a grammatically valid statement according to the rules of the programming language. The parser organizes tokens into a hierarchical structure — typically a parse tree or an abstract syntax tree — that reflects the syntactic structure of the program. For our example, the parser would determine that the statement is an assignment statement, that the right-hand side is an arithmetic expression involving addition and multiplication, and that multiplication has higher precedence than addition, so the tree groups rate * 60 before adding initial.

The third level is semantic analysis, where the compiler checks whether the syntactically valid statement is also meaningful. This involves checking type compatibility (you cannot multiply a string by an integer), verifying that all variables have been declared, ensuring that function calls have the correct number and types of arguments, and performing other contextual checks that cannot be captured by syntax rules alone. Semantic analysis uses information stored in a symbol table, which is a data structure that records information about every identifier in the program — its type, scope, memory location, and other attributes.

The three levels of analysis — lexical, syntactic, and semantic — correspond to three fundamentally different kinds of questions: What are the words? (lexical), Is the sentence grammatical? (syntactic), and Does the sentence make sense? (semantic). This layered approach mirrors how natural language understanding works and is one of the great organizing principles of compiler design.

Section 3

The Phases of a Compiler

Six transformations from source to target, orchestrated by symbol table and error handler

A compiler is not a monolithic block of code; it is organized into a series of phases, each of which transforms the program from one representation to another, progressively moving it closer to the target language. The classical model of a compiler, as presented in the Dragon Book (Aho, Lam, Sethi, Ullman), identifies six main phases plus two essential supporting components: the symbol table manager and the error handler. Understanding each phase, its input, its output, and the specific transformation it performs is absolutely central to answering exam questions in compiler design, and it is the kind of knowledge that rewards deep understanding rather than rote memorization.

Fig 1. — The classical six-phase compiler architecture, showing the pipeline from source to target code, with the Symbol Table Manager and Error Handler as shared components. The bracket annotations show which phases compose the front end (analysis) and back end (synthesis).

Phase 1 — Lexical Analysis (Scanning)

The very first phase of compilation is lexical analysis, performed by the lexical analyzer, also called the scanner. This phase reads the raw character stream of the source program and groups characters into meaningful sequences called lexemes, producing a stream of tokens as output. Each token is a pair consisting of a token name (an abstract symbol representing the kind of lexical unit) and an optional attribute value (pointing to the relevant entry in the symbol table). Whitespace characters — spaces, tabs, newlines — are typically consumed and discarded by the scanner, since they serve only to separate lexemes and carry no semantic content in most programming languages (though in languages like Python, indentation does carry meaning, handled at later stages).

Consider the statement position := initial + rate * 60. The lexical analyzer produces the following token stream, which it passes to the next phase:

LexemeToken NameAttribute Value
position<id, 1>Symbol table entry 1
:=<assign>—
initial<id, 2>Symbol table entry 2
+<+>—
rate<id, 3>Symbol table entry 3
*<*>—
60<num, 4>Symbol table entry 4 (value: 60)

The symbol table entries are populated during this phase. The lexical analyzer inserts each new identifier it encounters into the symbol table (if it is not already there) and passes a pointer to the entry as the token's attribute. For numeric literals, the actual numeric value may be stored. This is the compiler's first interaction with the symbol table, and it is far from the last — every subsequent phase will read from and write to this central data structure.

Phase 2 — Syntax Analysis (Parsing)

The syntax analyzer, or parser, receives the token stream from the lexical analyzer and organizes it into a hierarchical structure that reflects the grammatical structure of the source language. The most common representation is a parse tree (also called a syntax tree), in which the interior nodes represent syntactic constructs (such as "assignment statement" or "arithmetic expression") and the leaf nodes represent tokens. The parser checks whether the token sequence conforms to the grammar rules of the language — if the tokens form a sentence that can be derived from the start symbol of the grammar, the program is syntactically valid; otherwise, a syntax error is reported.

For our running example position := initial + rate * 60, the parser would construct a tree where the root is labeled "assignment," the left child is the identifier position, and the right child is an expression tree with + at its top, initial as its left operand, and * as its right operand's root, with rate and 60 as the multiplicand and multiplier. This tree structure captures the fact that multiplication binds more tightly than addition — a fact that was not explicitly present in the flat token stream but is part of the language's grammatical rules.

Phase 3 — Semantic Analysis

Semantic analysis uses the syntactic structure produced by the parser and the information in the symbol table to check the source program for semantic consistency with the language definition. The most important task performed during this phase is type checking. The semantic analyzer examines each operator and its operands to verify that the types are compatible. If rate is declared as a floating-point number and 60 is an integer literal, the semantic analyzer may insert an implicit type conversion (a "coercion") from integer to float before the multiplication. If an operation involves fundamentally incompatible types — such as multiplying a string by a boolean — the semantic analyzer reports a type error.

A key data structure produced by semantic analysis is the annotated syntax tree, which is the parse tree augmented with type information at each node. The semantic analyzer may also perform other checks: verifying that every variable is declared before use, ensuring that function arguments match parameter types, checking that break statements appear only inside loops, and so on. The output of this phase is a fully validated, type-annotated intermediate representation ready for code generation.

Phase 4 — Intermediate Code Generation

After semantic analysis, the compiler generates an explicit intermediate representation (IR) of the source program. This representation is designed to be easy to produce from the annotated syntax tree and easy to translate into the target machine code. It is deliberately independent of any specific machine architecture, which makes the compiler more portable and modular. The most common form of intermediate representation is three-address code, in which each instruction has at most one operator on the right-hand side and exactly one assignment on the left-hand side.

For our example position := initial + rate * 60, the three-address code would be:

t1 := int_to_real(60)
t2 := rate * t1
t3 := initial + t2
position := t3

Here, t1, t2, t3 are compiler-generated temporary variables that hold intermediate results. The instruction int_to_real(60) represents the type conversion inserted by the semantic analyzer. Each instruction is simple enough that it can be implemented with a small number of machine instructions, making it an ideal bridge between the high-level source and the low-level target.

Phase 5 — Code Optimization

The code optimization phase attempts to improve the intermediate code so that the resulting target code runs faster, uses less memory, or consumes less power, while preserving the exact meaning of the original program. This is one of the most mathematically sophisticated and practically impactful phases of compilation, and in industrial compilers (such as GCC or LLVM), the optimizer is by far the largest and most complex component.

Optimizations can be broadly classified into machine-independent optimizations (which operate on the intermediate code without knowledge of the target machine) and machine-dependent optimizations (which exploit specific features of the target hardware). Common machine-independent optimizations include constant folding (evaluating constant expressions at compile time), dead code elimination (removing code whose results are never used), common subexpression elimination (recomputing a previously computed expression only if its operands have changed), and loop optimization (moving invariant computations out of loops).

For our example, a simple optimization might observe that if rate and initial are constants known at compile time, the entire expression could be evaluated by the compiler and the result assigned directly — a process called constant propagation and folding. Even in the general case, the optimizer might reorder operations or eliminate unnecessary temporaries to produce more efficient code.

Phase 6 — Code Generation

The final phase is code generation, which takes the optimized intermediate representation and translates it into the target language, typically assembly language or relocatable machine code for a specific processor architecture. This phase involves instruction selection (choosing which machine instructions to use for each IR operation), register allocation (deciding which variables and temporaries should reside in the limited number of processor registers at each point in the program), and instruction scheduling (ordering instructions to exploit the pipelining and parallelism of the target processor).

For a hypothetical machine with registers R1, R2, etc., the code for our example might look like:

MOVF  rate, R1     ; Load rate into R1
MULF  #60.0, R1    ; Multiply R1 by 60.0
ADDF  initial, R1  ; Add initial to R1
MOVF  R1, position ; Store R1 into position

The code generator must make decisions about memory layout, addressing modes, and instruction formats that are specific to the target architecture. A well-designed compiler separates these machine-dependent decisions from the earlier phases, making it possible to retarget the compiler to a new machine by replacing only the code generator (and, partially, the optimizer).

The Symbol Table Manager

The symbol table is a data structure — typically a hash table or a set of linked hash tables — that stores information about every identifier (variable, function, type, constant, label) appearing in the source program. For each identifier, the symbol table records its name, type, scope (the region of the program in which it is visible), memory location, and any other attributes relevant to compilation. The symbol table is consulted and updated by virtually every phase: the lexical analyzer inserts new identifiers, the parser may record structural information, the semantic analyzer records type information, and the code generator records memory addresses and register assignments.

Scope management is a particularly important aspect of symbol table design. In languages with nested scopes (like C or Pascal), the compiler must maintain a scope stack so that when a new block (such as a function body) begins, a new scope is pushed onto the stack, and when the block ends, the scope is popped. An identifier lookup searches the scopes from the innermost outward, so that local declarations shadow enclosing ones. This mechanism is what makes it legal to declare a variable x inside a function even though x is also declared in the global scope — the local x "shadows" the global one within the function.

The Error Handler

Every phase of the compiler can detect errors. The error handler is the component responsible for reporting these errors in a way that is helpful to the programmer, and, where possible, for enabling the compiler to recover from errors and continue processing the remainder of the source program. A compiler that halts at the first error is of little practical use; a good compiler should detect and report as many errors as possible in a single run.

Errors detected by the lexical analyzer include illegal characters (such as @ in a language that does not use it) and malformed tokens (such as a floating-point number with two decimal points). Errors detected by the parser include missing semicolons, unbalanced parentheses, and invalid statement structures. Errors detected by the semantic analyzer include type mismatches, undeclared variables, and incorrect function call signatures. At each phase, the error handler uses a different strategy for error recovery: panic mode (skip input until a synchronizing token is found), phrase-level recovery (insert or delete tokens to repair the parse), or error productions (augment the grammar with rules for common mistakes).

Compilation in Action

Tracing a = b + c * 70 through every phase

One of the most frequently asked questions in compiler design examinations is to trace a given statement through all the phases of the compiler. This type of question can appear as a 10-mark or 15-mark question, and the student who can write a detailed, step-by-step walkthrough with diagrams and intermediate representations will score exceptionally well. Let us trace the statement a = b + c * 70 through each phase in complete detail.

Step 1 — Lexical Analysis (Scanning)

The lexical analyzer reads the character stream a = b + c * 70 and produces a sequence of tokens. It recognizes each lexeme, determines its token type, and either inserts it into the symbol table (for identifiers) or stores its value (for numeric literals). The resulting token stream is:

Token #LexemeToken NameAttribute
1a<id, 1>Entry 1 in symbol table
2=<assign>—
3b<id, 2>Entry 2 in symbol table
4+<+>—
5c<id, 3>Entry 3 in symbol table
6*<*>—
770<num, 4>Value 70 stored

The symbol table at this point contains entries for a, b, c, and the literal 70. Whitespace characters have been consumed and discarded.

Step 2 — Syntax Analysis (Parsing)

The parser receives the token stream and determines that it is a valid assignment statement whose right-hand side is an arithmetic expression. Using the grammar rules of the language, it constructs a parse tree. Because multiplication (*) has higher precedence than addition (+c * 70 as a subexpression under the + node. The parse tree structure is:

Fig 2. — Parse tree for a = b + c * 70. The tree hierarchy correctly reflects that * binds more tightly than +.

Step 3 — Semantic Analysis

The semantic analyzer walks the parse tree, performing type checks. Assuming a, b, and c are all of type integer, and 70 is an integer literal, the types are compatible throughout. No type conversion is needed. If, however, c were of type float, the semantic analyzer would insert a conversion from int to float before the multiplication. The output is an annotated parse tree where each node carries type information.

Step 4 — Intermediate Code Generation

The intermediate code generator traverses the annotated tree and produces three-address code. Each three-address instruction has at most one operator:

t1 := c * 70
t2 := b + t1
a  := t2

Here t1 and t2 are compiler-generated temporaries. Note that the order of operations (multiply before add) is preserved by the structure of the instructions. This representation is machine-independent and serves as the input to the optimizer.

Step 5 — Code Optimization

The optimizer examines the intermediate code for possible improvements. In this simple example, if the values of b and c are not known at compile time, there is limited opportunity for optimization. However, the optimizer might determine that t2 is used only once (as the source for the assignment to a), so it can eliminate the temporary and directly assign the result to a:

t1 := c * 70
a  := b + t1

This is an example of copy propagation and dead code elimination working together. In more complex programs, the optimizer performs far more sophisticated transformations.

Step 6 — Code Generation

The code generator translates the optimized intermediate code into target machine instructions. For a hypothetical machine with registers R1 and R2:

MOV  c, R1        ; Load c into R1
MUL  #70, R1      ; R1 = c * 70
MOV  b, R2        ; Load b into R2
ADD  R1, R2       ; R2 = b + (c * 70)
MOV  R2, a        ; Store result in a

The code generator selected registers for the two operands, chose appropriate machine instructions, and ensured that the final result was stored back in the memory location associated with identifier a.

For 10-mark and 15-mark exam questions: Always show all six phases with intermediate outputs. Draw the parse tree. Write the three-address code. Write the optimized code. Write the target assembly code. Mention the symbol table and error handler. This level of completeness demonstrates mastery and earns full marks.

Section 5

Front-End vs. Back-End

The architectural division that makes compilers portable

The six phases of a compiler are commonly divided into two major groups. The front end comprises lexical analysis, syntax analysis, semantic analysis, and intermediate code generation — the four phases that deal with the source language. The back end comprises code optimization and code generation — the phases that deal with the target machine. This division is not merely organizational; it reflects a deep architectural insight that enables one of the most powerful ideas in compiler engineering: the ability to build a single front end for a language and combine it with multiple back ends for different machines, or conversely, to build a single back end for a machine and combine it with front ends for different languages. This is how the GNU Compiler Collection (GCC) supports dozens of source languages and dozens of target architectures with a combinatorial number of compilers, rather than requiring a separate, monolithic compiler for each language-machine pair.

AspectFront EndBack End
PhasesLexical, Syntax, Semantic Analysis, Intermediate Code GenerationCode Optimization, Code Generation
InputSource program (character stream)Intermediate representation (IR)
OutputIntermediate representationTarget machine code
Depends onSource language grammar and semanticsTarget machine architecture

Error detectionLexical, syntax, semantic errorsFew new errors (code quality issues)
Portability roleChange front end to support new languageChange back end to target new machine

The front end is responsible for analysis — understanding the source program. The back end is responsible for synthesis — generating the target program. The intermediate representation serves as the contract between the two, the common language that decouples them.

A modular compiler designed for easy swapping of front-end and back-end components typically defines a clean, well-documented intermediate representation as the interface between the two halves. The LLVM project is the modern exemplar of this design philosophy: LLVM IR (Intermediate Representation) serves as the universal contract. Any language that compiles to LLVM IR can immediately benefit from LLVM's powerful optimizer and its many back ends (x86, ARM, RISC-V, WebAssembly, and more). This architectural insight — the separation of analysis from synthesis via a well-defined intermediate form — is arguably the single most important engineering principle in compiler design.

Section 6

Cousins of the Compiler

The ecosystem of translation and transformation tools

A compiler does not operate in isolation. It exists within a broader ecosystem of tools that collectively transform a high-level program into a running executable. These tools — preprocessors, assemblers, linkers, and loaders — are sometimes called the "cousins" of the compiler because they perform related but distinct translation and transformation tasks. Understanding these cousins is essential for a complete picture of how a program goes from source code on disk to executing instructions in a processor's memory.

Preprocessor

The preprocessor is a program that processes the source program before the compiler proper begins its work. In C and C++, the preprocessor handles directives that begin with #, such as #include (which textual includes the contents of header files), #define (which defines macros — text-substitution abbreviations), and #ifdef / #endif (which conditionally include or exclude sections of code based on compile-time flags). The output of the preprocessor is a "translation unit" — a fully expanded, self-contained version of the source file — which is then fed to the compiler. The preprocessor operates purely on text; it has no understanding of the programming language's syntax or semantics. Modern languages like Java and Rust have largely moved away from textual preprocessors in favor of more structured module and macro systems.

Assembler

The assembler translates the assembly language output of the compiler's code generation phase into relocatable machine code — a binary object file containing machine instructions in the format expected by the target processor, but with addresses that are not yet final. Assembly language is a human-readable representation of machine code, with one assembly instruction corresponding to one machine instruction (usually). The assembler replaces symbolic operation codes (like MOV, ADD) with their binary encodings, resolves local labels and offsets, and produces an object file (typically with a .o or .obj extension) that can be combined with other object files by the linker.

Linker (Link Editor)

A large program is typically divided into multiple source files, each of which is compiled and assembled separately into its own object file. The linker (also called a link editor) combines these multiple object files and resolves external references — addresses of functions and variables defined in one file but referenced in another. The linker also incorporates code from libraries (collections of precompiled object files for standard functions like printf or malloc). The output of the linker is a single executable file (or a shared library) in which all addresses have been resolved and the program is ready to be loaded into memory. There are two types of linking: static linking, where library code is copied into the executable at link time, and dynamic linking, where references to shared libraries are resolved at load time or run time.

Loader

The loader is the final stage before execution. It is part of the operating system and is responsible for reading the executable file from disk into main memory, setting up the address space for the program (including the stack, heap, and code segments), performing any remaining address relocation, and transferring control to the program's entry point (typically the main function in C). In modern operating systems with virtual memory, the loader does not necessarily load the entire program into physical memory at once; instead, it sets up the virtual address space and allows the demand paging mechanism of the OS to load pages of code and data as they are actually needed during execution.

"The journey from source code to running program is not a single leap but a carefully orchestrated sequence of transformations, each performed by a specialized tool — the preprocessor expands, the compiler translates, the assembler encodes, the linker combines, and the loader places."
Complete Compilation Pipeline (Sequence of Tools)
Source (.c) → Preprocessor (cpp) → Expanded Source (.i) → Compiler (cc1) → Assembly (.s) → Assembler (as) → Object (.o) → Linker (ld) → Executable (a.out) → Loader → Execution

This is the complete pipeline for a C program on a Unix-like system. Each stage produces an intermediate file that is consumed by the next stage. The names in parentheses (cpp, cc1, as, ld) are the actual tool names used in the GNU toolchain.

Section 7

Grouping of Phases & Passes

Single-pass, multi-pass, and the art of bootstrapping

The six phases of a compiler can be grouped in various ways, and the concept of a pass is central to this discussion. A pass is a single traversal of the source program (or its intermediate representation) during which one or more phases are performed. A compiler that reads the source program only once, producing the target code as it goes, is called a single-pass compiler. A compiler that reads the source program (or intermediate files) multiple times is called a multi-pass compiler.

Single-Pass Compiler

In a single-pass compiler, all phases are interleaved into a single traversal of the source program. The compiler reads the source from beginning to end exactly once, and as each construct is recognized, it is immediately translated into the target code. This design is efficient in terms of compilation speed because it avoids writing and reading intermediate files, and it requires less memory since the entire program need not be stored. However, single-pass compilers face severe limitations: they cannot handle language features that require knowledge of information that appears later in the source file. For example, in a language like Pascal (as originally designed by Wirth), all types and variables must be declared before they are used, which is specifically a design choice to enable single-pass compilation. A single-pass compiler cannot easily perform global optimizations, since it sees each part of the program only once.

The most famous example of a single-pass compiler is the original Pascal compiler, which Niklaus Wirth implemented in Pascal itself. The C language also has characteristics of a single-pass language, particularly in its header-file mechanism, where #include provides the compiler with declarations of functions and types that are defined in other files, enabling single-pass compilation of each translation unit.

Multi-Pass Compiler

In a multi-pass compiler, the source program or its intermediate representations are read multiple times, with each pass performing one or more phases. For example, the first pass might perform lexical and syntax analysis to build a parse tree, the second pass might perform semantic analysis and intermediate code generation, and the third pass might perform code optimization and code generation. Each pass reads its input from an intermediate file produced by the previous pass and writes its output to an intermediate file for the next pass (or, in memory-efficient designs, the intermediate representations are held in memory).

Multi-pass compilers have several advantages: they can handle language features that require information from later in the source (such as forward references), they can perform more sophisticated optimizations (which require seeing the entire program), and they are more modular (each pass can be developed, tested, and maintained independently). The disadvantage is increased compilation time, since the program must be read and written multiple times, and more disk space is needed for intermediate files.

Factors That Decide the Number of Phases

The number and grouping of phases in a compiler is determined by several factors:

  1. Language complexity: Languages with complex grammars and semantics (like C++) require more phases than simpler languages.
  2. Target machine complexity: Complex architectures (with many instruction formats, addressing modes, and pipeline hazards) require more back-end phases.
  3. Optimization requirements: Aggressive optimization requires multiple passes and sophisticated analysis phases.
  4. Memory constraints: Limited memory may force the compiler to use multiple passes, writing intermediate results to disk.
  5. Compiler construction tools available: Tools like parser generators and scanner generators may influence the phase structure.
  6. Modularity and maintainability: A more decomposed design is easier to develop and maintain.

Bootstrapping

Bootstrapping is the process of using a compiler written in its own source language to compile itself. This seems circular at first glance — how can you compile a compiler if you need the compiler to do the compilation? — but it resolves elegantly through a two-step process. Suppose we have a new language L for which we want to build a compiler C written in L itself. First, we write a small, simple compiler C₀ for L in some other language (such as assembly or an existing language) that is already available on the target machine. This initial compiler C₀ need not be fast or produce optimized code; it only needs to be correct. We then use C₀ to compile the full compiler C written in L, producing an executable C₁. Finally, we use C₁ to compile C again, producing C₂ — the final compiler, compiled by itself, which is both correct and (if C includes optimizations) produces optimized code.

The bootstrapping arrangement for three machines A, B, and C is a classic exam question. Suppose the compiler for language L is written in L itself and currently runs on machine A. We want to move it to machine B (a cross-compilation scenario). The process is:

  1. Modify the compiler's source (written in L) to generate code for machine B instead of machine A.
  2. Compile this modified compiler using the existing compiler on machine A. The result is a compiler that runs on A but generates code for B.
  3. Run this cross-compiler on machine A, feeding it its own source code as input. The output is a compiler that runs on B and generates code for B.
  4. Transfer the resulting binary to machine B and run it. Now the compiler is native to B.

This process can be extended to a third machine C by repeating the steps. Bootstrapping is a beautiful example of self-reference in computer science, and understanding it demonstrates a deep appreciation for what compilers are and how they are built.

Recall trick for bootstrapping: Think of it as "pulling yourself up by your own bootstraps." You start with a small, simple compiler (the bootstrap) that is just good enough to compile the real compiler. The bootstrap compiler is like training wheels — you need it to get started, but once the real compiler is built, you can throw it away.

Compiler Construction Tools

The specialized tools that automate parts of compiler building

Building a compiler from scratch is a massive undertaking, but fortunately, a rich ecosystem of compiler construction tools exists to automate many of the tedious and error-prone tasks involved. These tools generate compiler components from high-level specifications, freeing the compiler writer to focus on the creative and architectural aspects of the design. Section 9

Lexical Analysis: The First Gate

Why the scanner is separated from the parser, and what it must accomplish

Having now surveyed the overall architecture of a compiler, we turn to a deep study of the first phase: lexical analysis. The lexical analyzer, or scanner, is the component that reads the raw character stream of the source program and produces a stream of tokens for the parser. It is the compiler's first point of contact with the source text, and its design has significant implications for the efficiency and correctness of the entire compilation process.

Why Separate Lexical Analysis from Parsing?

A natural question arises: why not have the parser read characters directly? Why introduce an entire separate phase? The answer lies in several practical and theoretical considerations. First, simplicity of design: separating lexical analysis from parsing allows each phase to use the most appropriate mathematical model. Lexical analysis operates on the simple, flat structure of character sequences and is best described by regular expressions and finite automata. Parsing operates on the hierarchical, nested structure of grammatical constructs and requires context-free grammars and pushdown automata. Mixing these two levels of complexity in a single phase would make the resulting system far more complex and harder to understand.

Second, efficiency: the lexical analyzer processes the entire source program character by character, which is a very I/O-intensive operation. By grouping characters into tokens before passing them to the parser, the lexical analyzer reduces the number of units the parser must handle by a large factor — typically by a factor of ten or more. Since the parser's work is more computationally intensive per unit (it must maintain a stack and perform grammatical reductions), reducing the number of units it processes has a significant impact on overall compilation speed.

Third, portability: the only phase that deals with character-level details of the source language (such as the character encoding, the representation of newlines, and the handling of special characters) is the lexical analyzer. By isolating these platform-specific details in the scanner, the rest of the compiler can be made independent of the character set and encoding used by the source program.

Key Terminology:

  • Token: A pair consisting of a token name (an abstract symbol representing a kind of lexical unit) and an optional attribute value (pointing to the symbol table entry for this particular instance).
  • Lexeme: The actual character sequence in the source program that matches the pattern for a token. For example, position is a lexeme whose token is <id>.
  • Pattern: The rule that describes which character sequences can form a particular token. For the token <id>, the pattern might be "a letter followed by zero or more letters or digits."
  • Attribute: Additional information associated with a token, such as the pointer to the symbol table entry (for identifiers) or the actual numeric value (for number literals).

Analogy for Token, Lexeme, and Pattern: Think of the token name as the category label on a filing cabinet (e.g., "Identifier"), the pattern as the rule for what goes in that cabinet (e.g., "starts with a letter, followed by letters or digits"), and the lexeme as the specific document being filed (e.g., position). Different lexemes can match the same pattern and produce the same token name — position, initial, and rate are all different lexemes that produce the token <id> — but each has a different attribute value (pointing to a different symbol table entry).

Input Buffering

How the scanner reads characters efficiently from the source file

The lexical analyzer must read characters from the source file one at a time as it identifies tokens. Since disk I/O is significantly slower than in-memory operations, reading one character at a time from the file system would be extremely inefficient. The solution is to use input buffering, where large blocks of characters are read from the file into memory buffers, and the scanner then reads characters from these buffers at memory speed. The design of the buffering scheme has a meaningful impact on the scanner's performance, and the evolution from a naive one-buffer scheme to the standard two-buffer scheme with sentinels is a beautiful example of engineering optimization in practice.

The One-Buffer Scheme

The simplest buffering approach uses a single buffer of some fixed size. A block of characters is read from the source file into the buffer. A pointer (often called forward) scans through the buffer from left to right, and the lexical analyzer examines each character as it goes. When the buffer is exhausted, the next block is read from the file, overwriting the previous contents, and the forward pointer is reset to the beginning.

The critical problem with this scheme is the handling of lexemes that span buffer boundaries. Consider a buffer of 80 characters. If the 78th character is the beginning of a long identifier that extends into the 81st character, the identifier straddles the boundary between the current buffer and the next. When the buffer is refilled, the characters at the beginning of the identifier are lost. One could solve this by copying the unfinished lexeme to a separate buffer (a "lexeme buffer" or string table), but this copying adds overhead and complexity.

The Two-Buffer Scheme (Sentinel Technique)

The standard solution, described in the Dragon Book, uses a single large buffer divided into two equal halves, each of size N characters. This is the two-buffer scheme. At any given time, one half is active (being scanned by the forward pointer), while the other half may be refilled from the file if needed. When the forward pointer reaches the end of one half, the next half is loaded with fresh characters from the source file, and the scanner continues seamlessly into the new half.

The scheme maintains two pointers: lexemeBegin, which marks the beginning of the current lexeme being recognized, and forward, which scans ahead one character at a time. When a complete lexeme has been identified, lexemeBegin is advanced past it to start recognizing the next lexeme. If forward needs to look ahead past the current lexeme (as is common in lookahead-based scanning), it may need to cross a buffer boundary. The two-buffer scheme ensures that the characters at the boundary are preserved in the other half, so no data is lost.

Fig 3. — The two-buffer input scheme. The buffer is divided into two halves. The lexemeBegin pointer marks the start of the current lexeme, while forward scans ahead. EOF sentinel characters at the end of each half allow the scanner to detect end-of-buffer without an explicit comparison at every step.

The Sentinel Technique

A subtle but important optimization in the two-buffer scheme is the use of sentinel characters. In a naive implementation, the scanner must check at every step whether the forward pointer has reached the end of the current buffer half. This means every character read requires two comparisons: one to check for the specific condition being tested (e.g., "is this a digit?") and one to check whether the end of the buffer has been reached. Since the end-of-buffer check happens for every character, even though the end of the buffer is reached relatively rarely, this adds a constant overhead of roughly 50% to the scanning process.

The sentinel technique eliminates the end-of-buffer check for most characters by placing a special sentinel character — typically the eof character — at the very end of each buffer half (at positions N-1 and 2N-1). Since eof cannot appear in valid source code, the scanner can treat it as a character that will never match any token pattern. Thus, the scanner only needs to check for end-of-buffer when it encounters the sentinel — which is exactly once per buffer half, rather than once per character. This seemingly small optimization can make a meaningful difference in the performance of a compiler that processes millions of characters in a large source file.

Algorithm: Lookahead with Sentinels

// Two-buffer scheme with sentinel
initialize:
  read N characters into buffer[0..N-1]
  set buffer[N-1] = eof    // sentinel
  read N characters into buffer[N..2N-1]
  set buffer[2N-1] = eof   // sentinel
  lexemeBegin = 0
  forward = 0

scan:
  loop:
    if forward == N:              // reached end of half 1
      reload half 2 from file
      forward = 0                 // switch to half 2
    else if forward == 2*N:       // reached end of half 2
      reload half 1 from file
      forward = N                 // switch to half 1

    c = buffer[forward]
    if c == eof and (forward == N-1 or forward == 2*N-1):
      // true end of file (sentinel)
      handle end-of-file
    else:
      process character c
      forward = forward + 1

The key insight is that the sentinel at position N-1 or 2N-1 causes the scanner to enter the buffer-switching code naturally, without an explicit comparison at every character. A real sentinel (one placed because the file actually ended) is distinguished from a boundary sentinel by its position.

Will a Three-Buffer Scheme Further Improve Performance?

This is an insightful question that appears in some exams. The two-buffer scheme is already highly efficient because it overlaps computation (scanning the current half) with I/O (reading the next half from the file). In practice, the bottleneck is usually the I/O operation. A three-buffer scheme would allow double-buffering of I/O: while the scanner processes one buffer, the system could be reading the next two buffers ahead. In theory, this could hide I/O latency more effectively, particularly on systems with slow disk access. However, the additional memory overhead (50% more buffer space) and the added complexity of managing three buffers rarely justify the marginal improvement in practice. Modern operating systems already provide their own I/O buffering and prefetching, which achieves a similar effect transparently. The two-buffer scheme remains the standard design because it achieves an excellent balance of simplicity, efficiency, and correctness.

Specification & Recognition of Tokens

Regular expressions, transition diagrams, and the formal machinery of scanning

The two fundamental questions in lexical analysis are: What are the valid tokens? (specification) and How do we identify them in the character stream? (recognition). Token specification uses the mathematical formalism of regular expressions, while token recognition uses the computational model of finite automata, typically represented as transition diagrams. The beautiful correspondence between regular expressions and finite automata — that every regular expression can be converted to a finite automaton and vice versa — is what makes lexical analysis both theoretically well-founded and practically efficient.

Regular Expressions

A regular expression is a notation for describing a set of strings (a language) using a compact algebraic syntax. Regular expressions are built from three fundamental operations:

  1. Union (alternation): Written r | s (or r + s in some notations), it matches any string that matches r or s. For example, a | b matches the single character a or the single character b.
  2. Concatenation: Written rs (with no operator symbol), it matches any string that consists of a string matching r followed immediately by a string matching s. For example, ab matches exactly the two-character string ab.
  3. Closure (Kleene star): Written r*, it matches zero or more occurrences of any string matching r. For example, a* matches ε (the empty string), a, aa, aaa, and so on, ad infinitum.

There are also derived operations that are convenient shorthands. The positive closure r+ matches one or more occurrences of strings matching r (so r+ = rr*). The option r? matches zero or one occurrence (so r? = r | ε). Character classes such as [a-z] are shorthands for unions: [a-z] = a | b | c | ... | z.

The precedence of operators in regular expressions is: Kleene star (*) binds tightest, then concatenation, then union (|). Parentheses can be used to override precedence, just as in arithmetic. So a | bc* means a | (b(c*)) — it matches either a, or b followed by zero or more c's.

The first approach is simpler and more common in practice.

The LEX Compiler

Generating scanners automatically from regular expression specifications

Writing a lexical analyzer by hand, while educational, is tedious and error-prone for any non-trivial language. The LEX tool (and its modern GNU implementation, Flex) is a scanner generator that automates this process. LEX takes as input a specification file containing regular expressions paired with actions, and produces as output a C program that implements a lexical analyzer corresponding to those specifications. This C program can then be compiled and linked with the rest of the compiler. LEX is one of the most widely used compiler construction tools and has been a standard part of the Unix programming environment since the 1970s.

Fig 4 . — The LEX compilation pipeline. The LEX specification file (.l) is processed by the LEX compiler to generate a C source file (lex.yy.c). This file is compiled by the C compiler and linked with the LEX library to produce an executable scanner. The scanner's yylex() function is called by the parser each time it needs the next token.

Input Specification File Format

A LEX specification file (with the extension .l) has a specific three-section format, with each section separated by a delimiter consisting of two percent signs (%%):

{definitions}
%%
{rules}
%%
{user subroutines}

Section 1: Definitions. This section contains regular definitions (named regular expressions) and C declarations enclosed in %{ ... %} delimiters. The declarations are copied verbatim into the generated C file, typically including #include directives and global variable declarations. Regular definitions give names to commonly used patterns, making the rules section more readable.

Section 2: Rules. This is the core of the specification. Each rule has the form:

pattern    { action }

where pattern is a regular expression describing a token and action is a C code block to be executed when the pattern matches. The patterns are matched against the input in order; when multiple patterns match the same input, the first rule listed takes priority. Additionally, when the same pattern matches substrings of different lengths, LEX follows the maximal munch rule: it matches the longest possible prefix of the remaining input.

Section 3: User Subroutines. This section contains additional C functions that are copied verbatim into the generated file. It typically includes auxiliary functions called by the actions, such as symbol table lookup routines or error reporting functions. This section may be empty.

Example LEX Program

The following LEX specification implements a simple scanner that recognizes identifiers, unsigned integers, whitespace, and assignment operators:

/* === Section 1: Definitions === */
%{
#include <stdio.h>
#include "tokens.h"
int line_number = 1;
%}

letter    [A-Za-z_]
digit     [0-9]
id        {letter}({letter}|{digit})*
num       {digit}+

%%

 /* === Section 2: Rules === */

[ \t]+      { /* skip whitespace */ }
\n          { line_number++; }

{id}        {
              yylval = install_id(yytext);
              return ID;
            }

{num}       {
              yylval = atoi(yytext);
              return NUM;
            }

":="        { return ASSIGN; }
"+"         { return PLUS; }
"*"         { return STAR; }
";"         { return SEMI; }
"("         { return LPAREN; }
")"         { return RPAREN; }

.           {
              printf("Line %d: illegal character '%s'\n",
                     line_number, yytext);
            }

%%

 /* === Section 3: User Subroutines === */

int install_id(char *text) {
    /* Look up or insert identifier in symbol table */
    /* Return symbol table index */
    return lookup_or_insert(text);
}

The first section defines character classes letter and digit, and composite patterns id and num. The second section contains rules: whitespace is consumed silently (the action is empty), newlines increment a line counter (used for error messages), identifiers and numbers are recognized with actions that store their values and return token codes, and single-character operators return their token codes directly. The yylex() function generated by LEX is called by the parser; each call returns the next token. The variable yytext contains the matched lexeme, and yylval is used to pass attribute values to the parser.

Three key LEX behaviors to remember for exams:

  • Priority: When multiple rules match, the first rule in the list wins.
  • Maximal munch: When a rule can match different lengths of input, the longest match is preferred.
  • Default action: If no rule matches, the matched character is echoed to the output (printed as-is).
How LEX Works Internally: From RE to DFA

Internally, the LEX compiler performs the following steps to generate the scanner:

  1. Combine all regular expressions into a single large NFA (Nondeterministic Finite Automaton) using ε-transitions. Each pattern gets its own accepting state, and the action associated with that pattern is attached to the accepting state.
  2. Convert the NFA to a DFA (Deterministic Finite Automaton) using the subset construction algorithm. The DFA has no ε-transitions and at most one transition per state per character, making it efficient for execution.
  3. Minimize the DFA by merging equivalent states, producing the smallest possible DFA that recognizes the same language.
  4. Generate C code that implements the minimized DFA as a table-driven or switch-driven scanner. The generated code uses yytext to record the matched string and calls the appropriate action code when an accepting state is reached.

This pipeline — from regular expressions to NFA to DFA to minimized DFA to C code — is the theoretical foundation of scanner generation, and understanding it is valuable for both exams and practical tool use.

Viva Voce Questions with Model Answers

Q: Why is the symbol table called a "shared" data structure?

A: The symbol table is shared because every phase of the compiler both reads from and writes to it. The lexical analyzer inserts identifiers, the semantic analyzer records types, and the code generator records addresses. It serves as the central repository of program information across all phases.

Q: Can a compiler exist without a code optimizer?

A: Yes. Code optimization is an optional (though highly desirable) phase. A compiler without optimization would produce correct but potentially slower or larger target code. Many simple or educational compilers skip optimization entirely. The optimization phase is what distinguishes a good compiler from a basic one.

Q: What happens if two regular expressions in LEX can match the same input?

A: LEX resolves ambiguity using two rules: (1) the rule listed first in the specification takes priority (first-match wins), and (2) among different-length matches of the same rule, the longest match wins (maximal munch).

Q: Why do we need sentinels in the two-buffer scheme?

A: Without sentinels, the scanner must check for end-of-buffer at every character, adding one comparison per character. Sentinels eliminate this check for all characters except the last one in each half, since the sentinel character will trigger the buffer-switching logic naturally. This roughly doubles the scanning speed for the end-of-buffer check case.

Q: What is the difference between static and dynamic linking?

A: In static linking, the linker copies the library code into the executable at link time. The executable is self-contained but larger. In dynamic linking, references to shared libraries are resolved at load time or run time by the OS loader. The executable is smaller and multiple programs can share one copy of the library in memory.

Back end = Optimize + Code Gen (machine-dependent). Cousins: Preprocessor → Compiler → Assembler → Linker → Loader. Single-pass = one read, fast but no forward refs. Multi-pass = multiple reads, supports optimization & forward refs. Bootstrapping = self-compilation using a small initial compiler. Lexical Analyzer: Token = (name, attribute). Lexeme = matched string. Pattern = rule. Input buffering: Two halves, lexemeBegin + forward pointers, sentinels at boundaries. Regular expressions: Union (|), Concatenation, Star (*). Precedence: * > concat > |. Transition diagrams: States + transitions. Start = single circle. Accept = double circle. LEX: Scanner generator. 3 sections: defs, rules, subroutines. RE → NFA → DFA → C code. First rule wins. Maximal munch.
