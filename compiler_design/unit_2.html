1. The Role of the Parser

When a compiler reads source code, the very first meaningful work happens inside the lexical analyser (the scanner), which converts raw characters into a stream of tokens — discrete units like keywords, identifiers, operators, and literals. But a stream of tokens, however clean, is still just a flat sequence. It carries no information about the structure of the program: which expressions belong inside which statements, which statements are nested inside which blocks, or how operators group their operands. That structural understanding is the responsibility of the syntax analyser, more commonly called the parser.

The parser sits at the second major phase of compilation. It receives the token stream from the lexical analyser and determines whether that stream constitutes a valid sentence of the source language according to the language's context-free grammar (CFG). If the tokens form a syntactically correct program, the parser constructs a parse tree (or its more compact cousin, the abstract syntax tree) that represents the hierarchical grammatical structure. This tree then becomes the input to subsequent phases — semantic analysis, intermediate code generation, and so on. If the tokens do not conform to any valid production of the grammar, the parser reports a syntax error, ideally with a meaningful diagnostic message that helps the programmer locate and fix the problem.

Why does this matter so much? Because the parse tree is the compiler's primary representation of meaning. Without it, the compiler has no way to know whether a + b * c should be parsed as (a + b) * c or a + (b * c). The grammar's structure — encoded in the parse tree — resolves such ambiguities and establishes the correct evaluation order. Every subsequent compiler phase depends on this tree being correctly constructed.

Figure 1.1 — The parser's position in the compilation pipeline. The syntax analyser receives tokens and produces a parse tree.

1.1 What the Parser Must Accomplish

The parser has three fundamental responsibilities. First, recognition: it must determine whether the input token sequence is a valid sentence of the grammar. This is essentially a membership test — "Does this sequence belong to the language generated by the CFG?" Second, structural analysis: if the sentence is valid, the parser must construct the parse tree (or at least the information needed to build one), showing exactly which productions were applied at each step and how the nonterminals were expanded. Third, error detection and recovery: if the input is not a valid sentence, the parser must detect this fact, report a meaningful error, and ideally recover gracefully so that additional errors in the same compilation can be found.

The theoretical foundation for parsing comes from the theory of formal languages. Context-free grammars, which we shall study in detail in the next section, provide a natural and powerful notation for describing the syntax of programming languages. The parser essentially implements an algorithm that decides CFG membership and, in doing so, reconstructs the derivation of the input string from the start symbol of the grammar.

1.2 Two Families of Parsers

All practical parsers fall into two broad families, distinguished by the direction in which they traverse the parse tree.

Top-down parsers begin at the root of the parse tree (the start symbol) and work downward toward the leaves (the terminal symbols in the input). At each step, the parser has a current nonterminal that it needs to expand, and it chooses a production for that nonterminal. The choice is guided by looking at the next few input tokens. Predictive parsers like LL(1) look ahead exactly one token to decide which production to apply. Recursive descent parsers implement each nonterminal as a separate function that attempts to match the corresponding portion of the input.

Bottom-up parsers begin at the leaves (the input tokens) and work upward toward the root. At each step, the parser identifies a substring of the input that matches the right-hand side of some production and reduces it to the corresponding nonterminal. This is the reverse of applying a production. LR parsers (LR(0), SLR, CLR(1), LALR) are the most powerful practical bottom-up parsers and are widely used in parser generators like Yacc and Bison.

Think of parsing like diagramming a sentence in English class. The lexical analyser has already identified the nouns, verbs, and adjectives (tokens). The parser now groups them into phrases and clauses, building a tree that shows "the cat (subject) sat (verb) on (preposition) the mat (object)" — establishing structure from a flat sequence of words.

2. Context-Free Grammars

A context-free grammar (CFG) is a formalism for describing the syntax of a programming language in a way that is both mathematically precise and practically useful for compiler construction. The concept was introduced by Noam Chomsky in 1956 as part of his famous hierarchy of formal grammars, and it quickly became the standard tool for programming language specification because most programming language constructs can be naturally described by context-free rules, while the parsing algorithms for CFGs are efficient enough for practical use.

Formal Definition

A context-free grammar G is a quadruple (N, T, P, S) where:

  • N is a finite set of nonterminal symbols (also called variables or syntactic categories). These represent abstract syntactic constructs like "expression," "statement," or "program."
  • T is a finite set of terminal symbols (the tokens of the language). These are the actual symbols that appear in the input — keywords, identifiers, operators, literals. N ∩ T = ∅.
  • P is a finite set of productions (or rules). Each production has the form A → α, where A ∈ N and α ∈ (N ∪ T)*. The left-hand side is always a single nonterminal — this is what makes the grammar "context-free."
  • S ∈ N is the start symbol. The language generated by the grammar consists of all terminal strings derivable from S.

The term "context-free" deserves explanation because it reveals a fundamental property of the formalism. In a context-free grammar, a nonterminal A can be rewritten regardless of what symbols surround it in the current sentential form. The production A → α applies whether A appears in the middle of a long string or stands alone. This is in contrast to context-sensitive grammars, where the replacement of A can depend on its context. For programming languages, context-freeness is a very useful property: it means the syntax of an "expression" is the same whether that expression appears inside an assignment statement, a function call, or a conditional test.

2.1 Components Illustrated

Consider the classic arithmetic expression grammar:

E → E + T | T
T → T * F | F
F → ( E ) | id

Here, N = {E, T, F}, T = {+, *, (, ), id}, and S = E. The vertical bar | is shorthand for multiple productions with the same left-hand side: E → E + T and E → T are two separate productions. The nonterminal E represents "expressions," T represents "terms," and F represents "factors." This hierarchical decomposition encodes the standard precedence rules of arithmetic: multiplication (handled in T) binds more tightly than addition (handled in E), and parenthesized expressions and individual identifiers are the atomic units (handled in F).

This particular grammar is one of the most important examples in compiler design. You will encounter it repeatedly throughout this unit. It demonstrates how a CFG naturally captures operator precedence through its layered structure — each level of the grammar hierarchy corresponds to a precedence level in the language.

2.2 Derivations and Parse Trees

A derivation is a sequence of sentential forms obtained by repeatedly applying productions, starting from the start symbol. If we write α ⇒ β to mean "β is obtained from α by applying one production," then a derivation from S to a terminal string w is written S ⇒* w. The symbol ⇒* means "derives in zero or more steps."

There are two important types of derivation. In a leftmost derivation, at each step we always replace the leftmost nonterminal. In a rightmost derivation, we always replace the rightmost nonterminal. The choice of derivation order does not change the language generated, but it does affect the shape of the parse tree and, crucially, which parsing strategy is appropriate.

A parse tree (also called a derivation tree or syntax tree) is a graphical representation of a derivation. The root is labelled with the start symbol. Each interior node is labelled with a nonterminal A, and its children are labelled with the symbols on the right-hand side of some production A → α. The leaves of the tree, read from left to right, give the terminal string that was derived.

Figure 2.1 — Parse tree for id + id * id using the expression grammar E → E + T | T, T → T * F | F, F → (E) | id. Notice how the tree structure naturally enforces that * binds more tightly than +.

In the parse tree above, notice something important: the * operator appears deeper in the tree than the + operator. Because multiplication (T) is at a lower level than addition (E) in the grammar hierarchy, the tree structure forces id * id to be grouped as a single term before the addition is performed. This is how a CFG encodes operator precedence — not through explicit priority declarations, but through the layered structure of nonterminals.

The leftmost derivation of id + id * id is:

E ⇒ E + T
  ⇒ T + T
  ⇒ F + T
  ⇒ id + T
  ⇒ id + T * F
  ⇒ id + F * F
  ⇒ id + id * F
  ⇒ id + id * id

Each step replaces the leftmost nonterminal. The rightmost derivation would replace the rightmost nonterminal at each step, producing a different sequence of sentential forms but arriving at the same parse tree.

Exam Tip

When drawing parse trees in exams, always label every node clearly. Use rounded boxes or circles for nonterminals and square/rectangular boxes for terminals. Make sure the tree reads left-to-right at the leaf level to produce exactly the input string. For a 10-mark parse tree question, the tree alone might carry 5-6 marks, with the remaining marks for derivation steps and explanation.

3. Problematic Grammars & Their Solutions

Not all grammars are equally amenable to parsing. Three common problems can make a grammar unsuitable for efficient parsing algorithms: ambiguity, left recursion, and non-determinism (also called lack of left factoring). Each of these problems can be identified systematically and, in most cases, resolved by transforming the grammar into an equivalent one that is better behaved. These transformations are among the most frequently tested topics in university examinations, and you should be able to perform them mechanically and explain why they work.

3a. Ambiguous Grammars

A grammar is ambiguous if there exists at least one string in the language that has two or more distinct parse trees (equivalently, two or more distinct leftmost derivations or two or more distinct rightmost derivations). Ambiguity is problematic because the compiler cannot determine which parse tree is "correct" without additional information — the grammar itself does not resolve the structural meaning of the string.

Definition

A grammar G is ambiguous if and only if there exists a string w ∈ L(G) such that w has more than one parse tree (or equivalently, more than one leftmost derivation) in G.

Classic Example: The expression grammar E → E + E | E * E | id is ambiguous. Consider the string id + id * id. This string has two parse trees:

Parse Tree 1 (interpreting as id + (id * id)): The * is applied first, grouping the last two ids, then + is applied. This corresponds to standard mathematical precedence.

Parse Tree 2 (interpreting as (id + id) * id): The + is applied first, grouping the first two ids, then * is applied. This gives a completely different result.

Since the same input yields two different parse trees, the grammar is ambiguous. This is precisely why we use the unambiguous grammar E → E + T | T, T → T * F | F, F → (E) | id — its layered structure encodes precedence explicitly.

The Dangling-Else Ambiguity: Another classic example arises in conditional statements. The grammar:

S → if E then S | if E then S else S | other

is ambiguous because a statement like if E₁ then if E₂ then S₁ else S₂ can be parsed with the else belonging to either the outer or inner if. We will discuss how to resolve this using precedence rules in Section 8.

Common Student Confusion: "Ambiguous grammar" does not mean the grammar is bad or incorrect. It means the grammar admits multiple structural interpretations for some strings. For practical compiler use, we need unambiguous grammars because the parser must produce exactly one parse tree. However, ambiguous grammars are sometimes more concise and can still be used in parser generators that allow precedence declarations to resolve ambiguities (like Yacc).

PYQ Alert

Repeated "Check whether the grammar E → E + T | T, T → T * F | F, F → (E) | id is ambiguous." Answer: This grammar is unambiguous because every string has exactly one parse tree — the precedence layers (E for addition, T for multiplication, F for atoms) and the parenthesised sub-expression rule (F → (E)) eliminate all ambiguity. Explain by showing that the original ambiguous grammar E → E + E | E * E | id produces two trees for id + id * id, while this grammar produces exactly one.

3b. Left Recursion

A grammar is left-recursive if there exists a nonterminal A such that A ⇒+ Aα for some (possibly empty) sequence of symbols α. This can happen in two ways. Immediate (direct) left recursion occurs when a production has the form A → Aα — the nonterminal A appears as the very first symbol on the right-hand side. Indirect left recursion occurs when A derives through a chain of other nonterminals back to itself, as in A ⇒ Bβ ⇒ Aαβ.

Left recursion is a serious problem for top-down parsers. A top-down parser attempts to expand a nonterminal A by choosing a production and then trying to match the production's right-hand symbols against the input. If the chosen production is A → Aα, the parser will immediately need to expand A again — leading to the same production choice, and so on indefinitely. The parser gets stuck in an infinite loop without consuming any input. Bottom-up parsers are not affected by left recursion because they work in the opposite direction.

Algorithm: Removing Immediate Left Recursion

Suppose A has productions: A → Aα₁ | Aα₂ | ... | Aαₘ | β₁ | β₂ | ... | βₙ where no βᵢ begins with A. Replace these with:

A  → β₁A' | β₂A' | ... | βₙA'
A' → α₁A' | α₂A' | ... | αₘA' | ε

where A' is a new nonterminal not previously in the grammar. The ε (empty string) production allows the recursion to terminate.

Imagine you're trying to describe "a sequence of one or more apples." You might say "an apple is: an apple followed by another apple, or just an apple." That's left-recursive and circular. The fix: say "an apple sequence is: one apple optionally followed by more apples," where "more apples" can itself be empty. This is exactly what the algorithm does — it separates the "base case" (the β's) from the "recursive case" (the α's) and introduces a new nonterminal for the repetition.
Worked Numerical: Remove Left Recursion from S → Sda | ca | b

This is one of the most frequently appearing PYQ problems. Let us solve it step by step.

Step 1 — Identify the Left-Recursive Productions

The production S → Sda is immediately left-recursive because S appears as the first symbol on the right-hand side. The other productions S → ca and S → b do not start with S, so they are the "base cases" (the β's).

Here: α = da (the part after the recursive S), and the β's are ca and b.

Step 2 — Apply the Algorithm

We create a new nonterminal S' and rewrite:

S  → caS' | bS'
S' → daS' | ε
Step 3 — Verify

Let's verify that the new grammar generates the same language. Original: S can derive strings like ca, b, ca da, b da, ca da da, etc. (each time S → Sda adds a "da" suffix).

New grammar: S → caS' and S' → daS' | ε. So S' generates (da)* — zero or more "da"s. S generates ca(da)* or b(da)*. This matches the original language exactly.

The derivation of ca da da:

S ⇒ caS'           (using S → caS')
  ⇒ cadaS'         (using S' → daS')
  ⇒ cadadaS'       (using S' → daS')
  ⇒ cadada         (using S' → ε)
Worked Numerical: Remove Left Recursion from S → Sab | Scd | a | b | c
Step 1 — Identify Left-Recursive Productions

S → Sab and S → Scd are left-recursive (S appears first on RHS). The base cases (β's) are a, b, and c.

Here: α₁ = ab, α₂ = cd.

Step 2 — Apply the Algorithm
S  → aS' | bS' | cS'
S' → abS' | cdS' | ε
Step 3 — Verify

Original generates: strings starting with a, b, or c, followed by zero or more repetitions of "ab" or "cd" in any combination. New grammar: S' generates (ab | cd)*, and S prepends a, b, or c. Same language. Correct.

Worked Numerical: Remove Left Recursion from A → Aa | Acd | d | a
Step 1 — Identify

Left-recursive: A → Aa and A → Acd. Base cases: A → d and A → a. So α₁ = a, α₂ = cd, β₁ = d, β₂ = a.

Step 2 — Rewrite
A  → dA' | aA'
A' → aA' | cdA' | ε
Step 3 — Verify

Original: A generates d or a, followed by any sequence of a's and cd's. New grammar: A' generates (a | cd)*, and A prepends d or a. Correct.

Memory Trick

Think of the algorithm as "peeling off the recursion." The left-recursive productions (A → Aα) become the recursive part of the new nonterminal (A' → αA' | ε). The non-left-recursive productions (A → β) become the entry point (A → βA'). The new A' acts like a "while loop" that optionally repeats the α part zero or more times.

3c. Left Factoring (Non-Determinism)

A grammar has a common prefix problem (also called non-determinism) when two or more productions for the same nonterminal share a common prefix on their right-hand sides. For example, if we have A → αβ₁ | αβ₂, then a top-down parser looking at A cannot decide which production to use without looking beyond the prefix α. For LL(1) parsing, we are only allowed to look one token ahead, so this common prefix creates a conflict.

Left factoring is the transformation that resolves this problem. It "factors out" the common prefix into a single production and introduces a new nonterminal for the remaining suffixes.

Algorithm: Left Factoring

Suppose A has productions: A → αβ₁ | αβ₂ | ... | αβₙ | γ₁ | γ₂ | ... | γₘ where α is the longest common prefix and none of the γ's start with α. Replace with:

A  → αA' | γ₁ | γ₂ | ... | γₘ
A' → β₁ | β₂ | ... | βₙ
Worked Example: Left Factoring

Given: S → aB | aC | Sd | Se, B → bBc | f, C → g

Step 1 — First Remove Left Recursion (if present)

S → Sd | Se are left-recursive. Removing: S → aBS' | aCS', S' → dS' | eS' | ε. (We handle the non-left-recursive part aB and aC as β's, and Sd, Se as α's.)

Wait — S → aB | aC | Sd | Se. The left-recursive ones are S → Sd and S → Se. So α₁ = d, α₂ = e. The non-left-recursive ones are S → aB and S → aC.

S  → aBS' | aCS'
S' → dS' | eS' | ε
Step 2 — Now Left Factor

S → aBS' | aCS' share common prefix a. Factor out:

S  → aS'' | ...   (but we also have the original S' from left recursion removal)
S'' → BS' | CS'

Full grammar after both transformations:

S   → aS''
S'' → BS' | CS'
S'  → dS' | eS' | ε
B   → bBc | f
C   → g
Exam Tip — Order of Transformations

When a grammar has both left recursion and common prefixes, the standard approach is: (1) remove left recursion first, then (2) apply left factoring. The reason is that left recursion removal can itself introduce common prefixes (as seen above), so factoring should be done last to clean up any remaining issues.

4. Top-Down Parsing

Top-down parsing starts from the start symbol and attempts to derive the input string by successively expanding nonterminals. The parser maintains a prediction of what the remaining input should look like and tries to match it token by token. There are two major approaches: recursive descent parsing, which uses recursive function calls, and predictive parsing (LL(1)), which uses a parsing table and a stack.

4a. Recursive Descent Parsing

In recursive descent parsing, each nonterminal in the grammar is implemented as a separate function (or procedure). When a function for nonterminal A is called, it examines the next input token and decides which production of A to apply. It then tries to match the symbols on the right-hand side of that production: for each terminal, it checks that the input matches and advances; for each nonterminal, it makes a recursive call to the corresponding function.

Recursive descent parsers are intuitive, easy to write by hand, and easy to debug. Many real-world compilers and interpreters use them. However, they have limitations: they cannot handle left-recursive grammars (the recursive function would call itself infinitely without consuming input), and they may require backtracking when multiple productions share a common prefix and the parser cannot decide which one to use based on a single lookahead token.

A non-recursive descent parser (also called a table-driven parser or predictive parser) avoids recursive function calls by using an explicit stack and a parsing table. The LL(1) parser is the most important example. It uses FIRST and FOLLOW sets to build a table that tells the parser exactly which production to apply at each step, eliminating the need for backtracking entirely.

4b. FIRST and FOLLOW Sets

The concepts of FIRST and FOLLOW are the mathematical backbone of predictive parsing. They allow us to convert a grammar into a deterministic parsing algorithm by computing, for each nonterminal, which terminal symbols can appear at the beginning of strings derived from it, and which terminals can immediately follow it in valid derivations. Without these sets, building an LL(1) parsing table would be impossible.

FIRST Set

For any string α ∈ (N ∪ T)*, FIRST(α) is the set of all terminals that can appear as the first symbol of any string derived from α. Formally:

  • If α is a terminal a, then FIRST(α) = {a}.
  • If α is a nonterminal A with production A → ε, then ε ∈ FIRST(A).
  • If A → X₁X₂...Xₙ is a production, then FIRST(A) includes every terminal in FIRST(X₁) (excluding ε). If ε ∈ FIRST(X₁), also include FIRST(X₂) (excluding ε), and so on. If ε ∈ FIRST(X₁) through FIRST(Xₙ), then ε ∈ FIRST(A).
FOLLOW Set

For any nonterminal A, FOLLOW(A) is the set of all terminals that can appear immediately after A in some sentential form. Formally:

  • If A is the start symbol, then $ ∈ FOLLOW(A) (where $ is the end-of-input marker).
  • If there is a production B → αAβ, then every terminal in FIRST(β) (excluding ε) is in FOLLOW(A).
  • If there is a production B → αAβ and ε ∈ FIRST(β), then FOLLOW(B) ⊆ FOLLOW(A).
  • If there is a production B → αA, then FOLLOW(B) ⊆ FOLLOW(A).
Worked Numerical: Compute FIRST and FOLLOW Sets

Given Grammar (after removing left recursion):

E  → TE'
E' → +TE' | ε
T  → FT'
T' → *FT' | ε
F  → (E) | id
Step 1 — Compute FIRST Sets (bottom-up, starting from terminals)

FIRST(F): F → (E) starts with terminal (, and F → id starts with terminal id. So FIRST(F) = {(, id}.

FIRST(T): T → FT', so we look at FIRST(F). Since ε ∉ FIRST(F), we stop. FIRST(T) = {(, id}.

FIRST(T'): T' → *FT' starts with terminal *. T' → ε gives ε. So FIRST(T') = {*, ε}.

FIRST(E): E → TE', so we look at FIRST(T). Since ε ∉ FIRST(T), we stop. FIRST(E) = {(, id}.

FIRST(E'): E' → +TE' starts with terminal +. E' → ε gives ε. So FIRST(E') = {+, ε}.

Step 2 — Compute FOLLOW Sets (top-down, starting from start symbol)

FOLLOW(E): E is the start symbol, so $ ∈ FOLLOW(E). Also, F → (E), so ) ∈ FOLLOW(E). FOLLOW(E) = {$, )}.

FOLLOW(E'): E → TE', so FOLLOW(E') ⊇ FOLLOW(E) = {$, )}. (E' is at the end of E → TE'.) FOLLOW(E') = {$, )}.

FOLLOW(T): E → TE', so FIRST(E') \ {ε} ⊆ FOLLOW(T). That gives {+}. Also, since ε ∈ FIRST(E'), FOLLOW(E) ⊆ FOLLOW(T). So FOLLOW(T) ⊇ {+, $, )}. Also, E' → +TE', same reasoning: FOLLOW(T) ⊇ FOLLOW(E') = {$, )} and {+}. All together: FOLLOW(T) = {+, $, )}.

FOLLOW(T'): T → FT', so FOLLOW(T') ⊇ FOLLOW(T) = {+, $, )}. (T' is at the end of T → FT'.) FOLLOW(T') = {+, $, )}.

FOLLOW(F): T → FT', so FIRST(T') \ {ε} ⊆ FOLLOW(F). That gives {*}. Also, since ε ∈ FIRST(T'), FOLLOW(T) ⊆ FOLLOW(F). So FOLLOW(F) ⊇ {*, +, $, )}. Also, T' → *FT', same reasoning: FOLLOW(F) ⊇ FOLLOW(T') = {+, $, )} and {*}. All together: FOLLOW(F) = {*, +, $, )}.

Exam Presentation Tip

In exams, present FIRST and FOLLOW sets in a clean table format. Always show your work for each nonterminal. Common mistakes: (1) forgetting to include $ in FOLLOW of the start symbol, (2) not propagating FOLLOW sets through nullable nonterminals (when ε ∈ FIRST(β) in A → αBβ, FOLLOW(A) must flow into FOLLOW(B)), (3) confusing FIRST and FOLLOW — remember FIRST looks at the beginning of derivations, FOLLOW looks at what comes after.

4c. LL(1) Parsing

An LL(1) parser is a top-down, table-driven parser that reads input from Left to right, produces a Leftmost derivation, and uses 1 token of lookahead. The "L" in LL stands for the direction the input is scanned (left-to-right), and the second "L" stands for the type of derivation (leftmost). The "1" means the parser examines at most one upcoming token to decide which production to apply.

The LL(1) parser uses three data structures: an input buffer containing the token stream (ending with $), a stack for pending grammar symbols (initially containing $S, where S is the start symbol), and a parsing table M[A, a] that maps each nonterminal-terminal pair to a production or an error.

Algorithm: Constructing the LL(1) Parsing Table

For each production A → α in the grammar:

  1. For each terminal a in FIRST(α), add A → α to M[A, a].
  2. If ε ∈ FIRST(α), then for each terminal b in FOLLOW(A), add A → α to M[A, b]. If $ ∈ FOLLOW(A), also add A → α to M[A, $].

A grammar is LL(1) if and only if every cell of the parsing table contains at most one production (no conflicts).

Worked Numerical: Construct the LL(1) Parsing Table

Grammar (after left recursion removal):

E  → TE'          (Production 1)
E' → +TE'         (Production 2)
E' → ε            (Production 3)
T  → FT'          (Production 4)
T' → *FT'         (Production 5)
T' → ε            (Production 6)
F  → (E)          (Production 7)
F  → id           (Production 8)

Using the FIRST and FOLLOW sets computed earlier:

Step 1 — Apply the Algorithm to Each Production

E → TE': FIRST(TE') = FIRST(T) = {(, id}. So add to M[E, (] and M[E, id].

E' → +TE': FIRST(+TE') = {+}. So add to M[E', +].

E' → ε: ε is the entire RHS, so add to M[E', b] for each b in FOLLOW(E') = {$, )}. So add to M[E', $] and M[E', )].

T' → *FT': FIRST(*FT') = {*}. So add to M[T', *].

T' → ε: Add to M[T', b] for each b in FOLLOW(T') = {+, $, )}. So add to M[T', +], M[T', $], M[T', )].

F → (E): FIRST((E)) = {(}. So add to M[F, (].

Worked Numerical: LL(1) Parsing Simulation for Input id + id * id

Using the parsing table above, we parse the input string id + id * id $.

The algorithm: Look at the top-of-stack symbol X and the current input token a.

Why LL(1) and LR(0) Are Incomparable

An interesting theoretical fact: the classes of LL(1) grammars and LR(0) grammars are incomparable — neither is a subset of the other. This surprises many students who expect LL(1) to be "weaker" than LR(0) since LL(1) ⊂ LR(1).

LL(1) but not LR(0): S → Aa | b, A → c | ε. This is LL(1) (no conflicts in the parsing table) but not LR(0) because in the initial LR(0) item set, we have both A → .c (shift on c) and A → . (reduce on all inputs), creating a shift-reduce conflict on input c.

LR(0) but not LL(1): S → aA | aB, A → b, B → c. This is LR(0) (no conflicts in any LR(0) item set) but not LL(1) because FIRST(aA) = {a} and FIRST(aB) = {a} overlap in row S.

5. Bottom-Up Parsing: Foundations

Bottom-up parsers construct a parse tree from the leaves upward to the root. Rather than expanding nonterminals as a top-down parser does, a bottom-up parser performs reductions: it identifies a substring of the input that matches the right-hand side of some production and replaces it with the corresponding nonterminal. The sequence of reductions, when read in reverse, gives a rightmost derivation of the input.

5.1 Shift-Reduce Parsing

The most common framework for bottom-up parsing is shift-reduce parsing. The parser maintains a stack and an input buffer. At each step, it performs one of two actions:

  • Shift: Move the next input token onto the top of the stack.
  • Reduce: If the top symbols on the stack match the right-hand side of some production A → β, replace β on the stack with A. (This is the reverse of expanding A → β.)

The parser also needs two other operations: accept (when the start symbol is on the stack and the input is exhausted) and error (when neither shift nor reduce is applicable).

5.2 Handles

The critical concept in bottom-up parsing is the handle. A handle of a sentential form is a substring β that (1) matches the right-hand side of some production A → β, and (2) replacing β by A is a step in the reverse of a rightmost derivation. Intuitively, the handle is the "right thing to reduce" at each step. Finding the correct handle is the essential challenge of bottom-up parsing — shift too early and you miss the handle, shift too late and you reduce the wrong substring.

Imagine you are disassembling a model airplane back into its component pieces. The "handle" is the one sub-assembly that, when you remove it and replace it with its name (like "wing assembly"), moves you one step closer to having just the raw materials. If you try to remove the wrong sub-assembly first — say, trying to remove half the fuselage along with the wing — you won't match any known sub-assembly and you'll be stuck.

5.3 Viable Prefixes

A viable prefix is a prefix of a right-sentential form that does not extend past the right end of the handle. The set of viable prefixes is a regular language, which means it can be recognized by a finite automaton. This is the theoretical foundation for LR parsing: the LR parser's states correspond to states of a DFA that recognizes viable prefixes, and the parsing table encodes the DFA's transitions.

6. Operator-Precedence Parsing

Operator-precedence parsing is a special form of bottom-up parsing that works well for expression grammars where operators have clearly defined precedence and associativity. Rather than using the full machinery of LR parsing, it defines three precedence relations between pairs of terminal symbols and uses these relations to decide when to shift and when to reduce.

The three relations between adjacent terminal symbols a and b are:

  • a ⋖ b (a "yields to" b): b has higher precedence; we should shift b onto the stack.
  • a ≐ b (a "equals" b): a and b have the same precedence and appear in the same production; we should continue shifting.
  • a ⋗ b (a "takes precedence over" b): a has higher precedence; we should reduce the handle on the stack.
Algorithm: Constructing Operator Precedence Relations (Lead & Last Method)

Step 1: For each nonterminal A, compute Lead(A) = set of all terminals that can appear as the leftmost terminal in a sentential form derived from A. Compute Last(A) = set of all terminals that can appear as the rightmost terminal.

Step 2: For each production, examine pairs of adjacent symbols:

  • If the production contains ...aN... (terminal followed by nonterminal): a ⋖ every terminal in Lead(N).
  • If the production contains ...Na... (nonterminal followed by terminal): every terminal in Last(N) ⋗ a.
  • If the production contains ...ab... (two adjacent terminals): a ≐ b.

Step 3: Add boundary relations: $ ⋖ every terminal in Lead(S), and every terminal in Last(S) ⋗ $.

Step 4: For operators at the same precedence level (left-associative): a ⋗ a. For right-associative: a ⋖ a. For operators at different levels, use the given precedence order.

7. LR Parsers

LR parsing is the most powerful and general bottom-up parsing method used in practice. The name "LR" stands for Left-to-right scanning of input with Rightmost derivation in reverse. An LR parser reads input from left to right and constructs a rightmost derivation in reverse order — exactly what a bottom-up parser does. The elegance of LR parsing lies in its use of a deterministic finite automaton (DFA) to recognize viable prefixes, which enables it to make shift/reduce decisions with no backtracking.

There are four canonical variants of LR parsers, listed here from weakest to strongest:

  1. LR(0) — uses no lookahead. Simplest but least powerful.
  2. SLR (Simple LR) — uses FOLLOW sets as lookahead. More powerful than LR(0) but still limited.
  3. CLR(1) (Canonical LR(1)) — uses exact 1-token lookahead carried in each item. Most powerful but tables can be very large.
  4. LALR(1) (Look-Ahead LR) — merges CLR(1) states with the same LR(0) core. Same power as SLR for most practical grammars, with smaller tables than CLR(1).

All four share the same basic framework: construct a set of item sets (each representing a state of the parser), build a DFA from these items, and then construct a parsing table from the DFA. The differences lie in how items are augmented with lookahead information and how conflicts are resolved.

Figure 7.1 — The LR parser family. Each variant adds sophistication to handle more grammars.

7a. LR(0) Parsers

An LR(0) item is a production with a dot (·) placed somewhere on the right-hand side. The dot represents how far the parser has progressed in matching that production. For example, the production E → E + T generates four items:

  • E → · E + T (haven't seen anything yet)
  • E → E · + T (have seen E)
  • E → E + · T (have seen E +)
  • E → E + T · (have seen the entire RHS — ready to reduce)

An item with the dot at the very end (like E → E + T ·) is called a complete item or reduce item. It indicates that the parser has found a handle and should reduce. An item with the dot before a nonterminal (like E → · E + T) requires closure: we must also add all productions for that nonterminal with the dot at the beginning, because those are also possibilities the parser must track.

Closure and Goto Functions

Closure(I): If item [A → α · Bβ] is in set I, then for every production B → γ, add [B → · γ] to I (if not already present). Repeat until no more items can be added.

Goto(I, X): The set of items obtained by moving the dot past symbol X in all items of I where X immediately follows the dot, then computing the closure of the result.

7c. CLR(1) — Canonical LR(1) Parsing

CLR(1) parsing is the most powerful variant. It carries exact lookahead information in each item, rather than relying on the approximate FOLLOW sets that SLR uses. 7d. LALR(1) Parsing

LALR(1) parsing is a practical compromise between CLR(1) and SLR. It takes the CLR(1) item sets and merges any two states that have the same LR(0) core (the same set of items ignoring lookaheads). The merged state's lookaheads are the union of the two original states' lookaheads. This reduces the number of states (often dramatically) while preserving most of CLR(1)'s power.

The key property of LALR: it never introduces new shift/reduce conflicts. It may introduce new reduce/reduce conflicts if two merged reduce items have overlapping lookaheads, but for most practical grammars this does not happen.

LALR Check: S → ABC, A → aA | ε, B → bB | ε, C → cC | d

Step 1: Build CLR(1) items. (Abbreviated for space — the key observation is about state merging.)

Step 2: Identify states with the same LR(0) core. States that have items like [A → ·, ...] with different lookaheads will be candidates for merging.

Step 3: Merge and check for conflicts. After merging, if no reduce-reduce conflicts arise (i.e., no two reduce items in the same merged state have the same lookahead), the grammar is LALR(1).

For this particular grammar, the ε-productions create nullable nonterminals A, B, and C. In the CLR(1) construction, reduce items for A → ε, B → ε, and C → ε will carry specific lookaheads. When states are merged, these lookaheads are combined. If the combined lookaheads don't overlap with other reduce items in the same state, the grammar is LALR. In this case, the grammar is LALR(1) because the merged states do not create reduce-reduce conflicts.

8. Using Ambiguous Grammars

While ambiguous grammars are problematic for pure parser generators that require deterministic tables, they are actually used extensively in practice through tools like Yacc and Bison. These tools allow you to write ambiguous grammars and resolve the ambiguities using precedence and associativity declarations. This is often more convenient and readable than writing an equivalent unambiguous grammar.

8.1 The Dangling-Else Problem

The most famous ambiguity in programming language grammars is the dangling-else problem. Consider:

S → if E then S | if E then S else S | other

The statement if E₁ then if E₂ then S₁ else S₂ is ambiguous: does the else belong to the outer if or the inner if?

Standard resolution: Associate each else with the closest unmatched if (innermost matching). This can be implemented by rewriting the grammar as:

S → M | U
M → if E then M else M | other    (matched if)
U → if E then S | if E then M else U  (unmatched if)

In practice, most parser generators resolve this by preferring shift over reduce when a shift-reduce conflict occurs. Since the parser shifts the else (associating it with the innermost if), the standard convention is automatically applied.

8.2 Precedence and Associativity in Parser Generators

In Yacc/Bison, you can declare operator precedence and associativity using directives:

%left '+' '-'
%left '*' '/'
%right '^'
%nonassoc UMINUS

These declarations resolve the shift-reduce conflicts in expression grammars. Operators declared on the same line have equal precedence; operators declared later have higher precedence. %left means left-associative (prefer reduce), %right means right-associative (prefer shift), and %nonassoc means the operator cannot be chained (e.g., comparison operators like <).

9. Parser Generators & Error Handling

9.1 Parser Generators

A parser generator is a tool that automatically constructs a parser from a grammar specification. The most widely known parser generator is Yacc (Yet Another Compiler Compiler), developed by Stephen Johnson at Bell Labs in 1975, and its modern descendant Bison. These tools take a CFG augmented with semantic actions (pieces of C/C++ code) and produce a complete bottom-up parser — typically an LALR(1) parser — as output.

The workflow is straightforward: the programmer writes a .y file containing grammar rules, precedence declarations, and semantic actions. The parser generator reads this file, constructs the LALR(1) parsing table, and outputs a C/C++ source file containing the table-driven parser. This file is then compiled and linked with the lexical analyser (typically produced by Lex/Flex) to create a complete front end.

For top-down parsing, tools like ANTLR (ANother Tool for Language Recognition) generate LL(*) parsers with adaptive look-ahead. JavaCC is another popular tool for generating LL(1) parsers for Java.

9.2 Error Handling in Parsers

Error handling is a critical aspect of parser design. When the parser encounters a token that does not match any expected production, it must detect the error, report it usefully, and recover enough to continue parsing the rest of the input (so that multiple errors can be found in a single compilation run).

Types of errors detected during syntax analysis:

  • Syntax errors: Missing or extra tokens, misplaced delimiters (e.g., mismatched parentheses).
  • Token errors: Malformed tokens that the lexer couldn't classify (also detected at the lexical level).
  • Type errors: In some cases, syntactic misuse of types (though most type checking is done in semantic analysis).

Error Recovery Strategies

1. Panic-Mode Recovery: The simplest strategy. When an error is detected, the parser discards tokens from the input one by one until it finds a synchronizing token (like ;, }, or end) — a token that is likely to be a valid restart point. Then parsing resumes from that point. This is safe (it never enters an infinite loop) but may skip a lot of input.

2. Phrase-Level Recovery: When an error is detected, the parser performs a local correction: it may insert a missing token, delete an unexpected token, or replace one token with another. The parsing table can specify the recovery action for each error entry. This is more precise than panic mode but requires careful design to avoid cascading errors.

3. Error Productions: The programmer adds extra productions to the grammar that describe common syntactic errors. For example, adding a production S → if E then (missing the then-clause body) allows the parser to recognize and diagnose this specific mistake.

4. Global-Correction: The parser tries to find the minimal set of insertions, deletions, or changes that would make the input valid. This is theoretically appealing but computationally expensive (O(n³) or worse) and is not used in practice.

Quick Revision: Everything You Need in 5 Minutes

CFG: G = (N, T, P, S). Productions have single nonterminal on LHS. Generates context-free languages.

Ambiguous: Two parse trees for same string. Fix: rewrite grammar or use precedence declarations.

Left Recursion: A → Aα | β. Fix: A → βA', A' → αA' | ε.

Left Factoring: A → αβ₁ | αβ₂. Fix: A → αA', A' → β₁ | β₂.

FIRST(X): Terminals that can begin strings derived from X.

FOLLOW(A): Terminals that can immediately follow A in sentential forms. $ always in FOLLOW of start symbol.

LL(1) Table: For A → α: put in M[A, a] for all a ∈ FIRST(α). If ε ∈ FIRST(α), also put in M[A, b] for all b ∈ FOLLOW(A). No cell should have two entries.

LR(0) Item: Production with dot. Complete item → reduce on ALL terminals.

SLR: Reduce A → α only on FOLLOW(A).

CLR(1): Items carry exact lookahead [A → α·β, a]. Reduce only on a.

LALR: Merge CLR(1) states with same LR(0) core. Union lookaheads.

Operator Precedence: Three relations: ⋖ (shift), ≐ (equal/shift), ⋗ (reduce). Build table from grammar and precedence rules.

Error Recovery: Panic-mode (skip to sync token), phrase-level (local fix), error productions, global correction.

Commonly Confused Points

  • FIRST vs FOLLOW: FIRST asks "what can START a string from X?" FOLLOW asks "what can come AFTER X?"
  • LR(0) reduce vs SLR reduce: LR(0) reduces on ALL terminals; SLR reduces only on FOLLOW(A).
  • CLR(1) vs LALR: CLR(1) has distinct states per lookahead; LALR merges states with same LR(0) core.
  • Left recursion removal changes the grammar: The new grammar with A' is equivalent (generates same language) but has different parse trees.
  • LL(1) requires no left recursion and no common prefixes. If either exists, transform first.
  • Operator precedence parsing is NOT LR parsing. It's a simpler technique that works only for expression-like grammars.
  • ε ∈ FIRST(A) means A can derive the empty string. This affects both FIRST and FOLLOW computations.
  • Augmented grammar: Always add S' → S as production 0 for LR parsing. The augmented start symbol has $ in its FOLLOW set.
