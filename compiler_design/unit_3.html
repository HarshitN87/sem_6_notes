Part I

Syntax-Directed Translation

1. Introduction to Syntax-Directed Translation

When a compiler parses a program, it does far more than merely check whether the source code conforms to the grammar rules of the language. The parser must also gather meaning from the syntactic structure it discovers — computing values, building intermediate representations, generating code annotations, and performing type checking. Syntax-Directed Translation (SDT) is the foundational framework that enables a compiler to attach semantic actions (computations) to the productions of a context-free grammar, so that as the parser recognizes syntactic structure, it simultaneously performs the associated computations. In essence, SDT marries the shape of the parse tree with the meaning carried by its nodes.

Consider the problem from an intuitive standpoint. Suppose you are reading the arithmetic expression 3 * 4 * 5 + 6. As a human, you naturally evaluate the multiplications first (following precedence) and then the addition, arriving at 66. But a computer parser does not have your intuition — it sees only tokens and grammar rules. SDT provides the mechanism by which we tell the parser: "whenever you recognize that T → T * F has been matched, compute the product of the values associated with the T child and the F child, and store that product as the value of this T node." By attaching such instructions to every production, the entire expression can be evaluated automatically during parsing.

The historical motivation for SDT emerges from the early days of compiler construction in the 1960s and 1970s. Before SDT was formalized, compiler writers had to write ad hoc code to walk the parse tree after construction, extracting and computing values in a separate pass. This was error-prone, difficult to maintain, and conceptually unsatisfying. The realization that semantic computations could be coupled with syntactic recognition — that the grammar itself could serve as a skeleton for translation — was a profound insight attributed to Lewis, Rosenkrantz, and Stearns (1974), and later refined by Aho, Sethi, and Ullman in the Dragon Book. SDT became the standard framework because it provides a clean separation between the what (the grammar and its attributes) and the how (the evaluation strategy).

Key Idea

Syntax-Directed Translation = Context-Free Grammar + Attributes + Semantic Rules. The grammar defines the structure; attributes carry information at each node; semantic rules define how that information is computed.

SDT has a remarkably wide range of applications in compiler design. It is used for type checking (attaching type attributes to expressions and verifying compatibility), intermediate code generation (constructing three-address code or abstract syntax trees), constant folding (evaluating constant expressions at compile time), symbol table management (tracking declarations and scopes), code optimization annotations, and even error reporting (attaching source-location attributes to nodes so that error messages can reference specific lines and columns). In the context of your university examinations, SDT questions frequently appear as 10-mark or 15-mark descriptive questions asking you to explain concepts, construct annotated parse trees, compare evaluation strategies, and trace through worked examples. The material in this section will prepare you thoroughly for all such questions.

Common Exam Question: "What do you mean by Syntax-Directed Translation? Explain with examples." — This is a classic 5-mark opener. Begin with the definition, mention the three components (grammar, attributes, rules), give a small example like a desk calculator, and conclude with applications.

2. Syntax-Directed Definitions (SDD)

A Syntax-Directed Definition (SDD) is the formal specification of a syntax-directed translation. It is a context-free grammar augmented with two additional components: a set of attributes associated with the grammar symbols (non-terminals and terminals), and a set of semantic rules (also called semantic functions) attached to each production that define how the attributes are computed. The SDD is a declarative specification — it tells us what to compute at each node, without specifying when or in what order the computation happens. The question of evaluation order is addressed separately by the concepts of S-attributed and L-attributed definitions, which we shall explore shortly.

Formal Definition: A Syntax-Directed Definition (SDD) is a tuple (G, A, R) where G is a context-free grammar, A is a set of attributes associated with the grammar symbols in each production, and R is a set of semantic rules — one rule per attribute per production — that define how each attribute's value is computed from other attributes and constants.

To understand the anatomy of an SDD, consider the following desk-calculator SDD, which is a staple of university examinations. The grammar describes arithmetic expressions with addition and multiplication, and the SDD computes the value of the entire expression:

Production          Semantic Rule
─────────────────────────────────────────
L → E               { L.val = E.val }
E → E₁ + T          { E.val = E₁.val + T.val }
E → T               { E.val = T.val }
T → T₁ * F          { T.val = T₁.val * F.val }
T → F               { T.val = F.val }
F → ( E )           { F.val = E.val }
F → digit           { F.val = digit.lexval }

Here, each grammar symbol carries an attribute called val (except digit, which carries lexval obtained from the lexer). The subscript ₁ on E₁ and T₁ is a notational convenience to distinguish between multiple instances of the same non-terminal on the right-hand side of a production. The semantic rules are written in the style of mathematical assignments: they define equations that must hold after evaluation. For instance, the rule E.val = E₁.val + T.val says that the value of the E on the left side of the production must equal the sum of the value of the E child and the T child.

An SDD is typically presented as a semantic-action table or as annotations directly on the grammar productions. When we draw the annotated parse tree for a particular input, we place the computed attribute values next to each node. This annotated parse tree is the central artifact that students must be able to construct in examinations — it demonstrates both understanding of the grammar and correct application of the semantic rules.

Structure of an SDD — Three Components in Detail

1. The Grammar (G): This is a context-free grammar consisting of terminals, non-terminals, a start symbol, and productions. The grammar defines the syntactic structure of the language — it tells us what strings are valid and how they are structured. In the desk-calculator example above, the grammar is an ordinary expression grammar with proper precedence (multiplication binds tighter than addition because T is lower in the derivation tree than E).

2. Attributes (A): Each grammar symbol X can have a set of attributes associated with it, denoted X.a, X.b, etc. Attributes carry information — they might represent computed values, types, strings, code fragments, or any other data relevant to the translation. There are two fundamental kinds of attributes: synthesized attributes (which carry information upward from children to parents in the parse tree) and inherited attributes (which carry information downward or sideways from parents and siblings to a node). The distinction between these two kinds is so important that we devote the next two sections entirely to them.

3. Semantic Rules (R): For each production A → X₁ X₂ ... Xₙ, the SDD includes semantic rules of the form A.b = f(X₁.a, X₂.a, ..., Xₙ.a), where f is a function (often a simple arithmetic expression, but potentially arbitrary). The semantic rules define a system of equations over the attributes of the parse tree. The key property is that this system of equations must have a consistent solution — there must be no circular dependencies. If the dependency graph (explained later) is acyclic, then the attributes can be evaluated in some topological order.

"The SDD is a declarative specification. It says what to compute, not when to compute it. The evaluation order is a separate concern, determined by the type of attributes and the parsing strategy."

3. Synthesized Attributes

A synthesized attribute is an attribute of a non-terminal node in the parse tree whose value is computed from the attributes of its children in the parse tree. The term "synthesized" captures the essential idea: information is built up or synthesized from the leaves toward the root. If you imagine the parse tree as a factory assembly line, synthesized attributes represent the product being assembled as parts (child attributes) flow upward and are combined at each station (parent node).

Formal Definition: An attribute B.i of a non-terminal B occurring at a parse-tree node n is synthesized if its value is determined by a semantic rule associated with the production used at node n. That is, for a production with B on the left-hand side, the rule for B.i depends only on attributes of the symbols on the right-hand side of that production (the children of n).

In the desk-calculator SDD, every attribute is synthesized. Consider the production E → E₁ + T with the semantic rule E.val = E₁.val + T.val. Here, E.val is a synthesized attribute because its value is computed from the attributes of its children: E₁.val (the value of the left child E) and T.val (the value of the right child T). Similarly, T.val = T₁.val * F.val synthesizes the product of child values, and F.val = digit.lexval synthesizes the digit's value from the terminal leaf.

Synthesized attributes have a beautiful property: they can always be evaluated in a bottom-up order. Since each attribute depends only on its children's attributes, we can evaluate the attributes at the leaves first (where the values are typically given directly from the lexer or as constants), then move upward level by level, evaluating each parent's attributes once all its children's attributes are ready. This bottom-up evaluation strategy is natural for shift-reduce parsers (such as LR parsers), which construct the parse tree from leaves to root.

Every SDD that uses only synthesized attributes is called an S-Attributed Definition (discussed in detail in Section 6). S-attributed definitions are the simplest and most commonly encountered type, and they form the foundation for understanding more complex attribute grammars.

Worked Example: Evaluating Synthesized Attributes for "3 * 4 * 5 + 6"

Let us trace through the complete evaluation of the expression 3 * 4 * 5 + 6 using the desk-calculator SDD. We construct the parse tree, then evaluate all synthesized attributes bottom-up.

Fig. 1 — Annotated parse tree for "3 * 4 * 5 + 6" showing synthesized attribute values (L.val = 66)

Evaluation trace (bottom-up): We begin at the leaves, where the lexer provides digit.lexval values: 3, 4, 5, and 6. Moving upward, the production F → digit gives us F.val = digit.lexval, so we get F.val = 3, F.val = 4, F.val = 5, and F.val = 6. The production T → F propagates values upward without change: T.val = 3 (for the leftmost T). Then T → T₁ * F computes products: T.val = 3 * 4 = 12, and then T.val = 12 * 5 = 60. The production E → T gives E.val = 60. On the right side, T → F gives T.val = 6. Finally, E → E₁ + T computes E.val = 60 + 6 = 66, and L → E gives L.val = 66. The entire expression evaluates to 66.

Exam Writing Tip: When asked to "illustrate with examples," always draw the annotated parse tree and show the evaluation order explicitly. Professors award marks for both the correct tree structure and the correct attribute values at each node.

4. Inherited Attributes

An inherited attribute is an attribute of a non-terminal node whose value is determined by the attributes of its parent and/or its siblings in the parse tree, rather than its children. While synthesized attributes carry information upward, inherited attributes carry information downward or laterally through the parse tree. This distinction is not merely a technical convenience — it reflects a fundamentally different kind of information flow that arises naturally in many translation tasks.

Formal Definition: An attribute B.i of a non-terminal B at a parse-tree node n is inherited if its value is determined by a semantic rule associated with the production at the parent of n. That is, the rule for B.i depends on attributes of the parent node and/or siblings of B in the right-hand side of the production, but not on attributes of B's own children.

The canonical example of inherited attributes arises in type declaration processing. Consider a C-like declaration int a, b, c;. The grammar for such declarations might be:

D → T L           { L.inh = T.type }
T → int           { T.type = integer }
T → float         { T.type = real }
L → L₁ , id       { L₁.inh = L.inh; addType(id.entry, L.inh) }
L → id            { addType(id.entry, L.inh) }

Here, L.inh is an inherited attribute. When the parser recognizes D → T L, it sets L.inh = T.type — the type declared by T (e.g., integer) is passed down to the list of identifiers L. As L is expanded recursively through L → L₁ , id, the inherited attribute is propagated to each successive L₁, ensuring that every identifier in the comma-separated list receives the same type. The function addType records the type of each identifier in the symbol table.

This example illustrates why inherited attributes are necessary: the type information originates at the T node (a sibling of L in the production D → T L) and must flow downward through the list of identifiers. Synthesized attributes alone cannot accomplish this, because the L nodes have no way of learning the type from their children (the children are just identifiers and commas).

Another Example: Sign and Number Processing

Consider the SDD from the university PYQ:

S → A Sign         { if Sign.sign = 1 then S.val = A.val
                     else S.val = -A.val }
Sign → +           { Sign.sign = 1 }
Sign → -           { Sign.sign = 0 }
A → A₁ d           { A.val = A₁.val * 10 + d.lexval }
A → d              { A.val = d.lexval }

Here, A.val is synthesized (computed from children), Sign.sign is synthesized (determined by the terminal), and S.val is synthesized (computed from A.val and Sign.sign). However, if we were to modify the SDD so that the sign information must be propagated into the digit-processing rules (for instance, to handle negative digits directly), we would need inherited attributes to pass the sign information downward.

5. Dependency Graphs & Attribute Evaluation

When we have an annotated parse tree with both synthesized and inherited attributes, the question arises: in what order should we evaluate the attributes? The answer lies in the dependency graph, a directed graph that captures the data-flow relationships among all attributes in the parse tree. If the dependency graph is acyclic, then a valid evaluation order exists (any topological sort of the graph), and the SDD is said to be well-defined.

Dependency Graph: For a given parse tree, the dependency graph is a directed graph whose nodes correspond to attribute instances in the tree. There is a directed edge from attribute instance b to attribute instance c if the semantic rule for c depends on the value of b. In other words, an edge b → c means "c must be evaluated after b."

Constructing the Dependency Graph for "10 + 8 * 5"

Let us construct the dependency graph for the expression 10 + 8 * 5 using the desk-calculator SDD. The parse tree structure is E → E₁ + T, where E₁ → T → F → digit(10), and T → T₁ * F, where T₁ → F → digit(8) and F → digit(5).

Fig. 2 — Dependency graph for "10 + 8 * 5" showing attribute evaluation order (arrows indicate data-flow dependencies)

The dependency graph reveals the evaluation order clearly. The leaf attributes (digit.lexval) have no incoming edges — they are the starting points. From there, evaluation proceeds upward: F.val values depend on digit.lexval; T.val values depend on F.val and (for multiplication) on other T.val and F.val values; and finally, E.val depends on E₁.val and T.val. One valid topological ordering is: digit₁ → F₁ → T₁ → E₁, digit₂ → F₂ → T₂, digit₃ → F₃ → T₃ → E₂. The final result is E₂.val = 10 + 40 = 50.

Why Dependency Graphs Matter

If the dependency graph contains a cycle, the SDD is ill-defined — there is no consistent evaluation order, and the attributes cannot be computed. In practice, well-designed SDDs for compiler tasks always produce acyclic dependency graphs. The dependency graph also tells us whether an SDD can be evaluated during a single pass of the parser (e.g., bottom-up for S-attributed, left-to-right for L-attributed).

6. S-Attributed Definitions

An SDD that uses only synthesized attributes is called an S-Attributed Definition. This is the simplest and most commonly encountered form of syntax-directed definition. In an S-attributed definition, every attribute is computed from the attributes of the node's children in the parse tree, meaning information flows exclusively upward from leaves to root.

Formal Definition: An SDD is S-Attributed if every attribute is a synthesized attribute. That is, for every production, the semantic rules compute attributes of the left-hand side non-terminal from attributes of the right-hand side symbols only.

The desk-calculator SDD presented earlier is a perfect example of an S-attributed definition: every .val attribute is computed from child attributes. The beauty of S-attributed definitions is their simplicity and their natural compatibility with bottom-up parsing. Since LR parsers (such as SLR, CLR, and LALR parsers) construct the parse tree from the leaves upward — reducing children to parents — synthesized attributes can be evaluated at the exact moment each reduction is performed. The parser maintains an attribute stack (parallel to the state stack) that stores the attribute values of symbols on the stack. When a reduction A → X₁ X₂ ... Xₙ occurs, the parser pops the top n entries from the attribute stack, applies the semantic rule to compute A's attribute, and pushes the result back.

Properties of S-Attributed Definitions

  • No inherited attributes: All information flows bottom-up.
  • Acyclic dependency graph guaranteed: Since every edge in the dependency graph goes from a child to its parent, cycles are impossible in a finite tree.
  • Single-pass evaluation: Attributes can be computed during a single bottom-up traversal of the parse tree, making them ideal for LR parsing.
  • Simple implementation: Only a value stack is needed alongside the parser stack.
  • Limitation: Cannot express translations that require top-down information flow (such as propagating type information from a declaration to its variable list).

Key Exam Distinction: S-Attributed definitions are a subset of L-attributed definitions. Every S-attributed definition is L-attributed (trivially, since there are no inherited attributes to violate the L-attributed constraint), but not every L-attributed definition is S-attributed.

7. L-Attributed Definitions

An L-Attributed Definition (where "L" stands for "left-to-right" traversal) is an SDD in which attributes may be both synthesized and inherited, subject to a crucial constraint: for each production A → X₁ X₂ ... Xₙ, the semantic rule for an attribute of Xⱼ (where 1 ≤ j ≤ n) may depend only on:

  1. Attributes of the symbols X₁, X₂, ..., Xⱼ₋₁ (the siblings to the left of Xⱼ), and
  2. Attributes of A (the parent, which provides inherited attributes to Xⱼ), and
  3. Synthesized attributes of Xⱼ itself (which may depend on Xⱼ's children).

The constraint essentially says that attributes must be evaluable in a left-to-right pass over the right-hand side of each production. You cannot use attributes of symbols to the right of Xⱼ when computing Xⱼ's attributes. This restriction ensures that L-attributed definitions can be evaluated during a single left-to-right traversal of the parse tree — making them compatible with both top-down (LL) and bottom-up (LR) parsing strategies.

Formal Definition: An SDD is L-Attributed if, for every production A → X₁ X₂ ... Xₙ and for every semantic rule associated with Xⱼ, the rule depends only on:
(a) Synthesized attributes of Xⱼ or attributes of X₁, ..., Xⱼ₋₁ (symbols to the left), and
(b) Inherited attributes of A (the parent).

Example of an L-Attributed Definition

The type-declaration SDD from Section 4 is L-attributed. In the production D → T L, the rule L.inh = T.type computes L's inherited attribute from T's synthesized attribute — and T is to the left of L in the production. In the production L → L₁ , id, the rule L₁.inh = L.inh propagates the inherited attribute from the parent L to the child L₁ (which is also to the left of the , and id). All dependencies respect the left-to-right constraint.

Properties of L-Attributed Definitions

  • More expressive than S-attributed: Can handle both bottom-up and top-down information flow.
  • Left-to-right evaluation: Attributes can be computed in a single pass from left to right over each production's right-hand side.
  • Compatible with LL parsing: Can be evaluated during predictive (top-down) parsing by computing inherited attributes before expanding a non-terminal and synthesized attributes after.
  • Also compatible with LR parsing: With some modifications (using a side stack or passing attributes through the parser state).
  • No right-to-left dependencies: Cannot use attributes of symbols to the right in computing a given attribute.

8. Construction of Syntax Trees

A syntax tree (also called an abstract syntax tree or AST) is a condensed representation of the parse tree that captures the essential structure of the source program while omitting redundant syntactic details such as parentheses, single-production chains, and punctuation. While a parse tree (also called a concrete syntax tree) faithfully reflects every grammar production used during parsing, a syntax tree strips away the scaffolding and retains only the operators, operands, and their hierarchical relationships.

For example, the expression (3 + 4) * 5 would have a parse tree with nodes for the parentheses and multiple intermediate non-terminals (E, T, F), but its syntax tree would simply be:

Constructing Syntax Trees via SDD

A syntax tree can be constructed during parsing using an SDD that creates tree nodes. Each grammar symbol is augmented with an attribute .node (a pointer to a tree node), and the semantic rules create new nodes using a function like mkNode(op, left, right) for interior nodes and mkLeaf(val) for leaf nodes. For example:

E → E₁ + T    { E.node = mkNode('+', E₁.node, T.node) }
E → T          { E.node = T.node }
T → T₁ * F    { T.node = mkNode('*', T₁.node, F.node) }
T → F          { T.node = F.node }
F → ( E )      { F.node = E.node }
F → digit      { F.node = mkLeaf(digit.lexval) }

This SDD is S-attributed (all attributes are synthesized), and it constructs the syntax tree bottom-up as the parser reduces. Each reduction creates a new node (or reuses an existing one for single-production chains like E → T), and the resulting tree is the abstract syntax tree of the expression.

9. Bottom-Up Evaluation of S-Attributed Definitions

Since S-attributed definitions use only synthesized attributes, they can be evaluated naturally during bottom-up (LR) parsing. The mechanism is elegant and straightforward: the parser maintains an attribute value stack that runs parallel to the parser's state stack. Each time a symbol is shifted onto the state stack, its attribute value (if any) is pushed onto the value stack. When a reduction A → X₁ X₂ ... Xₙ occurs, the parser:

  1. Pops the top n entries from the value stack (these are the attribute values of X₁, X₂, ..., Xₙ).
  2. Applies the semantic rule to compute A's synthesized attribute from the popped values.
  3. Pushes A's attribute value onto the value stack.

This process is identical to how a shift-reduce parser works, with the value stack providing the "memory" for attribute computation. The value stack is sometimes called the semantic stack or attribute stack.

Worked Example: Evaluating "3 * 4 + 5" During LR Parsing

Let us trace the bottom-up evaluation for the input 3 * 4 + 5 using the desk-calculator SDD. We show the parser state stack, the value stack, and the action at each step:

StepParser StackValue StackInputAction
1$3 * 4 + 5 $Shift 3
2$ digit(3)[3]* 4 + 5 $Reduce F → digit; F.val = 3
3$ F[3]* 4 + 5 $Reduce T → F; T.val = 3
4$ T[3]* 4 + 5 $Shift *
5$ T *[3]4 + 5 $Shift 4
6$ T * digit(4)[3, 4]+ 5 $Reduce F → digit; F.val = 4
7$ T * F[3, 4]+ 5 $Reduce T → T * F; T.val = 3*4 = 12
8$ T[12]+ 5 $Reduce E → T; E.val = 12
9$ E[12]+ 5 $Shift +
10$ E +[12]5 $Shift 5
11$ E + digit(5)[12, 5]$Reduce F → digit; F.val = 5
12$ E + F[12, 5]$Reduce T → F; T.val = 5
13$ E + T[12, 5]$Reduce E → E + T; E.val = 12+5 = 17
14$ E[17]$Accept

The final value on the value stack is 17, which is the correct result of 3 * 4 + 5. Notice how the value stack mirrors the parse stack: when three symbols are popped during a reduction (step 7: T → T * F), three values are popped from the value stack and combined using the semantic rule.

Memory Anchor: Think of the value stack as a "shadow" of the parser stack — every time the parser stack changes, the value stack changes in the same way. The semantic rules are applied at reduction time, just as the grammar rules are.

10. Top-Down Translation

L-attributed definitions can be evaluated during top-down (LL) parsing, specifically during predictive parsing. The approach involves two kinds of actions embedded in the parsing process:

  1. Inherited attribute computation: When a production A → X₁ X₂ ... Xₙ is chosen during parsing, the inherited attributes of each Xⱼ are computed before Xⱼ is expanded. This is possible because the L-attributed constraint ensures that Xⱼ's inherited attributes depend only on A's attributes and attributes of X₁, ..., Xⱼ₋₁, which are already available.
  2. Synthesized attribute computation: After Xⱼ has been fully expanded (i.e., its entire subtree has been parsed), its synthesized attributes become available. These can then be used to compute inherited attributes of subsequent symbols Xⱼ₊₁, Xⱼ₊₂, ..., and ultimately to compute A's synthesized attributes.

Approach 1: Embedding Actions in Productions

The most common technique for top-down translation is to embed semantic actions (pieces of code) within the productions at specific points. By carefully placing these actions, we ensure that attributes are computed at the correct time. For example, consider the type-declaration SDD rewritten with actions:

D → T L          { L.inh = T.type }
T → int          { T.type = integer }
T → float        { T.type = real }
L → id R         { addType(id.entry, L.inh); R.inh = L.inh }
R → , id R₁      { addType(id.entry, R.inh); R₁.inh = R.inh }
R → ε            { /* nothing */ }

Here, the action { L.inh = T.type } is placed immediately after T is parsed and before L is expanded, ensuring that L.inh is available when needed. The inherited attribute R.inh is similarly set before expanding R.

Approach 2: Global Variables

A simpler (though less elegant) approach uses global variables to pass information between parsing functions. Each non-terminal's parsing function computes synthesized attributes as return values and uses global variables for inherited attributes. This approach is easy to implement in a recursive-descent parser but lacks the formal rigor of the embedded-action approach.

// Pseudocode for recursive-descent with translation
int parse_T() {
    if (lookahead == INT) { match(INT); return integer; }
    else { match(FLOAT); return real; }
}

void parse_L(int inherited_type) {
    match(ID); addType(id.entry, inherited_type);
    while (lookahead == COMMA) {
        match(COMMA); match(ID);
        addType(id.entry, inherited_type);
    }
}

void parse_D() {
    int t = parse_T();
    parse_L(t);  // pass type as inherited attribute
}

Part II

Run-Time Environments

1. Introduction & Source Language Issues

The run-time environment is the infrastructure that supports the execution of a program after it has been compiled. While the front end of a compiler (lexer, parser, semantic analyzer) deals with understanding the source program, and the back end (code generator, optimizer) deals with producing target code, the run-time environment is the context in which that target code actually executes. It encompasses everything from how memory is organized and allocated, to how function calls are managed, to how variables are accessed, to how parameters are passed between procedures. Understanding the run-time environment is essential for a compiler designer because the code generator must produce code that correctly interacts with this environment.

The need for a well-designed run-time environment arises from several source language issues that the compiler must address at execution time. The most fundamental of these is the question of scope — the region of the program text within which a variable name is meaningful. Most modern programming languages use static (lexical) scoping, where the scope of a variable is determined by the structure of the source code (the block in which it is declared), rather than by the order of function calls at run time. Static scoping requires the compiler to build a compile-time scope structure, but the run-time environment must support the corresponding mechanism for variable access — typically through access links or display registers.

A second critical issue is binding — the association between a name and the entity it refers to (a variable, a memory location, a type, a value). A binding is static if it occurs before run time and does not change during execution; it is dynamic if it occurs during execution and may change. For example, the binding of a local variable to a memory location on the stack is dynamic — a new location is allocated each time the function is called. The lifetime of a variable is the period during which it is bound to a particular memory location. Understanding lifetimes is crucial for choosing the correct storage allocation strategy.

A third issue is name management. During execution, the same variable name may refer to different storage locations at different times (e.g., a local variable in a recursive function). The run-time environment must provide mechanisms to distinguish between these different incarnations of the same name. This is typically accomplished through the use of activation records (also called stack frames), which we discuss in detail later.

Key Concepts to Remember
  • Scope: Where a name is visible (compile-time concept).
  • Binding: Association between a name and an entity (can be static or dynamic).
  • Lifetime: Duration of a binding (run-time concept).
  • Environment: The current set of name-to-location bindings at a program point.
  • State: The current values stored in all memory locations.

2. Storage Organization

The memory available to a running program is typically organized into several distinct regions, each serving a specific purpose. Understanding this organization is fundamental to understanding how the three storage allocation strategies (static, stack, and heap) operate. The canonical memory layout of a running program, from low addresses to high addresses, is as follows:

Fig. 4 — Canonical memory organization of a running program

The Code (Text) segment resides at the lowest addresses and contains the compiled machine instructions. This region is typically read-only to prevent accidental modification of the program during execution. Its size is fixed at compile time (or load time) and does not change during execution.

The Static Data segment holds global variables, static local variables, and compile-time constants. Like the code segment, its size is known before execution begins. In languages like C and FORTRAN, global variables are allocated here. In Java, class-level static fields reside in this region (within the method area of the JVM).

The Heap is the region used for dynamic memory allocation — when a program requests memory at run time using constructs like malloc() in C, new in Java/C++, or garbage-collected allocation in Python. The heap typically grows upward from the static data area.

The Stack is used for managing function calls and their local variables. Each function call creates a new activation record (stack frame) on the stack, and each return destroys it. The stack typically grows downward from the high addresses. In many programs, the heap and stack grow toward each other from opposite ends of the available memory, meeting in the middle. If they collide, the program runs out of memory (stack overflow or heap exhaustion).

3. Static Allocation

In static allocation, the storage for every variable is determined at compile time and remains fixed throughout the entire execution of the program. The compiler knows the exact memory address (or offset from a fixed base) for each variable before the program runs. No allocation or deallocation occurs at run time — everything is pre-determined.

Static allocation is the simplest storage strategy, but it comes with significant limitations. It was the primary allocation method in early languages like FORTRAN (the original FORTRAN 77 standard required static allocation). The key characteristic is that the lifetime of every variable is the entire duration of the program — there is no concept of a variable coming into existence when a function is called and ceasing to exist when it returns.

How It Works

The compiler assigns each global variable and each static local variable to a fixed memory address in the static data segment. When the program starts, these addresses are initialized (either to zero or to specified initial values). During execution, the generated code simply loads from and stores to these fixed addresses. There is no need for a stack pointer, frame pointer, or any dynamic memory management.

Advantages

  • Simplicity: No run-time overhead for allocation or deallocation.
  • Fast access: Variables are accessed at known, fixed addresses — no pointer indirection needed.
  • No memory fragmentation: Memory layout is fixed at compile time.
  • Predictable behavior: No stack overflow or heap exhaustion possible.

Disadvantages

  • No recursion: Since each variable has only one storage location, a recursive function cannot have separate copies of its local variables for each invocation. This is the most severe limitation.
  • No dynamic data structures: Cannot create data structures whose size is determined at run time.
  • Inflexible: Memory is wasted if variables are not always in use.
  • No separate compilation support: All memory addresses must be resolved at compile time, making it difficult to compile modules separately.

Classic Exam Question: "Explain static allocation with advantages and disadvantages." — Always mention FORTRAN as the historical example, explain why recursion is impossible, and draw a simple memory layout showing fixed addresses.

4. Stack Allocation

Stack allocation is the most widely used storage allocation strategy for managing function calls and their local variables. It is based on the observation that function calls follow a Last-In-First-Out (LIFO) discipline: the most recently called function is the first to return. This natural ordering makes a stack the ideal data structure for managing activation records.

How It Works

Each time a function is called, a new activation record (also called a stack frame) is pushed onto the stack. This activation record contains storage for the function's local variables, parameters, return address, and bookkeeping information. When the function returns, its activation record is popped from the stack, deallocating all its local storage. The stack pointer (SP) always points to the top of the stack (the most recently allocated activation record).

The beauty of stack allocation is that it naturally handles recursion. Each recursive call creates a new, independent activation record with its own copies of the local variables. When the call returns, its activation record is destroyed, and the previous incarnation's variables are restored (they were always there, just below the top of the stack).

Advantages

  • Supports recursion: Each call gets its own independent storage.
  • Efficient allocation/deallocation: Push and pop are O(1) operations.
  • Automatic management: No explicit deallocation needed — the stack handles it.
  • Good locality of reference: Recent frames are in cache.
  • Natural match for nested function calls.

Disadvantages

  • Cannot keep data beyond function return: Returning a pointer to a local variable is dangerous (dangling pointer).
  • Fixed-size allocation: The size of each frame must be known at compile time (for arrays, this means fixed-size arrays).
  • Stack overflow: Deep recursion or large local arrays can exhaust the stack.
  • No dynamic allocation: Cannot allocate memory whose size is determined at run time.

5. Heap Allocation

Heap allocation is the strategy used for dynamic memory allocation — memory that is requested during program execution and may be released at an arbitrary later time. Unlike stack allocation, heap allocation does not follow a LIFO order: memory can be allocated and freed in any order. This flexibility is essential for data structures like linked lists, trees, hash tables, and objects whose lifetimes are not tied to function calls.

How It Works

The heap is a large region of memory managed by the run-time system. When a program requests memory (via malloc(), new, etc.), the allocator searches the heap for a free block of sufficient size and returns a pointer to it. When the memory is no longer needed, it can be returned to the pool (via free()) for reuse. In languages with garbage collection (Java, Python, Go), the run-time system automatically reclaims memory that is no longer reachable by the program.

Memory Management Strategies

First Fit: Allocate the first free block that is large enough. Fast but may leave small fragments at the beginning.

Best Fit: Allocate the smallest free block that is large enough. Reduces wasted space but requires searching the entire free list.

Worst Fit: Allocate the largest free block. Leaves the largest remaining block, but degrades over time.

Buddy System: Memory is divided into blocks of power-of-2 sizes. When a block is freed, it can be merged with its "buddy" if the buddy is also free. Efficient but suffers from internal fragmentation.

Dangling References

A dangling reference (also called a dangling pointer) occurs when a program holds a pointer to memory that has already been deallocated. Accessing such a pointer leads to undefined behavior — the memory may have been reallocated for a different purpose, leading to data corruption or crashes. Dangling references are one of the most common and dangerous bugs in C/C++ programs.

// Dangling reference example in C
int* create_value() {
    int x = 42;
    return &x;   // BAD: x is on the stack, will be deallocated on return
}

int main() {
    int* p = create_value();
    printf("%d", *p);  // UNDEFINED BEHAVIOR: p is a dangling reference
}

In contrast, garbage-collected languages (Java, Python) prevent dangling references by only deallocating memory when no references to it remain. However, they may suffer from memory leaks if references to unneeded objects are accidentally retained.

6. Activation Records

An activation record (also called a stack frame) is the block of memory allocated on the stack each time a function (or procedure, method, or subroutine) is called. It contains all the information needed to execute the function and to properly return control to the caller when the function completes. The activation record is the fundamental data structure of stack-based allocation, and understanding its structure is essential for anyone studying compiler design or systems programming.

Definition: An activation record is a contiguous block of storage on the run-time stack that manages the execution of a single procedure activation. It contains the procedure's parameters, local variables, return address, saved registers, and other bookkeeping information needed for proper execution and return.

Fields of an Activation Record

A general-purpose activation record contains the following fields, arranged from the top (high address) to the bottom (low address) of the stack frame:

Fig. 5 — General activation record structure showing all standard fields

1. Return Value: Space allocated for the function's return value. In many calling conventions, small return values are passed in registers rather than on the stack, but the conceptual field exists in every activation record.

2. Actual Parameters: The arguments passed by the calling function. In some architectures (like x86-64), the first few parameters are passed in registers for efficiency, with overflow parameters placed on the stack. The number and size of parameters are known at compile time.

3. Return Address: The address in the calling function to which control should return when the called function completes. This is typically saved automatically by the CALL instruction on most architectures.

4. Saved Control Link (Dynamic Link): A pointer to the activation record of the caller. This forms a chain of activation records on the stack, allowing the run-time system to unwind the stack when a function returns. The control link is also called the dynamic link because it reflects the dynamic (run-time) calling sequence.

5. Saved Access Link (Static Link): A pointer to the activation record of the lexically enclosing function. This is needed in languages with nested functions (like Pascal, Python, and modern JavaScript) where an inner function may need to access variables declared in an outer function. The access link is also called the static link because it reflects the static (compile-time) nesting structure. In languages without nested functions (like C), the access link is not needed.

6. Saved Machine Status: Register values and other processor state that must be preserved across the function call. The calling convention specifies which registers the callee must save ("callee-saved" registers) and which the caller must save ("caller-saved" registers).

7. Local Data: Storage for the function's local variables. The size of this section is determined at compile time based on the declarations in the function.

8. Temporaries: Storage for intermediate values generated during expression evaluation that cannot be held in registers. The size of this section is determined by the code generator.

7. Activation Trees & Control Stack

An activation tree is a tree that represents the dynamic calling structure of a program during execution. Each node in the tree corresponds to a single activation (invocation) of a function, and an edge from node A to node B indicates that function B was called directly by function A. The root of the tree represents the initial invocation of the main function. The activation tree is a conceptual tool — it is not explicitly constructed at run time, but it helps us understand the relationship between function calls and the stack.

Fig. 6 — Activation tree for a sample program: main calls foo() and bar(); foo() calls baz() twice; bar() calls qux() which calls baz().

The relationship between the activation tree and the control stack is one of the most elegant observations in compiler design. As the program executes, the sequence of function calls traces a path through the activation tree in preorder (visit the node, then recursively visit children left to right). The control stack at any given moment contains exactly the nodes along the path from the root to the currently active node. When a function is called, its node is pushed onto the stack; when it returns, its node is popped.

Consider the activation tree in Fig. 6. The execution proceeds as follows: main() is called first (pushed onto the stack). main() calls foo() (pushed). foo() calls baz() the first time (pushed). baz() returns (popped). foo() calls baz() the second time (pushed). baz() returns (popped). foo() returns (popped). main() calls bar() (pushed). And so on. At each moment, the control stack mirrors the path from root to current node in the tree.

Dangling References (Detailed)

A dangling reference arises when a program holds a pointer or reference to a storage location that has been deallocated. This is one of the most pernicious categories of bugs in systems programming, and understanding it is essential for both compiler design and software engineering. The most common scenario occurs when a function returns a pointer to a local variable allocated on the stack:

int* dangerous() {
    int local = 42;
    return &local;  // local will be deallocated when function returns
}

void caller() {
    int* p = dangerous();
    // p now points to deallocated stack memory — dangling reference!
    printf("%d\n", *p);  // undefined behavior
}

When dangerous() returns, its activation record (including local) is popped from the stack. The pointer p in caller() now points to memory that may be overwritten by the next function call's activation record. The compiler cannot prevent this at compile time in languages like C — it is the programmer's responsibility. In contrast, Java and Python use garbage collection, which prevents dangling references by design (objects are only collected when no references to them remain).

Common Student Confusion

Many students confuse dangling references with memory leaks. A dangling reference is a pointer to freed memory (accessing it is undefined). A memory leak is memory that has been allocated but never freed (it becomes unreachable but is not returned to the system). They are opposite problems: dangling references free too early; memory leaks never free.

8. Storage Allocation in C

The C programming language provides a particularly instructive case study for understanding storage allocation, because C exposes all three strategies — static, stack, and heap — directly to the programmer. Unlike higher-level languages that abstract away memory management details, C requires the programmer to explicitly choose how and where memory is allocated, making it an ideal language for studying the tradeoffs involved.

Static Allocation in C

In C, global variables (declared outside any function) and static local variables (declared with the static keyword inside a function) are allocated statically. Their storage is reserved at program startup and persists for the entire duration of the program. Static local variables are particularly interesting: they retain their values across function calls, unlike regular local variables which are destroyed and recreated with each call.

void counter() {
    static int count = 0;  // allocated once, persists across calls
    count++;
    printf("Called %d times\n", count);
}

int main() {
    counter();  // prints "Called 1 times"
    counter();  // prints "Called 2 times"
    counter();  // prints "Called 3 times"
}

The variable count is initialized to 0 exactly once (at program startup, not at each function call). Each invocation of counter() increments and prints the same variable. The storage for count resides in the static data segment, not on the stack. This is a clear example of how static allocation gives a variable a lifetime that exceeds any single function activation.

Stack Allocation in C

Regular local variables in C are allocated on the stack. Each time a function is called, a new activation record is created, and local variables are allocated within it. When the function returns, the activation record is destroyed, and all local variable storage is implicitly deallocated. This is why local variables do not retain their values between calls (unless declared static).

void example() {
    int x = 10;     // on the stack
    char buf[100];  // on the stack — 100 bytes reserved in this frame
    double y = 3.14; // on the stack
    // all three are deallocated when example() returns
}

The size of the stack frame is determined at compile time: the compiler counts all local variables, calculates their sizes (including arrays with compile-time-known sizes), and allocates the appropriate amount of space. This is why variable-length arrays (VLAs), introduced in C99, are problematic — their size is not known until run time, making stack frame size dynamic.

Heap Allocation in C

C provides the malloc(), calloc(), realloc(), and free() functions for explicit heap memory management. Heap-allocated memory persists until explicitly freed by the programmer, regardless of which function allocated it or when it was called.

struct Node* create_node(int data) {
    struct Node* n = (struct Node*)malloc(sizeof(struct Node));
    n->data = data;
    n->next = NULL;
    return n;  // safe: heap memory survives function return
}

void destroy_list(struct Node* head) {
    while (head) {
        struct Node* temp = head;
        head = head->next;
        free(temp);  // explicitly return memory to heap
    }
}

The critical difference between stack and heap allocation in C is the responsibility for deallocation. Stack memory is automatically managed by the compiler (allocation on function entry, deallocation on function exit). Heap memory requires explicit management by the programmer. Failure to call free() results in memory leaks; calling free() too early (while pointers still reference the memory) creates dangling references.

9. Parameter Passing Mechanisms

When a function (the caller) invokes another function (the callee), it must communicate data to the callee through parameters. The mechanism by which this communication occurs is called parameter passing, and different languages support different mechanisms, each with distinct semantics, performance characteristics, and use cases. Understanding parameter passing is essential for compiler design (the compiler must generate correct code for each mechanism), for language design (choosing the right default mechanism affects language usability), and for exam preparation (parameter passing comparisons appear frequently in university examinations).

1. Call by Value

In call by value, the caller computes the value of each actual parameter and passes a copy of that value to the callee. The callee receives this copy in its formal parameter variables, which are local to the callee's activation record. Any modification to the formal parameters inside the callee does not affect the actual parameters in the caller. This is the default parameter passing mechanism in C, Java (for primitive types), and many other languages.

void swap(int a, int b) {  // a and b are copies
    int temp = a;
    a = b;         // modifies local copy only
    b = temp;      // modifies local copy only
}

int main() {
    int x = 5, y = 10;
    swap(x, y);
    printf("x=%d, y=%d\n", x, y);  // prints "x=5, y=10" — swap failed!
}

The swap function fails because a and b are copies of x and y. Modifying the copies has no effect on the originals. Call by value is safe (the callee cannot accidentally corrupt the caller's data) but limited (the callee cannot communicate results back through parameter modification).

Advantages: Simplicity, safety (callee cannot corrupt caller's variables), easy to reason about (no aliasing issues).

Disadvantages: Inefficient for large data structures (entire structure must be copied), cannot use parameters for output.

2. Call by Reference

In call by reference, the caller passes the address (or reference) of each actual parameter to the callee. The callee's formal parameters become aliases for the actual parameters — any modification to the formal parameter directly modifies the actual parameter in the caller's storage. This is the default in C++ (with & syntax), C# (with ref keyword), and Pascal (for var parameters).

// C++ example
void swap(int &a, int &b) {  // a and b are references to caller's variables
    int temp = a;
    a = b;         // modifies the original x
    b = temp;      // modifies the original y
}

int main() {
    int x = 5, y = 10;
    swap(x, y);
    cout << "x=" << x << ", y=" << y;  // prints "x=10, y=5" — swap works!
}

Advantages: Efficient (only an address is passed, not a copy of the data), allows the callee to modify caller's variables, natural for output parameters.

Disadvantages: Risk of unintended side effects (aliasing), harder to reason about code, callee can corrupt caller's data.

3. Call by Value-Result (Copy-In / Copy-Out)

Call by value-result (also called copy-in, copy-out) is a hybrid mechanism. Like call by value, the callee receives a copy of the actual parameter. However, when the callee returns, the final value of the formal parameter is copied back to the actual parameter. This gives the callee the ability to modify the caller's variables (like call by reference) while maintaining the locality benefits of call by value during execution.

// Pseudocode
procedure swap(a, b: integer)  // value-result parameters
    temp := a
    a := b
    b := temp
end

x := 5; y := 10
swap(x, y)
// After return: a's final value (10) is copied to x
//               b's final value (5) is copied to y
// Result: x=10, y=5

Key difference from call by reference: In value-result, the callee works on a copy during execution, so if the callee reads the parameter multiple times and the caller modifies the original between reads, the callee sees a consistent snapshot. In call by reference, the callee sees the caller's variable directly, which can lead to aliasing issues.

4. Call by Result

Call by result is similar to value-result, but the initial value of the formal parameter is undefined when the callee begins execution (no copy-in). Only on return is the final value of the formal parameter copied back to the actual parameter (copy-out). This is used for output-only parameters — parameters whose sole purpose is to communicate a result from the callee back to the caller.

5. Call by Name

Call by name is a parameter passing mechanism in which the actual parameter is not evaluated at the time of the call. Instead, the actual parameter expression is re-evaluated each time the corresponding formal parameter is used inside the callee. This is conceptually equivalent to textual substitution of the actual parameter for the formal parameter in the callee's body. Call by name was used in ALGOL 60 and is the theoretical basis for lazy evaluation in modern functional languages.

// ALGOL 60-style pseudocode
procedure increment(n, x)
    n := n + 1
    x := x + 1
end

i := 0
increment(i, i)
// n receives i (name "i"), x receives i (name "i")
// Step 1: n := n + 1 → i := i + 1 → i becomes 1
// Step 2: x := x + 1 → i := i + 1 → i becomes 2
// Result: i = 2

Call by name is powerful but confusing (the Jensen's device trick exploits it for elegant summation functions) and has largely been replaced by call by need (lazy evaluation) in modern languages like Haskell.

Can Call by Value, Call by Result, and Call by Reference Produce Different Results?

Yes, absolutely. Consider the following example adapted from the PYQ:

procedure P(x, y: integer)

Under call by reference: Both x and y are aliases for a. After x := x + 1, a becomes 6. After y := y + 1, a becomes 7. Result: a = 7.

Under call by value-result: x = 5, y = 5 (copies). After execution, x = 6, y = 6. On return, x's value (6) is copied to a, then y's value (6) is copied to a. Result: a = 6 (but this depends on copy-out order — if y is copied first, a = 6; if x is copied first, a = 6 in this case, but can differ in other scenarios).

10. Symbol Tables

A symbol table is a data structure maintained by the compiler (and sometimes by the run-time system) that stores information about all the identifiers (symbols) encountered in the source program. For each identifier, the symbol table records attributes such as its name, type, scope (the region of the program where it is visible), memory location (or offset), size, and any other relevant information. The symbol table is consulted during every phase of compilation: the lexer inserts new identifiers, the parser checks for declarations, the semantic analyzer verifies type compatibility, and the code generator uses it to determine memory addresses.

Definition: A symbol table is an association data structure that maps identifier names to their attributes (type, scope, memory location, etc.), supporting efficient lookup, insertion, and deletion operations during compilation.

Operations on Symbol Tables

The three fundamental operations on a symbol table are:

  1. Insert(symbol, attributes): Add a new identifier with its associated attributes. This is called when a declaration is processed. If the symbol already exists in the current scope, it indicates a duplicate declaration error.
  2. Lookup(symbol): Search for an identifier and return its attributes. This is called when the identifier is used in an expression or statement. If the symbol is not found, it indicates an undeclared variable error.
  3. Delete(scope): Remove all symbols belonging to a particular scope. This is called when a scope ends (e.g., when a function returns or a block closes). This operation is essential for managing nested scopes correctly.

Data Structures for Symbol Tables

Several data structures can be used to implement symbol tables, each with different performance characteristics:

1. Linear List: The simplest implementation — a list of (name, attributes) pairs. Lookup is O(n) — scan the list from the beginning. Insertion is O(1) if added at the front. Deletion is O(n). This is acceptable for small programs but too slow for large ones.

2. Hash Table (Hash Map): The most commonly used implementation in production compilers. A hash function maps identifier names to indices in an array of "buckets." Lookup, insertion, and deletion are all O(1) on average (O(n) worst case with many collisions). Collisions are handled by chaining (each bucket is a linked list) or open addressing. The hash table is typically organized as a set of hash tables, one per scope, to handle nested scopes efficiently.

3. Binary Search Tree (BST): Identifiers are stored in a BST ordered lexicographically. Lookup, insertion, and deletion are O(log n) in the balanced case. A balanced BST (such as an AVL tree or red-black tree) guarantees O(log n) worst case. BSTs are less commonly used than hash tables for symbol tables but provide ordered traversal, which is useful for debugging and error messages.

4. Tree-Structured Symbol Tables: For languages with nested scopes (like C, Java, Pascal), the symbol table is often organized as a tree of hash tables. Each scope has its own hash table, and the tree structure mirrors the nesting of scopes. When looking up an identifier, the compiler searches the current scope first, then the enclosing scope, and so on up to the global scope. This naturally implements static (lexical) scoping.

Fig. 8 — Tree-structured symbol table showing nested scopes and the lookup chain for static scoping

5. Sorted Array with Binary Search: Identifiers are stored in a sorted array. Lookup is O(log n) using binary search. Insertion is O(n) due to shifting. This is simple to implement but not practical for heavily modified symbol tables.

Code (low) → Static Data → Heap (↑ grows up) → [Free Space] → Stack (↓ grows down, high addresses)

Static Allocation

Fixed at compile time. No recursion. No dynamic data. Fast access. FORTRAN 77 example.

Stack Allocation

LIFO. Activation records pushed/popped. Supports recursion. Automatic deallocation. Stack overflow risk.

Heap Allocation

Dynamic. Arbitrary order. malloc/free or garbage collection. Supports linked lists, trees, objects.

Activation Record Fields

Return value, parameters, return address, control link, access link, saved registers, local data, temporaries.

Parameter Passing

Value (copy), Reference (alias), Value-Result (copy in/out), Result (output only), Name (re-evaluate).

Dangling Reference

Pointer to freed memory. Caused by returning address of local variable. Prevented by garbage collection.

Symbol Table

Maps identifiers to attributes. Operations: insert, lookup, delete. Best implementation: hash table.

Exam Night Revision Sheet

Ultra-condensed recap for the final hours before the exam

SDT — 60-Second Recap
  • SDT = Grammar + Attributes + Semantic Rules. Attaches computations to grammar productions.
  • SDD = Declarative specification. Says WHAT to compute, not WHEN.
  • Synthesized = computed from children (bottom-up). Inherited = from parent/siblings (top-down/sideways).
  • S-Attributed = only synthesized. Compatible with LR parsers. Evaluated during reductions.
  • L-Attributed = synthesized + inherited, constrained to left-to-right evaluation. Compatible with LL and LR parsers.
  • Dependency graph = directed graph of attribute dependencies. Acyclic → valid evaluation order.
  • Syntax tree = condensed parse tree without parentheses and single-productions. Built via mkNode / mkLeaf.
  • Bottom-up evaluation = attribute stack parallel to parser stack. Values pushed on shift, combined on reduce.
  • Top-down translation = embedded actions in LL parsing. Compute inherited before expanding, synthesized after.
Run-Time Environments — 60-Second Recap
  • Memory layout: Code → Static → Heap (↑) → Free → Stack (↓).
  • Static: Fixed addresses, compile-time. No recursion. Fast. FORTRAN.
  • Stack: LIFO activation records. Supports recursion. O(1) alloc/dealloc. Local variables.
  • Heap: Dynamic. malloc/new. Garbage collection. Supports dynamic data structures.
  • Activation record: Return value, params, return addr, control link, access link, saved regs, locals, temps.
  • Control link (dynamic): Points to caller's frame. Access link (static): Points to enclosing scope's frame.
  • Activation tree: Nodes = function invocations. Preorder = call order. Control stack = path from root to current.
  • Dangling reference: Pointer to deallocated memory. Caused by returning &local. Prevented by GC.
  • Call by value: Copy. Safe. Reference: Alias. Fast but dangerous. Value-Result: Copy in/out. Name: Re-evaluate expression.
  • Symbol table: Maps names to attributes. Operations: insert, lookup, delete. Best: hash table (O(1) avg).
