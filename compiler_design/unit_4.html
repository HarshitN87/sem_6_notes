Section 4.1

Intermediate Languages

Why compilers speak to themselves before speaking to machines

Why Does Intermediate Code Exist?

Consider the fundamental challenge facing any compiler writer: a single source language (say, C or Java) must eventually run on dozens of different processor architectures, each with its own instruction set, register file, memory model, and calling conventions. If the compiler translated directly from source to every target machine, you would need m × n separate compilers for m languages and n architectures — an engineering nightmare that scales catastrophically. The history of computing is littered with the corpses of projects that attempted this brute-force approach. The insight that resolved this combinatorial explosion was deceptively simple: insert an intermediate representation between the front end and the back end. Now the front end produces one intermediate form per source language, and the back end consumes one intermediate form per target architecture. The total work drops from m × n to m + n, a saving so dramatic that virtually every production compiler built since the 1970s has adopted this architecture. The GNU Compiler Collection (GCC) uses GIMPLE and RTL as its intermediate forms; LLVM uses its famous IR; the Java compiler produces bytecode. Each of these is an intermediate language designed to sit in that crucial middle position, absorbing the complexity of translation so that neither the front end nor the back end needs to understand the other's world.

The benefits of intermediate code extend far beyond mere modularity. An intermediate representation serves as the ideal substrate for machine-independent optimisations. When the compiler has translated the source program into a clean, structured intermediate form, it becomes possible to apply transformations — constant folding, dead code elimination, loop invariant code motion, common subexpression elimination — without worrying about the peculiarities of any particular instruction set. These optimisations improve the program regardless of where it will eventually run, so performing them at the intermediate level means the improvement automatically propagates to every target architecture. Furthermore, intermediate code makes the compiler vastly easier to debug and maintain. When something goes wrong, the developer can inspect the intermediate output and determine whether the fault lies in the front end (which produced bad intermediate code) or the back end (which mistranslated correct intermediate code). This separation of concerns is not merely convenient; it is the difference between a manageable engineering project and an unmaintainable monolith.

Figure 4.1 — The compiler pipeline. Intermediate code is the architectural pivot that decouples source-language analysis from target-machine synthesis.

Principal Intermediate Representations

Intermediate representations come in several flavours, each with its own strengths. The most common forms are Three Address Code (3AC), Quadruples, Triples, Indirect Triples, Abstract Syntax Trees (AST), Postfix notation, and DAGs (Directed Acyclic Graphs). Among these, Three Address Code and its tabular variants (quadruples and triples) dominate university syllabi and examination questions, and for good reason: they expose the structure of computation in a form that is both human-readable and machine-translatable. In Three Address Code, every instruction has at most one operator on the right-hand side, which means the instruction can be directly mapped to a single machine instruction on most architectures. This property — sometimes called the "one operation per statement" rule — is what makes 3AC so valuable as a compilation target. The restriction to three addresses (two operands and one result) mirrors the structure of actual hardware instructions, which typically consume two source registers and produce one destination register.

✦ Exam Tip — Benefits of Intermediate Code

Section 4.2

Three Address Code (3AC)

One operation, three addresses — the lingua franca of intermediate compilation

Understanding Three Address Code

Three Address Code is an intermediate representation in which each instruction contains at most one operator on the right-hand side, along with at most two operand addresses and one result address — hence the name "three address." The general form is x = y op z, where x is the result, y and z are operands, and op is an operator. When an instruction requires fewer than three addresses (such as unary operations or assignments), the unused fields are simply left empty or marked with a dash. The beauty of this restriction is that it breaks complex expressions down into their atomic computational steps, making explicit every temporary value that the programmer left implicit. Consider the expression a + b * c: a human understands operator precedence and evaluates b * c first, but the intermediate code must make this ordering explicit. In 3AC, this becomes two instructions — t1 = b * c followed by t2 = a + t1 — where t1 and t2 are compiler-generated temporary variables that hold intermediate results.

The introduction of temporary variables is one of the most important conceptual aspects of 3AC. When a programmer writes x = a + b * c - d, the compiler must decompose this single statement into a sequence of primitive operations, each producing a temporary result. The process mirrors how one might evaluate the expression on paper: first compute b * c, store it somewhere, then add a, store that result, then subtract d, and finally store the overall result in x. Each "store somewhere" corresponds to a temporary variable in 3AC. These temporaries are not part of the original program; they are the compiler's bookkeeping mechanism for tracking partial results. In the final machine code, temporaries typically become registers or stack locations, but at the intermediate level they exist as abstract names that simplify the compiler's task enormously. The number of temporaries required for an expression is directly related to the depth of the expression tree — a fact that has implications for register allocation later in the compilation process.

Three Address Code instructions can represent a variety of statement types. The most common categories include: assignments of the form x = y op z (binary operations) or x = op y (unary operations such as unary minus or negation); copy statements of the form x = y; unconditional jumps written as goto L; conditional jumps such as if x goto L or ifFalse x goto L or relational tests like if x relop y goto L; indexed assignments for array access such as x = y[i] and x[i] = y; pointer operations like x = *y and *x = y; and procedure-related instructions including param x, call p, n, and return x. Each of these forms maps naturally to one or a small number of machine instructions, which is precisely why 3AC serves so well as an intermediate form.

Generating 3AC from Expressions

The translation from an arithmetic expression to Three Address Code follows a systematic procedure rooted in the syntax tree of the expression. The compiler traverses the abstract syntax tree in a bottom-up fashion (post-order traversal), and for each interior node representing an operator, it emits a three-address instruction that applies that operator to the node's children and stores the result in a fresh temporary. Let us work through a detailed example to make this process concrete. Consider the expression a = -(x + y - z) + (b + c * d) * (x + y + g - h). This is a complex nested expression involving unary negation, multiple arithmetic operators, and repeated subexpressions. The 3AC for this expression proceeds as follows:

t1  = x + y
t2  = t1 - z
t3  = - t2          // unary minus
t4  = c * d
t5  = b + t4
t6  = x + y
t7  = t6 + g
t8  = t7 - h
t9  = t5 * t8
t10 = t3 + t9
a   = t10

Notice how the expression x + y appears twice — once in the negated subexpression and once in the right-hand product. A naive translation generates two separate temporaries (t1 and t6) for the same computation. A compiler performing common subexpression elimination (CSE) would recognise that x + y has already been computed and reuse t1 instead of generating t6. This is precisely the kind of optimisation that is easiest to perform at the intermediate code level, and it is one of the reasons why DAGs (which naturally detect common subexpressions) are discussed later in this unit. For examination purposes, unless the question specifically asks for optimised code, it is generally safe to generate the straightforward (unoptimised) 3AC and then note that CSE could improve it.

◆ Memory Anchor

Think of 3AC as a recipe with one step per instruction. Just as a recipe says "crack the eggs into bowl B, whisk, then add flour from bowl A," Three Address Code says "take operand A, apply operation, store result in temporary T." Each instruction does exactly one thing, making the sequence of computations completely explicit.

Implementation Representations of 3AC

Three Address Code is a conceptual model, but in practice it must be stored in a data structure within the compiler. The three most common implementations are Quadruples, Triples, and Indirect Triples. Each represents the same logical information but uses a different data structure, with different trade-offs in terms of space efficiency, ease of optimisation, and ease of code generation. Understanding these three representations — and being able to construct all three for a given expression — is essential for university examinations, where this topic appears with remarkable regularity. The next section provides a thorough treatment of each representation.

Section 4.3

Quadruples, Triples & Indirect Triples

Three ways to tabulate the same truth — each with its own engineering character

Quadruples

The quadruple representation stores each three-address instruction as a record with four fields: (op, arg1, arg2, result). The op field holds the operator, arg1 and arg2 hold the operands (or pointers to symbol-table entries), and result holds the name of the temporary or variable where the computed value is stored. For unary operations, the arg2 field is left blank (conventionally marked with a dash or left null). For unconditional jumps, the result field holds the target label. This representation is straightforward, easy to understand, and easy to manipulate — which is why it is the most commonly taught form in university courses. The quadruple table for the expression a = -(x + y - z) + (b + c * d) * (x + y + g - h) is shown below:

#oparg1arg2result
0+xyt1
1−t1zt2
2uminust2—t3
3*cdt4
4+bt4t5
5+xyt6
6+t6gt7
7−t7ht8
8*t5t8t9
9+t3t9t10
10=t10—a

The principal advantage of quadruples is that optimisation passes can easily manipulate the table — replacing operands, rewriting operators, or eliminating redundant instructions — because every instruction is self-contained. The result field explicitly names the temporary, so when a later instruction references t5, the compiler can look up row 4 and see exactly how t5 was computed. The disadvantage is space: every instruction occupies four fields even when some are unused, and the temporary names themselves consume storage. For very large programs, this overhead can become significant, which motivates the triple representation.

Triples

The triple representation eliminates the result field entirely, storing each instruction as a three-field record: (op, arg1, arg2). The result of each computation is implicitly identified by the position (row number) of the triple in the table. When a subsequent instruction needs to refer to the result of an earlier computation, it uses the row number as a pointer — written in parentheses, such as (0) to refer to the result of the triple in row 0. This saves space because temporary names are no longer needed, but it introduces a complication: if the compiler rearranges or deletes triples during optimisation, all position-based references become invalid. This fragility makes triples less suitable for aggressive optimisation, though they are perfectly adequate for straightforward translation. The triple table for the same expression is:

#oparg1arg2
0+xy
1−(0)z
2uminus(1)—
3*cd
4+b(3)
5+xy
6+(5)g
7−(6)h
8*(4)(7)
9+(2)(8)
10=(9)a

Observe how every reference to a previously computed value uses the row number in parentheses. Triple (5) computes x + y independently of triple (0), even though they compute the same value — the triple representation does not inherently perform common subexpression elimination. A compiler using triples would need a separate pass to detect and merge such redundancies. The assignment a = t10 is represented as triple (10) with op =, arg1 (9) (the value being assigned), and arg2 a (the target variable). Different textbooks may order the arguments of the assignment differently, so it is worth checking your course material for the exact convention used.

Indirect Triples

Indirect triples combine the space efficiency of triples with the flexibility of quadruples. Instead of storing instructions directly in a position-indexed table, the compiler maintains two structures: a pointer table (an array of pointers, one per instruction, in execution order) and an instruction table (a pool of unique triple records). The pointer table determines the order of execution, while the instruction pool stores each distinct instruction only once. This separation means that the compiler can rearrange the pointer table (changing execution order) without disturbing the instruction pool, so optimisation passes can reorder, insert, or delete instructions simply by manipulating pointers — the underlying triples remain stable. This is a significant practical advantage over plain triples, where reordering invalidates positional references.

For the same expression, the indirect triple representation would have a pointer table of 11 entries (indices 0 through 10) pointing into an instruction pool. If triples (0) and (5) both compute x + y, the instruction pool might store this triple only once, and both pointer entries 0 and 5 would point to it. This natural deduplication saves space and also hints at common subexpression elimination. However, note that the two x + y computations are conceptually independent in the unoptimised code; the indirect triple representation makes it easy to detect the duplication, but the actual merging requires a deliberate optimisation decision.

Quadruples

Fields: 4 (op, arg1, arg2, result)
References: By temporary name
Space: Higher (explicit temp names)
Optimisation: Easy — self-contained records
Reordering: Safe — no positional dependencies

Triples

Fields: 3 (op, arg1, arg2)
References: By row position
Space: Lower (no temp names)
Optimisation: Fragile — reordering breaks refs
Reordering: Unsafe — positional refs invalidated

Indirect Triples

Fields: 3 + pointer table
References: By pointer into pool
Space: Moderate (pool + pointers)
Optimisation: Flexible — pointer table is mutable
Reordering: Safe — rearrange pointers, not triples

When to Use What

Quadruples: When optimisation is a priority and space is not constrained.
Triples: When space is tight and the code is straightforward.
Indirect Triples: When you want both space efficiency and optimisability — the best of both worlds.

Worked Example: a + a * (b − c) + (b − c) * d

This expression is interesting because the subexpression (b - c) appears twice, making it a candidate for common subexpression elimination. Let us first generate the unoptimised 3AC, then construct all three representations. The syntax tree tells us to evaluate b - c, multiply by a, add a, compute b - c again, multiply by d, and add the two results:

// Unoptimised 3AC
t1 = b - c
t2 = a * t1
t3 = a + t2
t4 = b - c        // same as t1 — common subexpression
t5 = t4 * d
t6 = t3 + t5

The quadruple table for this expression is:

#oparg1arg2result
0−bct1
1*at1t2
2+at2t3
3−bct4
4*t4dt5
5+t3t5t6

And the triple table is:

#oparg1arg2
0−bc
1*a(0)
2+a(1)
3−bc
4*(3)d
5+(2)(4)

For indirect triples, the pointer table has entries [ptr0, ptr1, ptr2, ptr3, ptr4, ptr5] pointing into the instruction pool, which contains the unique triples. Since triples 0 and 3 are identical (both compute b - c), the pool stores this triple once, and both ptr0 and ptr3 reference it — a natural space saving that also signals the common subexpression to the optimiser.

The pattern is identical: two repeated subexpressions, one multiplied on the left and one on the right, with the outermost addition combining them. Practice this pattern and you can handle any variant.

Section 4.4

Declarations

How the compiler records the existence and shape of every named entity

When the compiler encounters a declaration — whether it declares a variable, an array, a record structure, or a procedure — it does not generate executable code in the usual sense. Instead, it performs bookkeeping: it creates or updates entries in the symbol table, recording the name, type, scope, storage class, and (crucially) the relative memory address of the declared entity. The task of processing declarations is primarily a front-end responsibility, but the information gathered during declaration processing directly affects the intermediate code that the back end will eventually translate into target code.

For simple scalar variable declarations such as int x; or float y;, the compiler allocates a fixed amount of storage (4 bytes for a typical integer, 4 or 8 bytes for a floating-point number, depending on the target architecture) and records the offset from some base address — typically the beginning of the current activation record on the runtime stack. The intermediate code for a simple declaration might be implicit (just a symbol table update) or explicit, depending on the intermediate representation. Some intermediate representations emit an instruction like alloc int, 4 to indicate that 4 bytes of storage should be reserved for an integer variable, but this is relatively uncommon in examination contexts.

Array declarations are more interesting from an intermediate code perspective. When the compiler encounters a declaration like int A[10][20], it must compute the total storage required (10 × 20 × 4 = 800 bytes for a two-dimensional integer array in row-major order) and record the dimensions in the symbol table so that later array accesses can be translated into address calculations. The symbol table entry for an array typically stores the base address, the element type and size, the number of dimensions, and the upper and lower bounds of each dimension. This information is essential for computing the address of A[i][j] using the formula base + ((i - low1) × (high2 - low2 + 1) + (j - low2)) × sizeof(element). For arrays with lower bound 1 (common in many languages), this simplifies to base + ((i-1) × n + (j-1)) × w where n is the number of columns and w is the element width.

For record (struct) declarations, the compiler assigns offsets to each field based on the sizes and alignment requirements of the fields. In C, for example, the compiler may insert padding between fields to ensure that each field begins at an address aligned to its natural boundary. The intermediate code for accessing a record field typically involves computing base + field_offset, where field_offset is a constant determined at compile time from the struct layout. Type declarations (typedef, enum, etc.) do not generate intermediate code at all; they simply create type aliases or enumerated constants in the symbol table.

✦ Exam Tip

Questions on declarations in compiler design exams typically focus on how the symbol table is populated and how array address calculations work. For a 5-mark question, explain the symbol table entry structure (name, type, size, offset, dimensions for arrays) and give the address formula for a 2D array. For a 10-mark question, include a worked example of computing the address of A[3][5] in a int A[10][10] declaration with base address 200 and element size 4 bytes: 200 + ((3-1)×10 + (5-1))×4 = 200 + 96 = 296.

Section 4.5

Assignment Statements

Translating the most fundamental computational act into intermediate form

An assignment statement has the form id = expression, and its translation to Three Address Code is one of the most fundamental operations in a compiler. The process is conceptually straightforward: translate the right-hand side expression into a sequence of three-address instructions that compute its value into a temporary, then emit a copy instruction that stores the temporary's value into the left-hand side variable. The subtlety lies in the details — particularly when the left-hand side involves array accesses, pointer dereferences, or record field selections, each of which requires additional intermediate code to compute the target address.

For a simple scalar assignment like x = a + b * c, the translation is: t1 = b * c; t2 = a + t1; x = t2. The last instruction (x = t2) is a simple copy. For an array element assignment like A[i] = a + b, the compiler must first compute the address of A[i] and then store the value there. In 3AC, this is represented as t1 = a + b; t2 = i * w; A[t2] = t1, where w is the element width. The notation A[t2] indicates that the value should be stored at offset t2 from the base address of A. For two-dimensional arrays, the address computation is more involved: A[i][j] = expr becomes a sequence that computes the linear index from the two subscripts, multiplies by the element width, and stores the value at the computed offset from the base address.

Pointer assignments require special treatment. An assignment like *p = x (store x at the address pointed to by p) is represented in 3AC as *p = x, where the asterisk denotes indirect store. Conversely, x = *p (load from the address in p into x) is represented as x = *p. These indirect operations are essential for implementing pointers and references in languages like C and C++, and they map directly to load and store instructions with indirect addressing modes on most target machines. The intermediate code must distinguish between direct assignments (where the left-hand side is a simple variable name) and indirect assignments (where the left-hand side involves a pointer dereference or array index), because the generated target code is fundamentally different in each case.

// Example: x = a[i] + *p
t1 = i * w          // compute offset for a[i]
t2 = a[t1]          // load a[i]
t3 = *p             // load value pointed to by p
t4 = t2 + t3        // add
x = t4              // store result

// Example: A[i][j] = x + y  (A is m×n, element width w)
t1 = x + y
t2 = i - lb1        // subtract lower bound of dimension 1
t3 = n              // number of columns
t4 = t2 * t3
t5 = j - lb2        // subtract lower bound of dimension 2
t6 = t4 + t5
t7 = t6 * w         // multiply by element width
A[t7] = t1          // store at computed address
Section 4.6

Boolean Expressions

Translating logic, short-circuit evaluation, and flow of control

Boolean expressions play a dual role in programming languages. On one hand, they appear in contexts where their value is needed as data — for example, assigning the result of a comparison to a boolean variable. On the other hand, and more commonly, they appear as the controlling conditions of flow-of-control statements: if, while, for, and so on. The compiler's treatment of boolean expressions differs significantly depending on which role the expression is playing. When the value is needed as data, the compiler generates code that computes the boolean result (typically 0 or 1) into a temporary variable. When the expression controls a branch, the compiler generates code that jumps to one of two labels depending on whether the expression evaluates to true or false — without ever explicitly computing a boolean value. This second approach, known as jump-based or flow-of-control translation, is both more efficient and more common in practice.

A boolean expression in a typical programming language consists of boolean operators (||, &&, !), relational operators (<, <=, >, >=, ==, !=), and boolean constants (true, false). The translation of relational expressions like a < b into 3AC for flow-of-control contexts is direct: emit if a < b goto L_true followed by goto L_false. The boolean operators && and || are short-circuit operators in C-like languages, meaning that E1 && E2 does not evaluate E2 if E1 is false, and E1 || E2 does not evaluate E2 if E1 is true. This short-circuit behaviour is naturally implemented by the jump-based translation: if E1 is false, the code for E1 && E2 jumps directly to the false label without executing the code for E2.

The jump-based translation of boolean expressions uses two label lists: the true list (a list of jump instructions that should eventually jump to the "true" target) and the false list (a list of jump instructions that should eventually jump to the "false" target). When the compiler begins translating a boolean expression, it does not yet know where the true and false targets will be — these depend on the surrounding control structure (the body of an if, the exit of a while, etc.). The compiler therefore emits jumps with incomplete labels and records the positions of these jumps in the true and false lists. Later, when the control structure is fully parsed and the targets are known, the compiler backpatches the incomplete jumps — filling in the correct target labels. This mechanism of deferred label resolution is called backpatching, and it deserves a thorough treatment, which we provide in the dedicated section below.

◆ Memory Anchor

Think of backpatching like writing a letter where you mention "I'll tell you the meeting location later." You write the letter now (emitting jumps with blank labels), and later, when you know the location (the target label), you go back and fill in the blank. The true-list and false-list are your notes reminding you which blanks need to be filled.

Section 4.7

Case / Switch Statements

Translating multi-way branching into efficient intermediate code

The switch (or case) statement provides a multi-way branch based on the value of an expression. Its general form in C is:

switch (E) {
    case C1: S1; break;
    case C2: S2; break;
    ...
    case Cn: Sn; break;
    default: Sd;
}

The most straightforward translation strategy generates a sequence of conditional tests, one per case label. The compiler evaluates the expression E once, stores the result in a temporary, and then emits a series of comparisons: if t == C1 goto L1; if t == C2 goto L2; ...; if t == Cn goto Ln; goto Ld. Each label Li points to the code for the corresponding case body Si, and Ld points to the default body. After each case body, a goto to the exit label ensures that execution does not fall through to the next case (implementing the break semantics). This linear-search approach is simple to implement and works well when the number of cases is small. For a switch with many cases or densely packed integer constants, compilers may use a jump table — an array of code addresses indexed by the case value — which allows O(1) dispatch instead of O(n) sequential testing. However, the jump table optimisation is typically a back-end concern; at the intermediate code level, the sequential-test approach is the standard textbook treatment.

Let us translate the following switch statement into Three Address Code:

switch(a + b) {
    case 1: x = y + z; break;
    case 2: u = v + w; break;
    case 3: p = q * r / s; break;
    default: a = b + c;
}

The 3AC translation using the sequential-test approach is:

    t0 = a + b
    if t0 == 1 goto L1
    if t0 == 2 goto L2
    if t0 == 3 goto L3
    goto Ld

L1: t1 = y + z
    x = t1
    goto Lexit

L2: t2 = v + w
    u = t2
    goto Lexit

L3: t3 = q * r
    t4 = t3 / s
    p = t4
    goto Lexit

Ld: t5 = b + c
    a = t5

Lexit:

Notice the structure: the expression a + b is evaluated once into t0, and then a cascade of conditional jumps tests t0 against each case constant. Each case body ends with an unconditional jump to Lexit, preventing fall-through. The default case is reached only if none of the preceding tests succeed. In a real compiler, the backpatching mechanism would be used to fill in the labels — the jumps to L1, L2, L3, and Lexit would initially be emitted with incomplete targets, and the labels would be resolved when the corresponding code positions are determined.

✦ PYQ Alert — Switch-Case Translation

This exact switch-case translation question has appeared in previous exams. The key steps are: (1) evaluate the switch expression into a temporary, (2) emit a cascade of conditional jumps comparing the temporary to each case constant, (3) emit a fall-through to the default, (4) translate each case body with a goto-exit at the end, (5) translate the default body last. Remember that break translates to goto Lexit, and omitting break would mean falling through to the next case body.

Section 4.8

Backpatching

Deferred label resolution — the elegant mechanism that makes single-pass code generation possible

The Problem Backpatching Solves

When a compiler translates a control-flow statement like if (E) S1 else S2, it faces a timing dilemma. The boolean expression E must generate a conditional jump to the beginning of S1 (if true) or S2 (if false), but the compiler does not learn the target of the "false" jump until it has finished parsing S1 and encountered the else keyword. Similarly, the "true" jump for S1 must skip over S2 to the exit label, but this label is not known until the entire if-then-else construct has been parsed. In a multi-pass compiler, this is not a problem — the first pass can determine all label positions, and the second pass can fill them in. But in a single-pass compiler that generates code on the fly, the labels are genuinely unknown at the time the jumps are emitted. Backpatching resolves this dilemma by allowing the compiler to emit jumps with incomplete (blank) targets, record the positions of these jumps in a list, and fill in the correct targets later when they become known.

The Backpatching Mechanism

Backpatching uses three functions and maintains lists of incomplete jump instructions. The key data structure is a list of jump instruction positions — each element in the list is the index (in the instruction array) of a goto or conditional branch instruction whose target label has not yet been filled in. Three functions operate on these lists:

makelist(i) creates a new list containing the single instruction index i. This is called when a new jump instruction is emitted with an incomplete target.

merge(p1, p2) concatenates two lists p1 and p2 and returns the merged list. This is used when combining the true-lists (or false-lists) of two sub-expressions connected by || or &&.

backpatch(p, label) goes through every instruction index in list p and fills in the target field with label. This is called when the compiler finally determines the target address for a group of jumps.

SDT for Boolean Expressions with Backpatching

The following Syntax-Directed Translation scheme translates boolean expressions using backpatching. Each non-terminal has two inherited attributes, .truelist and .falselist, which are lists of jumps to be backpatched when the true target or false target (respectively) becomes known. The non-terminal also has a synthesized attribute .nextlist for jumps that should go to the next instruction after the construct.

// E → E1 || E2  (short-circuit OR)
E1.truelist = E.truelist       // if E1 is true, E is true
E1.falselist = makelist(nextinstr) // if E1 is false, try E2
                                    // emit: goto __
E2.truelist = merge(E1.truelist, E.truelist)
E2.falselist = E.falselist
backpatch(E1.falselist, instr for E2) // fill in: goto E2's code

// E → E1 && E2  (short-circuit AND)
E1.truelist = makelist(nextinstr)  // if E1 is true, try E2
                                    // emit: goto __
E1.falselist = E.falselist         // if E1 is false, E is false
E2.truelist = E.truelist
E2.falselist = merge(E1.falselist, E.falselist)
backpatch(E1.truelist, instr for E2) // fill in: goto E2's code

// E → !E1
E1.truelist = E.falselist
E1.falselist = E.truelist

// E → id1 relop id2
emit: if id1 relop id2 goto __
E.truelist = makelist(nextinstr - 1)
emit: goto __
E.falselist = makelist(nextinstr - 1)

// E → true
emit: goto __
E.truelist = makelist(nextinstr - 1)

// E → false
emit: goto __
E.falselist = makelist(nextinstr - 1)

The same backpatching mechanism extends naturally to control-flow statements. For if (E) S1 else S2:

// S → if (E) S1 else S2
// When parsing E, we don't know where S1 and S2 begin.
E.truelist  = makelist(...)  // jumps to S1, filled later
E.falselist = makelist(...)  // jumps to S2, filled later

// After parsing E:
backpatch(E.truelist, instr for S1)   // true → go to S1
backpatch(E.falselist, instr for S2)  // false → go to S2

S.nextlist = merge(S1.nextlist, S2.nextlist, makelist(goto __))
// The goto at the end of S1 skips over S2 to the exit
// backpatch(S.nextlist, next instruction after S)

Section 4.9

Procedure Calls

Translating the act of delegation — passing control, arguments, and receiving results

A procedure call is one of the most complex constructs to translate into intermediate code, because it involves multiple coordinated actions: evaluating and passing parameters, transferring control to the procedure body, allocating storage for the procedure's local variables, executing the procedure, returning the result (if any), and deallocating the local storage. The intermediate code for a procedure call typically uses three special instructions: param x (push parameter x onto the parameter list), call p, n (call procedure p with n parameters), and return x (return the value x to the caller). Some intermediate representations also use begin_call and end_call markers to delimit the parameter-passing sequence.

For a procedure call like f(a + b, c * d), the intermediate code is:

param a + b        // or: t1 = a + b; param t1
param c * d        // or: t2 = c * d; param t2
call f, 2          // call f with 2 parameters

The exact sequence depends on the parameter-passing convention. In call-by-value, the values of the arguments are computed and passed to the procedure, which receives copies. In call-by-reference, the addresses of the arguments are passed instead, allowing the procedure to modify the caller's variables. The intermediate code for call-by-reference would compute the addresses of the arguments and pass those addresses as parameters. For array arguments, the address of the first element (or the array base) is typically passed. The distinction between value and reference parameters affects both the intermediate code generation and the eventual target code, and it is a common topic for comparison-based exam questions.

Code Generation

Section 4.10

Issues in the Design of a Code Generator

The engineering tensions that shape the last mile of compilation

The code generator is the final phase of a compiler, responsible for translating the intermediate representation into the target machine code. This seemingly straightforward task is fraught with design decisions that affect the correctness, speed, and size of the generated code. The principal design issues can be grouped into several categories, each representing a fundamental tension in compiler engineering.

Input to the code generator. The code generator receives the intermediate code produced by the front end (and possibly improved by the optimiser) along with information from the symbol table about the types, sizes, and storage locations of all variables. The intermediate code may be in the form of Three Address Code, a DAG, a syntax tree, or a linearised representation. The choice of intermediate representation affects the complexity of the code generator: a simple linear 3AC is easy to translate instruction-by-instruction, while a DAG representation enables the generator to detect and exploit common subexpressions.

Instruction selection. The target machine typically offers multiple ways to accomplish the same computation. For example, the operation a + b might be implemented as an ADD instruction (if both operands are in registers), or as a sequence involving LOAD, ADD, and STORE instructions (if the operands are in memory). The code generator must select an instruction sequence that is both correct and efficient. Good instruction selection can dramatically improve code quality; poor instruction selection can produce code that is many times slower than necessary. The challenge is that the "best" instruction sequence depends on the surrounding context — the values already in registers, the addressing modes available, and the instructions that follow.

Register allocation. Registers are the fastest storage in any computer, but they are also the scarcest. The code generator must decide which values to keep in registers at each point in the program and which to spill to memory. This is an NP-complete optimisation problem in its general form, so practical compilers use heuristics such as graph colouring or the simple "next-use" strategy. Register allocation has an enormous impact on performance: a program that keeps its frequently accessed variables in registers can be orders of magnitude faster than one that repeatedly loads and stores from memory.

Instruction ordering. The order in which instructions are executed affects not only correctness but also performance, particularly on modern processors with pipelined execution, branch prediction, and out-of-order execution. While instruction scheduling is primarily a back-end optimisation, even a simple code generator must produce a correct ordering of instructions that respects data dependencies.

Evaluation order. The order in which the operands of an expression are evaluated can affect the efficiency of the generated code. If one operand is already in a register and the other must be loaded from memory, it may be more efficient to evaluate the register operand first so that the register can be freed sooner. Choosing an optimal evaluation order is another NP-hard problem in general, but simple heuristics (such as evaluating the operand with the highest "cost" first) can yield significant improvements.

◆ Memory Anchor for Design Issues

Remember the acronym IRIE: Instruction selection, Register allocation, Instruction ordering, Evaluation order. These four issues dominate every code generator design decision.

Section 4.11

The Target Machine

Understanding the hardware that will execute our generated code

A code generator must have a model of the target machine — its instruction set, registers, addressing modes, and memory architecture. University courses typically use a simplified target machine model to teach code generation without the overwhelming complexity of real architectures like x86 or ARM. The standard model, often called the "basic block machine," has the following characteristics:

Instruction set. The machine supports a set of instructions that closely mirror three-address code operations. Common instructions include: LD reg, addr (load a value from memory into a register), ST addr, reg (store a register value into memory), ADD reg1, reg2, reg3 or ADD reg1, reg2, addr (addition), and similarly for SUB, MUL, DIV. Some instructions support an immediate operand (a constant embedded in the instruction), such as ADD reg, reg, #5 (add the constant 5). Addressing modes include direct (the address is given explicitly), indexed (base + index register), and register indirect (the address is in a register).

Registers. The model typically has a small number of general-purpose registers, denoted R0, R1, R2, ..., Rn. All arithmetic and logical operations work on registers; memory is accessed only through load and store instructions. This load-store architecture is a simplification of RISC machines and makes the code generation algorithm easier to teach and understand. On a CISC machine, some arithmetic operations can have memory operands, which complicates instruction selection but can sometimes produce shorter code.

Cost model. Each instruction has an associated cost, typically measured in instruction count or clock cycles. The simplest cost model assigns cost 1 to every instruction. A more refined model might assign cost 2 to multiplication and division (since these operations take longer on most hardware) and cost 1 to loads, stores, and additions. The code generator aims to minimise the total cost of the instruction sequence for each basic block.

Section 4.12

Run-time Storage Management

How the compiler organises memory for code, data, stack, and heap

At runtime, the memory of a running program is typically divided into several regions: the code area (holding the compiled machine instructions), the static data area (holding global variables and constants whose addresses are known at compile time), the stack (holding activation records for procedure calls), and the heap (holding dynamically allocated data). The code generator must understand this layout because it determines how variables are addressed: a global variable might be at a fixed address in the static area, a local variable is at a known offset from the stack pointer within the current activation record, and a dynamically allocated object is accessed through a pointer stored on the stack or in a register.

The activation record (also called a stack frame) is the data structure that the compiler allocates on the stack each time a procedure is called. A typical activation record contains, from bottom to top: the actual parameters passed by the caller, the return address (the address to which control should return when the procedure finishes), the saved frame pointer (the caller's base pointer, used to restore the stack after the call), the local variables of the procedure, the temporaries generated during computation, and the saved registers (registers that the callee must preserve). The exact layout varies by architecture and calling convention, but this general structure is nearly universal.

Section 4.13

Basic Blocks & Flow Graphs

Partitioning code into straight-line segments for analysis and optimisation

What Is a Basic Block?

A basic block is a maximal sequence of three-address instructions with the property that control enters at the first instruction and leaves at the last instruction, with no branches or branch targets in between. In other words, once the first instruction of a basic block is executed, every subsequent instruction in the block is executed exactly once, in order, without any possibility of jumping in from outside or jumping out to somewhere else (except at the very end). This property makes basic blocks the natural unit for many analyses and optimisations: within a basic block, the flow of control is completely predictable, so the compiler can reason about the values of variables, the liveness of temporaries, and the availability of expressions without worrying about the complications introduced by branches.

Rules for Identifying Leaders

To partition a sequence of three-address code into basic blocks, the compiler first identifies the leaders — the first instructions of each basic block. The rules for identifying leaders are:

  1. The first instruction in the intermediate code is a leader.
  2. Any instruction that is the target of a conditional or unconditional goto is a leader.
  3. Any instruction that immediately follows a conditional or unconditional goto is a leader.

Once the leaders have been identified, each basic block consists of a leader and all instructions up to (but not including) the next leader. This three-rule algorithm is straightforward to apply and produces a partition of the intermediate code into non-overlapping basic blocks that cover every instruction exactly once.

Flow Graphs

A flow graph (or control flow graph, CFG) is a directed graph in which each node represents a basic block and each edge represents a possible transfer of control between blocks. There is an edge from block B1 to block B2 if B2 can immediately follow B1 in the execution of the program — that is, if the last instruction of B1 is a goto that targets the first instruction of B2, or if B2 immediately follows B1 in the instruction sequence and B1 does not end with an unconditional goto. The flow graph is the fundamental data structure for control flow analysis, data flow analysis, and many code optimisations.

Worked Example: Factorial Program

Consider the following factorial function and its three-address code:

// Source
fact(n) {
    int f = 1;
    for (i = 2; i <= n; i++)
        f = f * i;
    return f;
}

// Three Address Code
 1:  f = 1
 2:  i = 2
 3:  if i > n goto 8
 4:  t1 = f * i
 5:  f = t1
 6:  i = i + 1
 7:  goto 3
 8:  return f

Applying the leader rules: Instruction 1 is a leader (first instruction). Instruction 3 is a leader (target of goto 7). Instruction 8 is a leader (target of the conditional goto at instruction 3, and also follows the unconditional goto at instruction 7). This gives us three basic blocks:

B1: Instructions 1–2 (f = 1; i = 2) — the initialisation block.
B2: Instructions 3–7 (if i > n goto 8; t1 = f*i; f = t1; i = i+1; goto 3) — the loop block, containing both the condition test and the loop body.
B3: Instruction 8 (return f) — the exit block.

Figure 4.5 — Control flow graph for the factorial program. B1 initialises, B2 contains the loop (condition + body), and B3 is the exit. Note the back edge from B2 to itself representing the loop.

The flow graph has three nodes (B1, B2, B3) and three edges: B1→B2 (fall-through after initialisation), B2→B2 (loop back when i ≤ n), and B2→B3 (exit when i > n). The edge B2→B2 is a back edge, which is the hallmark of a loop in the flow graph. Identifying back edges is the first step in loop detection and loop optimisation.

Section 4.14

Next-use Information

Knowing which values will be needed again — the key to intelligent register allocation

When generating code for a basic block, the code generator must decide at each instruction whether a variable's value should be kept in a register or stored back to memory. This decision depends on whether the variable will be used again within the block, and if so, when. Next-use information (also called next-use analysis or liveness within a block) tells the compiler, for each variable at each point in the program, the next instruction that will read that variable's value. If a variable has no next use (it will not be read again before being overwritten), its register can be safely reclaimed for another value. If a variable has a near next use, it should be kept in a register if possible.

The algorithm for computing next-use information processes each basic block backwards, from the last instruction to the first. This backwards scan is necessary because next-use is inherently a forward-looking property: to know when a variable is next used, we need to know what happens after the current instruction, not before. The algorithm maintains a table mapping each variable to its next use (instruction number) and whether it is live (will be used before being redefined). The steps are:

  1. Initialise: for all variables, mark them as "not live" with no next use.
  2. For each instruction i in the block, from last to first:
    (a) If instruction i is x = y op z: set the next-use information for instruction i as follows — for x: current next-use is "not live" (since x is being defined here); for y and z: their next-use is whatever is currently recorded (since they are being read here). Then update: mark x as "not live" with no next use, and mark y and z as "live" with next use at instruction i.
    (b) For any instruction that reads a variable v: record the current next-use of v for this instruction, then update v's next-use to this instruction and mark it live.
    (c) For any instruction that writes a variable v: record the current next-use of v for this instruction, then mark v as not live with no next use.

This algorithm is efficient — it makes a single backward pass through the basic block — and produces the complete next-use information needed by the code generator. The information is typically stored in a table alongside the intermediate code, with each instruction annotated with the next-use and liveness of every variable it references.

✦ Exam Tip

Next-use analysis is often tested as part of a larger code generation question. The key points to convey are: (1) it is computed per basic block, (2) it is computed backwards, (3) it records when each variable is next read and whether it is live, (4) it drives register allocation decisions — a register holding a dead variable (no next use) can be immediately reclaimed.

Section 4.15

A Simple Code Generator

Translating intermediate code to machine instructions, one statement at a time

The Algorithm

The simple code generator processes each three-address instruction in a basic block and generates target machine instructions using a small set of registers. The generator maintains a register descriptor (tracking which values are currently in each register) and an address descriptor (tracking where the current value of each variable can be found — in a register, in memory, or both). For each instruction x = y op z, the generator follows a systematic procedure:

  1. Get y into a register. Call getReg(y) to find or allocate a register Ry for y. If y is already in a register, use that register. If not, emit LD Ry, y. If all registers are full, choose a register to spill based on next-use information (spill the register whose value has the farthest next use or no next use).
  2. Perform the operation. If z is already in a register Rz, emit OP Ry, Ry, Rz. If z is a memory location and the instruction set supports memory operands, emit OP Ry, Ry, z. Otherwise, load z into a register first.
  3. Update descriptors. Record that x is now in register Ry, and update the register descriptor to reflect that Ry contains x. If y or z are not live after this instruction (no next use), update the descriptors to indicate that their registers are available.

After processing all instructions in the basic block, the generator must store any live variables that are only in registers (not yet in memory). This ensures that the values are preserved across block boundaries. The generator scans the register descriptor and emits ST x, Rx for every variable x that is live at the end of the block and whose current value is only in register Rx.

Worked Example

Generate target code for: result = (A - B) * (A - C) * (B - C). Assume three registers R0, R1, R2 are available. The three-address code is:

t1 = A - B
t2 = A - C
t3 = t1 * t2
t4 = B - C
t5 = t3 * t4
result = t5

Step-by-step code generation:

LD R1, B

This is 11 instructions. A cleverer register allocator might avoid reloading A and C by reordering the computation, but the simple generator processes instructions sequentially and does not reorder.

Section 4.16

Register Allocation & Assignment

The art of keeping the most valuable data in the fastest storage

Register allocation is the problem of deciding which program values should reside in registers at each point in the program. Register assignment is the related problem of deciding which specific register should hold each value. These two problems are closely intertwined and are among the most impactful optimisations a compiler can perform. The difference between good and poor register allocation can easily account for a factor of two or more in execution speed, because accessing a register is typically 10 to 100 times faster than accessing main memory.

The simplest approach to register allocation is local allocation within a basic block, using next-use information as described in the previous section. The code generator maintains a fixed pool of registers and, for each instruction, decides which value to keep and which to spill based on when each value is next needed. A value with no next use can be immediately evicted; a value with a far-future next use is a better candidate for spilling than one needed in the very next instruction. This greedy strategy works well within a single basic block but does not consider the global picture — a value that is used frequently across multiple blocks might be spilled and reloaded repeatedly, generating unnecessary traffic between registers and memory.

A more sophisticated approach is global register allocation, which considers the entire flow graph. The most widely used technique in production compilers is graph colouring. The idea is to construct an interference graph where each node represents a variable (or temporary) and each edge connects two variables that are simultaneously live at some point in the program — meaning they cannot share the same register. The register allocation problem then reduces to colouring the interference graph with k colours (where k is the number of available registers) such that no two adjacent nodes have the same colour. If the graph is k-colourable, each colour corresponds to a register, and the allocation is complete. If the graph is not k-colourable, some variables must be spilled to memory, and the process iterates.

The graph colouring approach is elegant but NP-complete in general. Practical implementations use heuristic algorithms such as the Chaitin-Briggs algorithm, which simplifies the graph by repeatedly removing nodes with fewer than k neighbours (since such nodes can always be coloured), spilling nodes when no simplification is possible, and then reconstructing the coloured graph. This heuristic works remarkably well in practice and is the foundation of register allocation in GCC, LLVM, and most other production compilers.

◆ Memory Anchor

Think of register allocation as seating guests at a dinner party with limited chairs (registers). Two guests who are "at the party at the same time" (simultaneously live) cannot share a chair. The interference graph records who conflicts with whom. Graph colouring assigns chairs so that no two conflicting guests sit in the same chair. If there aren't enough chairs, some guests must wait outside (be spilled to memory).

Section 4.17

DAG Representation of Basic Blocks

Trees that share — how directed acyclic graphs expose common subexpressions and enable optimisation

What Is a DAG?

A Directed Acyclic Graph (DAG) for a basic block is a directed graph in which each interior node represents an operator (or a statement), each leaf node represents an identifier (variable or constant), and the children of each interior node are the operands of the operator. The crucial property that distinguishes a DAG from a syntax tree is sharing: if the same computation (same operator applied to the same operands) appears multiple times in a basic block, the DAG represents it with a single node that has multiple parents, rather than creating duplicate subtrees. This natural sharing makes the DAG the ideal representation for detecting common subexpressions within a basic block.

The DAG also captures the relationships between definitions and uses of variables. If a variable is defined multiple times within a block, the DAG node for the most recent definition is the one that represents the variable's current value. This is implemented by attaching the variable name as a label to the node that computes its latest value, and removing that label from any earlier node. The DAG thus provides a complete picture of data flow within a basic block, making it possible to perform optimisations such as common subexpression elimination, dead code elimination, and constant folding in a single, unified framework.

Constructing a DAG — The Algorithm

To construct a DAG for a basic block, process each three-address instruction in order. For each instruction x = y op z:

  1. Find or create nodes for y and z. If y (or z) already has a node in the DAG (from a previous definition or as a leaf), use that node. Otherwise, create a new leaf node labelled y (or z).
  2. Check for common subexpression. Look for an existing node in the DAG with operator op whose left child is the node for y and whose right child is the node for z. If such a node exists, reuse it (this is the common subexpression elimination). If not, create a new interior node.
  3. Attach the result variable. Label the (new or reused) node with x. If x was previously labelled on another node, remove that label from the old node (since x's value has been overwritten).

Worked Example 1: ((a*b) + (c-d)*(a*b)) + b

This expression contains the common subexpression a*b, which appears twice. The DAG construction proceeds as follows:

3AC (unoptimised):
t1 = a * b
t2 = c - d
t3 = a * b       // common subexpression with t1
t4 = t2 * t3
t5 = t1 + t4
t6 = t5 + b

When we encounter instruction 3 (t3 = a * b), the DAG already has a node for a * b (created for instruction 1). We reuse this node and simply label it with t3 as well. The resulting DAG has 9 nodes instead of the 10 that a syntax tree would require, and the optimised 3AC derived from the DAG eliminates the redundant computation:

Optimised 3AC from DAG:
t1 = a * b
t2 = c - d
t3 = t2 * t1
t4 = t1 + t3
t5 = t4 + b
Figure 4.6 — DAG for ((a*b) + (c-d)*(a*b)) + b. The node for a*b is shared between the two subexpressions, shown with a red edge. The leaf node b connects to both the * node and the final + node.

Worked Example 2: (a - b) + c * (d / e)

This expression has no common subexpressions, so the DAG has the same structure as the syntax tree. The 3AC is:

t1 = a - b
t2 = d / e
t3 = c * t2
t4 = t1 + t3

Worked Example 3: Array Access Statements

Consider the following three-address statements inside a basic block:

t1 = 4 * i
t2 = a[t1]
t3 = 4 * i       // same as t1
t4 = b[t3]
t5 = t2 * t4
t6 = prod + t5
prod = t6

The common subexpression 4 * i appears in both instructions 1 and 3. The DAG construction reuses the node for 4 * i, and both array accesses a[t1] and b[t3] use the same index computation node. The optimised 3AC derived from this DAG is:

t1 = 4 * i
t2 = a[t1]
t3 = b[t1]       // reused t1 instead of recomputing 4*i
t4 = t2 * t3
t5 = prod + t4
prod = t5

Section 4.18

Generating Code from DAGs

Walking the graph to emit instructions — the final synthesis

Once a DAG has been constructed for a basic block, the code generator can traverse the DAG to produce target code. The traversal is essentially a post-order walk: for each interior node, generate code for its children first (ensuring their values are available in registers), then generate the instruction for the node itself. The DAG naturally eliminates common subexpressions (since shared nodes are visited only once), so the generated code is automatically more efficient than code generated from the original linear 3AC.

The algorithm for generating code from a DAG is as follows. First, perform a topological sort of the DAG nodes (this ensures that every node is processed after its children). Then, for each node in topological order:

  1. If the node is a leaf (a variable or constant), no code needs to be generated — the value is either already in a register or can be loaded on demand when it is first used as an operand.
  2. If the node is an interior node with operator op and children pointing to nodes whose values are in registers Ry and Rz, emit OP Rx, Ry, Rz where Rx is the register assigned to this node. If a child's value is not in a register, emit a LOAD instruction first.
  3. If the node has variable labels attached (meaning it defines one or more variables), emit STORE instructions for any variables that are live at the end of the block and not already in memory. Variables that are not live need not be stored — their values are dead and can be discarded.

The key advantage of generating code from a DAG (versus generating code directly from linear 3AC) is that the DAG has already performed common subexpression elimination and identified redundancies. The code generator simply walks the reduced graph, producing one instruction per interior node. For the DAG in Figure 4.6 (the expression ((a*b) + (c-d)*(a*b)) + b), the code generator would produce instructions for 5 interior nodes (the two multiplications, the subtraction, and the two additions) instead of the 6 instructions in the unoptimised 3AC, because the shared a*b node generates code only once.

In practice, the order in which the DAG nodes are evaluated affects register usage. If the code generator chooses a good evaluation order — one that minimises the number of values that must be live simultaneously — it can reduce register spilling. This is where the interplay between DAG traversal order and register allocation becomes important. Some compilers use a heuristic that evaluates the "heaviest" subtree first (the one requiring the most registers), ensuring that its register can be freed as soon as possible.

✦ Exam Tip — gencode() for 2D Array Iteration

A PYQ asks to "Apply the gencode() function to design the machine code for a given program fragment iterating over 2D arrays." For a loop like for(i=1;i<=10;i++) for(j=1;j<=10;j++) sum[i][j]=a[i][j]+b[i][j], the key steps are: (1) compute the address of each 2D array element using the formula base + ((i-1)*10 + (j-1))*w, (2) generate load-add-store sequences for each element, (3) recognise that the address computation for consecutive elements differs by a constant stride (which can be exploited by strength reduction optimisation, replacing multiplications with additions). Show the 3AC first, then the target code with register allocation.

Revision

Quick Revision Sheet

Everything you need, condensed for exam night

Three Address Code — Core Facts

Form: x = y op z (at most one operator per instruction).
Temporaries: Compiler-generated names (t1, t2, ...) for intermediate results.
Instruction types: Assignment, copy, unary, conditional jump, unconditional jump, indexed access, pointer, procedure call/return.
Implementations: Quadruples (4 fields, self-contained), Triples (3 fields, position-referenced), Indirect Triples (pointer table + pool).
Key difference: Quadruples are easy to optimise; Triples save space but break on reordering; Indirect Triples combine both advantages.

Backpatching — Core Facts

Purpose: Fill in jump targets that are unknown at emission time.
Three functions: makelist(i) — create list with one entry; merge(p1,p2) — concatenate lists; backpatch(p,label) — fill in target for all entries in list p.
Attributes: Each boolean expression has .truelist and .falselist.
For if-then-else: Backpatch true-list to S1 start, false-list to S2 start.
For while-do: Backpatch true-list to body start, backpatch body's nextlist back to condition start, use false-list as while's nextlist.

Basic Blocks & Flow Graphs — Core Facts

Basic block: Maximal sequence with single entry, single exit, no branches in between.
Leader rules: (1) First instruction, (2) Target of any goto, (3) Instruction following any goto.
Flow graph: Nodes = basic blocks, Edges = control flow between blocks.
Back edge: Edge to an ancestor in a DFS → indicates a loop.

DAG — Core Facts

DAG vs Syntax Tree: DAG shares common subexpression nodes; tree duplicates them.
Construction: For each instruction, find/create operand nodes, check for existing operator node (CSE), label result.
Benefits: Common subexpression elimination, dead code detection, constant folding.
Code from DAG: Post-order traversal, one instruction per interior node.

Code Generation — Core Facts

Design issues: Instruction selection, register allocation, instruction ordering, evaluation order.
Simple algorithm: For each 3AC instruction: get operands into registers, perform operation, update descriptors, store live results.
Register descriptors: Track what's in each register.
Address descriptors: Track where each variable's value is.
Next-use: Computed backwards per basic block; drives register spilling decisions.
Graph colouring: Global register allocation via interference graph; NP-complete, solved by heuristics (Chaitin-Briggs).

Most Commonly Confused Points

1. Triples vs Indirect Triples: Triples use row positions as references and are fragile under reordering. Indirect triples add a pointer table that decouples ordering from the instruction pool, making reordering safe.

2. Backpatching vs Forward references: Backpatching handles forward jumps (jumps to labels that haven't been defined yet). It does not handle backward jumps, which are resolved immediately since the target is already known.

3. Basic block vs Extended basic block: A basic block has a single entry and single exit. An extended basic block allows multiple entries (from different predecessors) but maintains a single exit — used in some instruction scheduling algorithms.

4. DAG for a basic block vs DAG for an expression: A DAG for a basic block handles multiple assignments and can detect when a variable is redefined (by relabelling nodes). A DAG for a single expression is simpler — just a shared tree.

5. Register allocation vs Register assignment: Allocation decides which values get registers; assignment decides which specific register each value gets. Graph colouring does both simultaneously.

How to Structure a 10-Mark Answer on Backpatching

Para 1: Define backpatching and explain the problem it solves (forward jumps with unknown targets in single-pass code generation).

Para 2: Define the three functions: makelist, merge, backpatch. Explain what each does and what data structures they use.

Para 3: Explain the truelist and falselist attributes of boolean expressions.

Para 4: Show the SDT rules for E → E1 || E2 and E → E1 && E2. Explain how truelist and falselist are merged and backpatched.

Para 5: Show the SDT for if-then-else: how E's truelist is backpatched to S1, E's falselist to S2, and S1's nextlist jumps over S2.

Para 6: Show the SDT for while-do: how the loop back edge is created by backpatching S1's nextlist to the condition start.

Para 7: Draw a diagram showing the control flow for if-then-else and while-do with labelled edges.

Para 8: Conclude with a small worked example (e.g., if(a).

How to Draw DAGs Quickly in Exams

Step 1: Write out the 3AC first. Identify all leaf nodes (variables and constants) and draw them in a row at the top.

Step 2: Process instructions in order. For each t = a op b, draw a node labelled op and connect it to the nodes for a and b.

Step 3: Before creating a new node, check if an identical node already exists (same operator, same children). If yes, reuse it — draw an extra edge from the existing node instead of creating a new one.

Step 4: Label each node with the temporary(s) or variable(s) it defines. If a variable is redefined, remove its label from the old node and add it to the new one.

Step 5: Draw edges from children to parents (top to bottom). Shared nodes will have multiple outgoing edges — this is the visual signature of common subexpression elimination.

Essential labels: Every node must be labelled with its operator (interior) or variable/constant (leaf). Annotations like "t1, t3" on shared nodes show which temporaries share the computation.
