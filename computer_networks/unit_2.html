Section 2.1

Introduction to the Link Layer

Before a single IP packet traverses the internet, before a TCP segment is assembled, before any of the grand architectures of the network layer are invoked, there is a far more local problem that must be solved: how does a packet actually get from one node to the next node along its path? The network layer operates in the realm of end-to-end communication—a packet born in Mumbai must reach a server in Bangalore, and the network layer reasons about this journey as a whole. But that journey is not a single leap; it is a chain of individual hops, each hop crossing a single physical link. The link layer is the protocol layer responsible for those individual hops. It is the layer that governs communication across a single link—a single Ethernet segment, a single WiFi channel, a single point-to-point serial line.

This distinction between end-to-end and hop-by-hop is the defining conceptual boundary of the link layer. The network layer says "get this packet from source to destination." The link layer says "get this frame from this node to the immediately next node." Every packet that travels across the internet is encapsulated within a link-layer frame at every hop along its path. The frame is transmitted, received, stripped of its link-layer headers, and then re-encapsulated in a new frame for the next link. The network layer packet remains largely intact through this process; the link-layer framing changes at every hop. This is why the link layer is sometimes called the "hop-to-hop" layer, as opposed to the "end-to-end" transport layer and the "source-to-destination" network layer.

Think of the link layer as a local courier service. The network layer is the logistics company that plans the route from warehouse to warehouse. The link layer is the van that drives the package from one warehouse to the next. The van does not need to know the package's final destination; it only needs to know where the next warehouse is. At each warehouse, the package is unloaded from one van and loaded onto another van for the next leg of the journey.

The entities that the link layer connects are called nodes (hosts, routers, switches, access points) and the communication medium that connects them is called a link. A link can be a wired Ethernet cable, a fiber optic strand, or a wireless radio channel. The data unit at the link layer is called a frame. When the network layer passes a datagram down to the link layer, the link layer encapsulates it within a frame by adding a header and (often) a trailer, then transmits the frame across the link.

Services Provided by the Link Layer

The link layer provides several fundamental services to the network layer. Not every link-layer protocol provides every service; the specific combination depends on the link-layer technology. But the conceptual catalog of services is as follows:

Framing. Almost all link-layer protocols encapsulate the network-layer datagram within a frame by adding a header and a trailer. The header typically contains addresses and control information; the trailer often contains error-detection bits. The framing service defines where the frame begins and ends, allowing the receiver to extract the datagram from the received bit stream. This is arguably the most essential service—without framing, the receiver would have no way of knowing which bits constitute a single transmission unit.

Link Access (Medium Access Control). When multiple nodes share a single broadcast link (as in WiFi or traditional Ethernet), a protocol is needed to coordinate which node transmits at any given time. This coordination is the medium access control (MAC) protocol. If two nodes transmit simultaneously on a shared medium, their signals collide and both transmissions are corrupted. The MAC protocol prevents, minimizes, or recovers from such collisions. Point-to-point links with a single sender and a single receiver do not need MAC protocols in the traditional sense, but shared media absolutely require them. This is why the entire subfield of multiple access protocols exists—and why Section 2.3 of this document is as large as it is.

Reliable Delivery. Some link-layer protocols provide reliable delivery—guaranteeing that each frame is delivered without error and in the correct order. This is typically achieved through acknowledgments and retransmissions, similar to TCP at the transport layer. Reliable delivery at the link layer is most commonly used over links with high error rates (such as wireless links), where local retransmission is far more efficient than relying on the transport layer's end-to-end retransmissions. Wired links, which have very low error rates, typically do not use link-layer reliable delivery because the overhead is not justified.

Error Detection and Correction. Bit errors can occur during transmission due to signal attenuation, electromagnetic interference, or noise. The link layer includes error-detection bits in the frame trailer, allowing the receiver to detect (and in some cases correct) these errors. The most common error-detection technique is the Cyclic Redundancy Check (CRC), which detects errors with very high probability. Forward error correction (FEC) goes one step further, allowing the receiver to correct certain errors without retransmission. Error detection is nearly universal in link-layer protocols; error correction is used in specific contexts like wireless communication.

Flow Control. Flow control prevents a fast sender from overwhelming a slow receiver. If a transmitter sends frames faster than the receiver can process them, frames may be dropped. Flow control mechanisms—such as feedback signals or rate limiting—allow the receiver to pace the sender. This is conceptually similar to TCP flow control but operates at the link level.

Where is the link layer implemented? Unlike the network and transport layers, which are implemented entirely in software (within the operating system's network stack), the link layer is implemented in a combination of hardware and software. The link layer's core functions—framing, error detection, and medium access control—are typically implemented in the network interface card (NIC), also called a network adapter. The NIC contains a dedicated controller chip (such as an Ethernet controller) that handles the bit-level details of frame transmission and reception. The NIC firmware handles lower-level link-layer logic, while the operating system's device driver provides the software interface between the NIC and the network stack. This split implementation means that the link layer has a distinctly different character from the layers above it: it is partly hardware, partly firmware, and partly software.

Q: What is the difference between the network layer and the link layer?

The network layer provides end-to-end logical communication between source and destination hosts, routing packets across multiple links. The link layer provides hop-by-hop communication, moving a frame across a single link between two adjacent nodes. The network layer deals with IP addresses and routing; the link layer deals with MAC addresses and frame transmission on a specific link.

Q: Why is the link layer implemented partly in hardware?

Because the link layer must process bits at wire speed—it must be fast enough to handle incoming and outgoing frames at the full rate of the physical link. Software processing would be too slow for modern link speeds (1 Gbps, 10 Gbps). The NIC hardware handles time-critical operations like framing, CRC computation, and medium access, while the OS driver handles higher-level configuration and interface to the network stack.

Q: Does every link-layer protocol provide reliable delivery?

No. Reliable delivery (using acknowledgments and retransmissions) is optional. It is commonly used over high-error-rate links like WiFi (802.11 uses link-layer ACKs). Wired Ethernet does not provide link-layer reliable delivery; it relies on error detection (CRC) and discards corrupt frames, leaving retransmission to higher layers (TCP).

Section 2.2

Error Detection & Correction

No physical communication channel is perfect. Electrical noise, signal degradation, interference from nearby devices, clock synchronization errors, and a thousand other physical phenomena conspire to flip bits during transmission. A 0 sent may arrive as a 1; a 1 may arrive as a 0. If the receiver naively accepts every bit as correct, the consequences can range from minor data corruption to catastrophic system failure. Error detection and correction are the mechanisms by which the receiver can determine whether the received data is intact and, in some cases, recover the correct data without retransmission.

The fundamental tradeoff in error detection and correction is between overhead and capability. A single parity bit adds minimal overhead but can detect only an odd number of bit errors. A CRC with 32 check bits adds more overhead but can detect virtually all burst errors up to 32 bits long and most longer burst errors. Hamming codes and other forward error correction (FEC) schemes add even more redundancy but can both detect and correct errors without requiring the sender to retransmit. The choice of technique depends on the error characteristics of the channel, the cost of retransmission, and the acceptable level of residual error rate.

Parity Checking

Parity checking is the simplest error detection technique. A single bit, called the parity bit, is appended to the data. The parity bit is set so that the total number of 1-bits in the data plus the parity bit is either even (for even parity) or odd (for odd parity).

In even parity, the parity bit is chosen such that the total number of 1s in (data + parity bit) is an even number. For example, if the data is 1011001, there are four 1s (which is already even), so the even parity bit is 0, and the transmitted codeword is 10110010. If the data were 1011011 (five 1s, odd), the even parity bit would be 1, making the total six (even), and the transmitted codeword would be 10110111.

In odd parity, the parity bit is chosen so that the total number of 1s is odd. For data 1011001 (four 1s, even), the odd parity bit is 1, giving 10110011.

The receiver counts the 1s in the received codeword. If the count violates the expected parity, an error is detected. Even parity is more commonly used in practice.

Limitation of single parity bit: A single parity bit can detect any odd number of bit errors (1, 3, 5, ...) but cannot detect any even number of bit errors (2, 4, 6, ...). If two bits are flipped, the parity is preserved, and the error goes undetected. This makes single parity checking quite weak for channels where multi-bit errors are common (such as burst error channels). However, it is useful for detecting single-bit errors in memory systems and simple serial communication.

Two-dimensional parity (also called matrix parity or block parity) extends the idea to detect (and sometimes correct) more errors. The data is arranged in a matrix, and parity bits are computed for each row and each column. A single-bit error causes both its row parity and column parity to fail, uniquely identifying the bit's position—which means the error can be corrected. Two-dimensional parity can detect all 1-bit, 2-bit, and 3-bit errors, and most 4-bit errors.

Cyclic Redundancy Check (CRC)

The Cyclic Redundancy Check is the workhorse of error detection in computer networks. It is used in Ethernet, WiFi, USB, Bluetooth, and virtually every other link-layer protocol that requires robust error detection. CRC is based on polynomial arithmetic over GF(2)—the field of two elements, where addition is XOR and multiplication is AND. While the mathematics behind CRC is deep and elegant, the practical computation is straightforward: it is binary division using XOR, and the remainder of this division is the CRC value that gets appended to the data.

The conceptual motivation for CRC comes from a simple observation: if we treat the data as a polynomial (where each bit is a coefficient), and we divide this polynomial by a fixed generator polynomial, the remainder uniquely depends on the data. If even a single bit of the data changes, the remainder will almost certainly change. A well-chosen generator polynomial ensures that all common error patterns (single-bit errors, double-bit errors, burst errors) produce a non-zero remainder at the receiver.

Here is how CRC works, stated formally:

  1. The sender and receiver agree on a generator polynomial G(x) of degree r. This polynomial is typically written in the form xr + ... + 1, and its binary representation has r+1 bits (the coefficients of the polynomial).
  2. Let the data to be transmitted be D, represented as a polynomial of degree d. In binary, D is a sequence of d+1 bits.
  3. The sender appends r zero bits to the right of D, creating D × 2r. In polynomial terms, this is D(x) × xr.
  4. The sender divides D × 2r by G using binary division (XOR-based). The remainder R has at most r bits.
  5. The sender transmits the codeword: D followed by R. In polynomial terms, this is D(x) × xr + R(x).
  6. The receiver divides the received codeword by G. If the remainder is zero, the data is accepted as error-free. If the remainder is non-zero, an error is detected.

The mathematical elegance of CRC lies in a property of polynomial division: if T(x) = D(x)×xr + R(x), then T(x) is exactly divisible by G(x). This is because R(x) is the remainder of dividing D(x)×xr by G(x), which means D(x)×xr = Q(x)×G(x) + R(x) for some quotient Q(x). Therefore, T(x) = Q(x)×G(x) + R(x) + R(x). In GF(2), addition is XOR, so R(x) + R(x) = 0. Thus T(x) = Q(x)×G(x), which is perfectly divisible by G(x). Any error introduced during transmission changes T(x) to T(x) + E(x), where E(x) is the error polynomial. The receiver computes [T(x) + E(x)] / G(x). If E(x) is not itself divisible by G(x), the remainder will be non-zero, and the error is detected.

Think of CRC like a highly sensitive fingerprint for your data. The generator polynomial is the fingerprinting algorithm. The sender computes the fingerprint (remainder) of the data and sends both the data and the fingerprint. The receiver recomputes the fingerprint of the received data. If it matches the received fingerprint, the data is intact. Even a tiny smudge (a single bit flip) on the data will produce a completely different fingerprint, alerting the receiver to the error.

Step-by-Step Binary Division for CRC (The XOR Method)

The binary division used in CRC is not the standard decimal-like binary division you might expect. It is polynomial division over GF(2), where subtraction is identical to addition, and both are performed using the XOR operation. Here are the rules:

  1. Append zeros: Append r zeros to the data, where r is the degree of the generator polynomial (which is one less than the number of bits in the generator).
  2. Align and XOR: Align the generator polynomial with the leftmost 1 of the appended data. Perform a bitwise XOR. This is equivalent to "subtracting" the generator from the data.
  3. Bring down: Bring down the next bit from the data to fill the gap, creating a new intermediate value.
  4. Repeat: If the leftmost bit of the intermediate value is 1, align the generator and XOR. If the leftmost bit is 0, align an all-zero string (of the same length as the generator) and XOR. (Equivalently, you can simply skip the step and bring down another bit until the leftmost bit is 1 again, but the formal algorithm always XORs with either the generator or zeros).
  5. Remainder: When you run out of bits to bring down, the remaining bits (which will be exactly r bits long) are the CRC remainder.

Common Student Confusion: Students often try to use regular binary subtraction (with borrows) instead of XOR. This is wrong. In CRC, every column is independent: 0-0=0, 1-0=1, 0-1=1 (no borrow!), 1-1=0. This is exactly the XOR truth table. If you find yourself "borrowing" from the left, you are doing it incorrectly.

Requirements of a Good Generator Polynomial: The International Telecommunication Union (ITU) and IEEE have standardized several generator polynomials. A good generator polynomial must be able to detect: (1) All single-bit errors. (2) All double-bit errors (if the polynomial contains x+1 as a factor). (3) Any odd number of errors (if the polynomial contains x+1 as a factor). (4) All burst errors of length less than or equal to the degree of the polynomial. (5) Most burst errors of length greater than the degree of the polynomial (with probability 1 - 2-r).

Part B: Single Bit Parity Correction

Single bit parity can detect a single bit error, but it cannot correct it. To correct a single bit error, we need more redundant bits, such as in Hamming Code. With single parity, if the parity fails, we know an odd number of bits flipped, but we do not know which bit flipped, so correction is impossible.

Internet Checksum

The Internet Checksum is another error detection method, used primarily at the network and transport layers (IP, TCP, UDP) rather than the link layer, but it is frequently asked in comparisons with CRC. Unlike CRC, which uses polynomial division, the checksum uses one's complement arithmetic.

The sender divides the data into 16-bit segments. These segments are added together using one's complement arithmetic. If a carry is produced (i.e., the sum exceeds 16 bits), the carry is wrapped around and added back to the least significant bits. The final 16-bit sum is then complemented (all bits flipped) to produce the checksum value, which is sent along with the data.

The receiver performs the same addition on all segments including the checksum. If no errors occurred, the result of adding all segments and wrapping the carry should be all 1s (FFFF in hex). The complement of this result is all 0s, indicating no error. If the result is not all 1s, an error is detected.

CRC vs Checksum: CRC is far more robust than the Internet Checksum. CRC can detect all burst errors up to the degree of the polynomial and most longer burst errors. The checksum is weak against certain error patterns—for example, if one bit is flipped upward in one segment and the same bit is flipped downward in another segment, the checksum will not detect it. CRC is implemented in hardware (NIC) for speed; checksum is implemented in software and is cheaper but weaker.

Error Detection vs. Error Correction

Error detection and error correction represent two fundamentally different strategies for dealing with transmission errors, and the choice between them depends on the nature of the channel and the cost of retransmission.

Error Detection mechanisms (like parity, CRC, checksum) only determine whether an error has occurred. They do not identify which bit was corrupted. When an error is detected, the standard response is to discard the frame and request retransmission (using an Automatic Repeat Request, or ARQ, protocol). This approach is efficient on channels with low error rates, where retransmissions are rare and the overhead of sending redundant bits for correction is not justified. Most wired links (Ethernet) use pure error detection.

Error Correction mechanisms (Forward Error Correction, or FEC, like Hamming codes, Reed-Solomon codes) include enough redundant information to not only detect an error but to locate and correct it without retransmission. FEC requires more redundant bits than pure detection. For example, a single parity bit can detect a single-bit error, but you need multiple check bits (as in Hamming code) to correct it. FEC is essential on channels where retransmission is extremely expensive or impossible—such as satellite links with long propagation delays, or simplex (one-way) communication like broadcast television.

Hamming Code

Hamming codes are a family of linear error-correcting codes invented by Richard Hamming in 1950. They can detect up to two-bit errors and correct up to one-bit errors. The central idea is to place check bits at positions that are powers of 2 (positions 1, 2, 4, 8, 16...), while data bits occupy all other positions.

For a Hamming code with r check bits and m data bits, the fundamental relationship is: 2r ≥ m + r + 1. This equation ensures there are enough check bits to cover all possible single-bit error positions (including the check bits themselves) plus the "no error" state.

Each check bit is responsible for checking the parity of a specific group of bits. Check bit at position 2k checks all bit positions whose binary representation has a 1 in the k-th position from the right. For example, check bit 1 (position 001) checks positions 1, 3, 5, 7, 9... Check bit 2 (position 010) checks positions 2, 3, 6, 7, 10... Check bit 4 (position 100) checks positions 4, 5, 6, 7, 12...

When a codeword is received, the receiver recalculates the parity for each check bit group. If all parities are correct, no error occurred. If one or more parities fail, the failing check bit positions sum to the position of the erroneous bit. This sum is called the syndrome. For example, if check bits 1 and 4 fail (but 2 passes), the error is at position 1 + 4 = 5. You flip that bit to correct the error.

The error is at position 7.

The bit at position 7 is currently 1. Flipping it gives 0.

Corrected codeword: 1011010

Q: Why is CRC better than simple parity for network communication?

Network errors often occur in bursts (multiple consecutive bits corrupted). Simple parity cannot detect even-numbered bit errors and cannot detect burst errors at all. CRC, through polynomial division, can detect all single-bit errors, all double-bit errors, all odd-numbered errors (if x+1 is a factor), and all burst errors of length ≤ r (degree of polynomial). It is specifically designed for the burst-error nature of real network channels.

Q: What happens if a CRC remainder is zero at the receiver?

It means the received codeword is perfectly divisible by the generator polynomial. Assuming the generator polynomial is well-chosen, this indicates that no detectable error has occurred, and the receiver accepts the data by stripping off the CRC bits.

Multiple Access Links & Protocols

There are two fundamentally different types of network links: point-to-point links and broadcast links. A point-to-point link has exactly one sender and one receiver—a dedicated lane between two endpoints. A broadcast link (or multi-access link) is shared among multiple nodes; when one node transmits, the signal propagates to all other nodes on the link. Ethernet LANs, WiFi networks, and satellite uplinks are all examples of broadcast links.

The broadcast link creates a central coordination problem: if two nodes transmit frames at the same time, their signals overlap and interfere with each other. This interference is called a collision. Neither frame can be successfully received; both are garbled. To make a broadcast link functional, we need a protocol to coordinate access to the shared channel. These are Multiple Access Protocols.

The ideal multiple access protocol for a broadcast channel of rate R bps would achieve two properties: (1) When only one node has data to send, it should be able to transmit at the full rate R. (2) When M nodes have data to send, each should be able to transmit at an average rate of R/M. No single protocol perfectly achieves this under all conditions, and the history of multiple access protocols is a tale of different engineering tradeoffs.

These protocols are broadly classified into three categories: Channel Partitioning Protocols, which divide the channel into pieces and assign them exclusively; Random Access Protocols, which allow collisions and provide mechanisms to recover from them; and Taking-Turns Protocols, which enforce a strict sequential order of transmission.

Channel Partitioning Protocols (TDMA, FDMA)

Channel partitioning protocols divide the channel resource (time or frequency) into smaller, dedicated slots and assign each slot to a specific node. This completely eliminates collisions by design, because no two nodes ever share the same channel resource.

TDMA (Time Division Multiple Access): Time is divided into frames, and each frame is divided into N time slots. Each node is assigned a specific time slot. Node 1 can only transmit during slot 1, node 2 during slot 2, and so on. If a node has no data to send during its slot, the slot remains idle—wasted channel capacity.

FDMA (Frequency Division Multiple Access): The channel's total frequency band is divided into N smaller frequency bands. Each node is assigned a dedicated frequency band. Again, if a node has nothing to send, its frequency band sits idle.

Exam tip: The main advantage of TDMA/FDMA is the complete elimination of collisions. The main disadvantage is the waste of bandwidth when nodes are silent. A node with a lot of data cannot use the idle slots of other nodes.

Random Access Protocols: ALOHA

Random access protocols take the opposite approach to channel partitioning. Nodes are not assigned dedicated resources. Instead, any node can transmit whenever it has data. If collisions occur, the protocol provides a mechanism to detect the collision and retransmit the frame after a random delay. The randomness is crucial: if two nodes collide and both wait the exact same amount of time before retransmitting, they will collide again. Randomizing the waiting time breaks this destructive synchronization.

Pure ALOHA was the earliest random access protocol, developed at the University of Hawaii in the early 1970s for packet radio networks. In Pure ALOHA, the rule is breathtakingly simple: when a node has a frame to send, it just sends it. If the frame collides with another transmission, the sender waits for a random amount of time and retransmits. The node does not check whether the channel is busy before transmitting.

The throughput of Pure ALOHA can be analyzed mathematically. Let the frame transmission time be T. A frame will not suffer a collision only if no other frame begins transmission in the vulnerable period of 2T (from T before the start of the frame to T after the start). If the total traffic on the channel follows a Poisson distribution with an average load of G frames per frame time, the probability that zero frames are generated during the vulnerable period (2T) is e-2G. Therefore, the throughput S = G × e-2G.

The maximum throughput of Pure ALOHA occurs when G = 0.5, yielding S = 0.5 × e-1 ≈ 0.184. This means the channel can only be utilized about 18.4% of the time at best—the rest is lost to collisions or idle time.

Slotted ALOHA improves upon Pure ALOHA by dividing time into discrete slots, each equal to the frame transmission time T. Nodes are synchronized so that a frame can only be transmitted at the beginning of a slot. This halves the vulnerable period from 2T to T, because a collision can only occur if another frame is sent in the exact same slot. The probability of zero frames in a single slot is e-G, so the throughput is S = G × e-G. The maximum throughput occurs at G = 1, giving S = e-1 ≈ 0.368. Slotted ALOHA doubles the maximum efficiency of Pure ALOHA, but it requires time synchronization across all nodes.

Carrier Sense Multiple Access (CSMA/CD & CSMA/CA)

The ALOHA protocols are remarkably inefficient because nodes transmit without any regard for what other nodes are doing. A natural improvement is to "listen before you speak"—check if the channel is currently busy before transmitting. This is the core idea of Carrier Sense Multiple Access (CSMA).

In CSMA, a node with a frame to send first listens to the channel. If the channel is idle, the node transmits the entire frame. If the channel is busy, the node waits until the channel becomes idle and then transmits. This dramatically reduces collisions compared to ALOHA, but it does not eliminate them entirely. Why? Because of propagation delay.

Even at the speed of light, a signal takes time to travel from one end of the medium to the other. Suppose node A begins transmitting at one end of a cable. The signal from A has not yet reached node B at the other end. Node B senses the channel, hears silence (because A's signal hasn't arrived yet), and begins transmitting. A collision occurs. The longer the propagation delay, the more vulnerable CSMA is to collisions.

CSMA/CD (Collision Detection): Used in wired Ethernet. Nodes not only listen before transmitting but also monitor the channel while transmitting. If a node detects that another signal is interfering with its own, it immediately stops transmitting and sends a short jamming signal to notify all other nodes of the collision. This saves time because the node doesn't continue sending a full frame that is already garbled. After a collision, the node waits using the binary exponential backoff algorithm: after the k-th collision, the node chooses a random delay from {0, 1, 2, ..., 2k-1} × 512 bit times, up to a maximum of k=10.

CSMA/CA (Collision Avoidance): Used in WiFi (802.11). Collision detection is impractical in wireless because the node's own transmission drowns out any received signal, making it hard to detect a collision. Instead, CSMA/CA tries to avoid collisions. It uses a Request to Send (RTS) and Clear to Send (CTS) handshake. The sender broadcasts an RTS, the receiver replies with a CTS, and then the sender transmits the data. The RTS/CTS frames contain a duration field that tells all other nodes how long to wait (the Network Allocation Vector, or NAV), effectively reserving the channel.

Taking-Turns Protocols (Polling, Token Passing)

Taking-turns protocols represent a middle ground between the rigid, wasteful division of channel partitioning and the chaotic collisions of random access. They enforce a strict sequence: nodes take turns transmitting, eliminating collisions while allowing a node with data to use the full channel capacity during its turn.

Polling: One node is designated as the master (or controller). The master polls each slave node in a round-robin fashion, asking "Do you have anything to send?" If the slave has data, it transmits; if not, the master moves on to the next slave. Polling eliminates collisions and is fair. However, it introduces latency (a node must wait to be polled), and it has a single point of failure: if the master node crashes, the entire channel goes down. It also consumes some bandwidth for the polling messages themselves.

Token Passing: A special frame called a token circulates among the nodes in a logical ring. When a node receives the token, it is allowed to transmit data. If it has nothing to send, it passes the token to the next node. If it has data, it attaches the data to the token (or sends a data frame and releases the token afterward), and the frame circulates to the destination. Token passing is decentralized (no master node), but it has its own problems: if the token is lost (due to a node failure), the entire ring stops. A complex token recovery protocol is required to regenerate the lost token.

Section 2.4

Switched Local Area Networks & Ethernet

In the early days of networking, all devices on a LAN shared a single physical cable—a true broadcast medium where every frame was heard by every node. This architecture required CSMA/CD and created a large collision domain. Modern LANs have almost entirely moved away from shared media to switched architectures, where devices connect to a central link-layer switch. The switch isolates traffic, creates separate collision domains for each port, and selectively forwards frames only to their intended destination. This section covers the addressing that makes this possible, the Ethernet protocol that dominates wired LANs, and the switches that tie it all together.

Link-Layer Addressing: MAC Addresses

While IP addresses identify the network location of a host (the "who" and "where" at the network layer), MAC addresses (Media Access Control addresses) identify the specific network interface hardware at the link layer. A MAC address is a 48-bit (6-byte) address, typically written in hexadecimal notation as six pairs of digits separated by colons or hyphens (e.g., 1A:2B:3C:4D:5E:6F).

MAC addresses are assigned by the manufacturer of the NIC and are intended to be globally unique and permanent. The first 24 bits (3 bytes) are the Organizationally Unique Identifier (OUI), assigned by IEEE to the manufacturer. The last 24 bits are assigned by the manufacturer to each individual NIC. When a frame is sent from one interface to another on the same LAN, it is identified by its MAC address, not its IP address. The IP address is used to get the packet to the correct network; the MAC address is used to get the frame to the correct interface on that network.

Think of the IP address as the postal address of a building (it can change if you move), and the MAC address as the Social Security Number of a person (it is permanent and tied to the individual hardware). A letter is routed to the building using the postal address, but inside the mailroom, the SSN ensures it reaches the exact person.

Address Resolution Protocol (ARP)

Every host on a LAN has both an IP address and a MAC address. But when a host needs to send a frame to another host on the same LAN, it must know the destination's MAC address—the link-layer hardware only understands MAC addresses. How does a host map a known IP address to an unknown MAC address? This is the function of the Address Resolution Protocol (ARP).

Each host maintains an ARP table (or ARP cache) in its memory, which maps IP addresses to MAC addresses. Each entry has a TTL (Time To Live), usually around 20 minutes, after which the entry is discarded to allow for changes (like a device being replaced).

When Host A wants to send a datagram to Host B on the same subnet, A checks its ARP table. If B's IP-MAC mapping is present, A simply encapsulates the IP datagram in a frame destined for B's MAC address. If the mapping is absent, A uses ARP to find it:

  1. Host A constructs an ARP query packet, which contains A's own IP and MAC, and the target IP address (B's IP). The target MAC is left blank or set to 0.
  2. This ARP packet is encapsulated in a broadcast Ethernet frame (destination MAC = FF:FF:FF:FF:FF:FF). Every adapter on the LAN receives and processes this frame.
  3. All hosts on the LAN examine the ARP query. If a host's IP does not match the target IP, it ignores the query. Host B recognizes its own IP.
  4. Host B responds by sending an ARP response packet directly back to Host A (unicast), containing B's MAC address.
  5. Host A receives the response, updates its ARP table with B's mapping, and can now send the original datagram.

RARP (Reverse ARP): Historically, RARP was used by diskless workstations that knew their MAC address but did not know their IP address. A device would broadcast a RARP request containing its MAC, and a RARP server would reply with the IP address assigned to that MAC. RARP is now obsolete and has been replaced by BOOTP and DHCP, which are far more flexible.

Proxy ARP: Sometimes a router answers ARP queries on behalf of another device. For example, if a host on one subnet tries to reach a host on a different subnet (but doesn't realize it's on a different subnet because of a non-standard subnet mask), it will send an ARP query for an IP that is not on the local link. The router, acting as a Proxy ARP agent, responds with its own MAC address. The sender then sends frames to the router, which forwards them to the actual destination. This makes the remote network appear as if it is part of the local link.

Link Layer Switches

A link-layer switch is a device that receives incoming frames, examines their destination MAC address, and forwards them selectively to the appropriate output port. Unlike a hub (which mindlessly repeats every frame to every port), a switch learns which devices are on which ports and creates a dedicated path for traffic. This is the fundamental architectural shift that made modern Ethernet so powerful.

Forwarding and Filtering: Filtering is the switch's ability to determine that a frame should NOT be forwarded to a particular port. Forwarding is determining which port a frame SHOULD go to. Both functions rely on the switch table (also called a forwarding table or MAC address table). The switch table maps MAC addresses to the switch port through which that MAC address can be reached.

When a frame arrives at a switch, the switch reads the source MAC address and records which port the frame came from—this is how the switch learns. It then looks up the destination MAC address in its table. There are three possible scenarios:

  1. Found, same port: The destination is on the same port as the source. The frame is filtered (dropped), because the destination already received it on the shared segment.
  2. Found, different port: The frame is forwarded only to the specific port listed in the table.
  3. Not found: The switch does not know where the destination is. It floods the frame—forwarding it to all ports except the one it arrived on. This ensures the frame reaches its destination even if the switch hasn't learned that MAC address yet.

Self-Learning: Switches do not require manual configuration of their tables. They build their tables automatically through a beautifully simple process. Every time a frame arrives, the switch records the source MAC address and the incoming port in its table, along with a timestamp. If an entry is not refreshed within a certain timeout period (typically a few minutes), it is removed. This allows the switch to adapt when devices are moved or disconnected.

Problems with Switched LANs & Solutions

While switches dramatically improved LAN performance, they introduced new architectural problems that had to be solved.

1. Broadcast Storms: Switches forward broadcast frames (like ARP requests) to all ports. In a large switched network, if a device malfunctions and starts generating massive amounts of broadcast traffic, this traffic propagates to every switch port, consuming all bandwidth and paralyzing the network. Routers naturally block broadcasts; switches do not. The solution is VLANs (Virtual Local Area Networks), which logically divide a single physical switch into multiple isolated broadcast domains.

2. Switching Loops: In enterprise networks, switches are often connected with redundant links to ensure fault tolerance. If Switch A is connected to Switch B via two cables, and both switches receive a broadcast frame, they will flood it out all ports—including the redundant link back to the other switch. This creates an infinite loop where broadcast frames circulate endlessly, creating a broadcast storm that crashes the network. The solution is the Spanning Tree Protocol (STP), which logically blocks redundant paths to create a loop-free tree topology, while keeping the blocked paths available as backups if the primary path fails.

3. Security: A switch provides no inherent security against a malicious host. An attacker can easily flood a switch with fake source MAC addresses until the switch's MAC table is full (MAC flooding attack), forcing the switch to behave like a hub and flood all traffic to all ports, allowing the attacker to sniff network traffic. Solutions include port security (limiting the number of MAC addresses per port) and DHCP snooping.

Network Connecting Devices: Gateway vs Router

A Router operates at the Network Layer (Layer 3) and routes packets between different networks based on IP addresses. It is the most common inter-networking device.

A Gateway is a more general term. It operates at the highest layer involved in the translation. A gateway connects two dissimilar networks that use different protocols or data formats. For example, a gateway might connect an IP network to an SNA (Systems Network Architecture) network, performing deep protocol translation at every layer from physical to application. In modern usage, "default gateway" simply refers to the router that connects a local network to the internet, but a true protocol-converting gateway is a much more complex device than a router.
