Part I

Software Defined Networking

The Idea Behind SDN

Imagine you manage a building where every light switch is hardwired to a specific bulb, and reconfiguring which switch controls which bulb requires physically rewiring the wall. That is, in a loose but useful sense, how traditional networking operates. Each router and switch carries its own brain — its own control logic — baked into the firmware. The device that decides where packets should go is the same device that actually forwards them. The decision-maker and the doer are inseparable, locked in the same metal box.

This arrangement worked well enough for decades, when networks were small and mostly static. But networks grew — into data centers, cloud platforms, enterprise campuses spanning continents — and something strange happened. The old model began to crack under its own weight. Every time you wanted to change how traffic flowed, you had to reconfigure individual devices, one by one, through command-line interfaces that hadn't changed much since the 1990s. Want to reroute traffic around a failed link? Log into each router. Want to enforce a new security policy? Log into each firewall. Want to balance load across twenty switches? You get the idea.

The central insight of Software Defined Networking is almost embarrassingly simple once you hear it: what if we pulled the brain out of every device and put it somewhere central? What if the decision-making — the "control plane" — sat in one place, and the doing — the "data plane" — stayed distributed across the devices? The devices become what they perhaps always should have been: fast, dumb packet-movers, receiving instructions from a smart, centralized controller that sees the entire network.

Formal definition: SDN is an approach to building networks in which the control plane and data plane are physically separated, the control plane is centralized, a standard southbound API (such as OpenFlow) provides the interface between them, and the network is directly programmable and vendor-neutral.

Notice how many distinct claims are packed into that definition. It is not merely "centralize the control." It is also: codify the separation in an open interface (so you are not locked into one vendor's hardware), make the network programmable (so you can write software that changes behavior on the fly), and ensure agility (so the network adapts as fast as the applications running on it). Each of these constraints matters. Without an open interface, you would simply have invented a slightly different kind of vendor lock-in. Without programmability, a centralized controller would be just another management console. The definition is a bundle of engineering decisions that reinforce each other.

The job of the control plane: determine routes (running BGP, OSPF, RIP). The job of the data plane: forward packets along those routes, hop by hop.

There is a tempting but slightly wrong intuition here — that SDN simply means "running routing protocols on a server instead of a router." That is part of it, but it underestimates the shift. In a traditional network, each router runs its own instance of a routing protocol; they exchange information peer-to-peer and each builds its own routing table. In SDN, the controller has a global view. It does not need to run distributed consensus algorithms because it is the consensus. It sees every link, every flow, every device, and computes forwarding rules with complete information. This is a fundamentally different architectural posture, and it changes what you can do: traffic engineering that was previously intractable, security policies enforced uniformly, network slices provisioned in seconds rather than weeks.

So SDN is defined by several properties working in concert: separation of control and data planes, centralization of the control plane, a standard southbound API, direct programmability, agility through abstraction, and open, vendor-neutral standards. No single property is sufficient on its own. Together, they describe a genuinely different way to build and operate networks.

Control Plane, Data Plane, and the Wall Between Them

Let us make the control plane / data plane distinction precise, because it is the load-bearing wall of everything that follows in SDN.

The control plane is the logic that determines how the network should behave. It runs routing protocols (BGP, OSPF, RIP), configures middleboxes (firewalls, NATs, intrusion detection systems), and decides policies. It is the decision-maker. In a traditional network, this logic runs on every router independently; in SDN, it runs on the controller.

The data plane is the machinery that implements those decisions on actual packets. It does IP forwarding, Layer 2 switching, ACL matching — the high-speed, per-packet work. It is the doer. In SDN, the data plane lives in the switches, which have become simpler: they do not need routing daemons or policy engines. They receive rules from the controller and execute them at line rate.

At first glance this seems like a trivial separation — "deciding vs. doing" — but the interesting question is not really the distinction itself, but what happens when you physically separate them. When the control plane sits on a different machine from the data plane, you gain a centralized view, but you also introduce a new problem: the controller must communicate with every switch, and if that communication fails, the switch is on its own. The switch has no local intelligence to fall back on. This is the classic reliability concern with SDN, and it is why production deployments use redundant controllers and failover mechanisms. The separation buys you power and programmability; it costs you a new category of failure modes.

Figure 1 — In a traditional network, each router carries its own control logic and exchanges routing information peer-to-peer. In SDN, the controller holds all control logic; switches become pure data-plane devices.

SDN operates on a three-tier architecture: the application tier at the top (where network applications live), the controller tier in the middle (the server software that replaces traditional CLI-based management), and the data plane tier at the bottom (the switching devices themselves). We will explore each tier in detail when we discuss the SDN architecture layers. For now, the essential point is that the three tiers communicate through well-defined APIs — northbound APIs between application and controller, southbound APIs between controller and switches — and this layering is what makes SDN programmable and vendor-neutral.

Use Cases and Benefits

It is one thing to say SDN separates the control and data planes. It is another to understand why anyone would go to the trouble. The benefits are not abstract — they map to concrete operational problems that network administrators face daily.

  • Abstraction of hardware into virtual network slices

  • Load balancers, firewalls, IDS provisioned on demand

Read through that list again and notice a pattern: nearly every benefit is about removing humans from the loop of routine network management, or about enabling things that were theoretically possible but practically infeasible in a distributed-control world. Traffic engineering, for instance, is not impossible in a traditional network — it is just that computing optimal paths for thousands of flows requires global information, and no single router has global information. The controller does. Multi-tenancy is not impossible either — VLANs existed before SDN — but giving each tenant full control over their own addressing, topology, and routing without interfering with other tenants is fiendishly difficult when every switch is independently configured. SDN makes it tractable.

In a traditional network, changing behavior means reconfiguring devices — often through vendor-specific CLIs. This is slow, error-prone, and does not scale. In SDN, "programmable" means you can write a Python script (or use a REST API) to modify forwarding rules across the entire network in milliseconds. This is not a convenience — it is a qualitative shift in what networks can do. Think of the difference between compiling a program and interpreting one: the interpretation overhead changes the kinds of programs you can reasonably write.

SDN Architecture: The Three Layers

The SDN architecture is a stack of three layers, each with a distinct role, communicating through well-defined interfaces. It is worth understanding each layer not as a passive container but as an active participant with its own responsibilities and internal complexity.

Figure 2 — The three-layer SDN architecture. Northbound APIs (typically RESTful) connect applications to the controller. Southbound APIs (typically OpenFlow) connect the controller to infrastructure devices.

Application Layer

The top layer is where network applications reside. These are not end-user applications like web browsers; they are network applications — programs that observe, analyze, and control the network. Examples include network monitoring tools, traffic engineering engines, security policy enforcers, and load balancers. This layer also includes Network Service Functions (the Slicing Manager that partitions the network into virtual slices, the Topology Manager that tracks the network graph, the Host Tracker that follows endpoint locations), Network Orchestration Functions (coordinating resources across the network), and Management Functions (configuration, fault handling).

The application layer communicates with the controller through Northbound APIs, which are typically RESTful. This is a deliberate choice: REST APIs are well-understood, language-neutral, and allow applications to be written in any language — Python, Java, Go, whatever — without needing to understand the controller's internal architecture. The northbound interface is what makes SDN an open ecosystem for network innovation.

Control Layer (SDN Controller)

The controller is the central brain of the SDN architecture. It makes routing decisions, manages network devices, implements policies, and provides a global view of the entire network. Internally, it consists of several components: the Controller API (exposing Java and REST interfaces for applications), the Service Abstraction Layer (SAL) (which translates between the controller's internal services and the protocol plug-ins), and the Protocol Plug-ins (supporting various southbound protocols including PCEP, SMTP, XMPP, BGP, and OpenFlow versions 1.0 through 1.4).

The SAL is worth pausing on. It exists because the controller might need to speak multiple southbound protocols — OpenFlow to some switches, BGP to some routers, XMPP to others. The SAL provides a uniform internal interface so that the controller's core logic does not need to know which protocol it is using for any given device. This is a classic abstraction layer, and it is what allows the controller to manage heterogeneous infrastructure.

Infrastructure Layer (Data Plane)

The bottom layer contains the physical devices — switches, routers, access points — that actually forward packets. These devices are simpler than their traditional counterparts: they do not run routing protocols or make independent forwarding decisions. Instead, they follow rules provided by the controller through southbound protocols. This layer also includes overlay tunnel technologies like VxLAN and NVGRE, which create virtual network overlays on top of the physical infrastructure.

The reduction in device complexity is a feature, not a bug. Simpler devices are cheaper to build, easier to manage, and less likely to have configuration bugs. All the intelligence lives in the controller; all the speed lives in the switch's hardware forwarding pipeline.

OpenFlow Protocol

You might imagine that separating the control and data planes is sufficient — that once you have a controller and some switches, they will simply figure out how to talk to each other. But the interface between controller and switch needs to be specified precisely: what messages can the controller send? What can the switch report? How are forwarding rules represented? Without a standard protocol, every controller vendor would invent its own communication mechanism, and we would be back to vendor lock-in — the very problem SDN was designed to solve.

This is where OpenFlow enters. OpenFlow is the first standard communication interface defined between the control and forwarding layers of SDN architecture. It is a protocol specification that describes how an OpenFlow controller communicates with an OpenFlow switch. It is layered on top of TCP, and controllers listen on TCP port 6653. The protocol has three components: the OpenFlow controller, the OpenFlow protocol itself (the message format), and the OpenFlow switch.

Key fact for exams: OpenFlow runs over TCP. The controller listens on port 6653. The controller communicates with the switch over a secure channel. The protocol defines the message format. The purpose of the control channel is to update the flow table. Logic is executed at the controller, not at the switch.

How OpenFlow Works: The Mechanism

  1. The OpenFlow controller establishes a connection with the switch over a secure channel (TLS-encrypted TCP session on port 6653).
  2. The controller sends messages to the switch to populate, modify, or delete entries in the switch's flow table.
  3. When a packet arrives at the switch, the switch matches the packet's header fields against entries in the flow table.
  4. In OpenFlow v1.0, the packet header is matched against one of N flow tables. If a match is found, the switch performs the associated action. If no match is found, the packet is sent to the controller for instructions.
  5. The controller examines the packet, determines the appropriate forwarding rule, and installs a new flow entry in the switch's flow table.
  6. Subsequent packets in the same flow are forwarded directly by the switch, without controller involvement.

Notice the clever bootstrapping problem solved here. The switch does not need to know what to do with any packet in advance; it can always fall back to asking the controller. But once the controller has provided a rule, the switch handles future packets of that flow autonomously. The controller is involved only in the first packet (in reactive mode) or not at all (in proactive mode). This keeps the data plane fast while preserving the control plane's authority.

The OpenFlow Switch and Its Flow Tables

An OpenFlow switch's primary data structure is the flow table, which consists of flow entries. Each flow entry has three components:

Figure 3 — The three components of a flow entry. Header fields determine which packets match; counters track statistics; actions determine what happens to matched packets.

The actions are where the real flexibility lives. A flow entry can instruct the switch to: (1) forward the packet to zero or more specific ports, (2) encapsulate the packet and forward it to the controller (for flows the switch does not yet know how to handle), (3) send the packet to the normal processing pipeline (the switch's traditional L2/L3 forwarding, if available), or (4) modify fields in the packet header before forwarding (rewriting source/destination, changing VLAN tags, etc.). This last capability — modifying fields in-flight — is remarkably powerful. It enables network address translation, tunnel encapsulation, traffic marking, and other middlebox functions directly in the switch, without needing separate appliances.

Notice that the action "forward to zero or more ports" includes the case of zero ports — which means dropping the packet. This is how SDN implements firewall rules: a flow entry that matches certain traffic and has an empty action list simply discards those packets. No separate firewall appliance needed. The switch itself becomes the enforcement point, with rules centrally managed by the controller.

Operating and Control Modes

OpenFlow defines two operating modes that determine when flow entries are installed, and two control modes that determine how many controllers manage the network. These are orthogonal choices, and understanding the tradeoffs of each is essential for both exams and real deployment decisions.

Operating Modes: Reactive vs. Proactive

Reactive Mode

The first packet of a new flow triggers the controller to insert a flow entry into the switch. The switch sends the unknown packet to the controller, the controller computes the forwarding rule, and installs it. Subsequent packets of that flow are handled locally by the switch.

  • Efficient use of flow table space (only active flows have entries)
  • Incurs setup latency for the first packet of every new flow
  • Risk of overwhelming the controller during traffic spikes
Proactive Mode

The controller pre-populates the flow table with entries for anticipated flows before any traffic arrives. When a packet comes in, its rule is already in place.

  • Zero additional setup time — all forwarding is at switch speed
  • Wastes flow table space on entries that may never be used
  • Requires the controller to predict which flows will arrive

There is a design philosophy hiding in this choice. Reactive mode embodies the SDN ideal: the controller is omniscient and responds to everything in real time. Proactive mode concedes that sometimes you want the speed of pre-computed rules. In practice, networks use both: proactive rules for known, stable traffic patterns, and reactive rules for unexpected or dynamic flows.

Control Modes: Centralized vs. Distributed

Centralized control means one controller manages all switches. Simple, consistent, but a single point of failure and a potential bottleneck. Distributed control means multiple controllers share the management burden, typically with one active controller per switch and failover mechanisms. Distributed control is more robust but introduces the need for controller-to-controller synchronization — a nontrivial distributed systems problem.

Flow-Based vs. Aggregated Routing

Property Flow-Based Aggregated
Setup Every flow individually set up by controller One flow entry covers large groups of flows
Match Type Exact-match flow entries Wildcard flow entries
Table Entries One entry per flow One entry per category of flows
Best For Fine-grain control (e.g., campus networks) Large number of flows (e.g., backbone)

The flow-based vs. aggregated distinction is about granularity. In a campus network, you might want to control each user's traffic individually — different QoS policies per user, different security rules per device. Flow-based gives you that precision. In a backbone network carrying millions of flows, individual entries would exhaust the flow table. Aggregated entries (using wildcard matching, similar to how a routing table uses CIDR prefixes) scale much better, at the cost of coarser control.

Part II

Delay Tolerant Networks

What Is a DTN, and Why Does It Exist?

The Internet, as most of us understand it, rests on a set of assumptions so deeply embedded that we no longer notice them. A TCP connection assumes there is a continuous end-to-end path between sender and receiver. It assumes round-trip times are short enough for acknowledgments to arrive before timeouts expire. It assumes data rates are roughly symmetric. It assumes error rates are low enough that retransmission handles the occasional lost packet. These assumptions are so fundamental to Internet protocols that they are practically invisible — until you try to use the Internet in a place where none of them hold.

Consider what happens when a Mars rover sends data back to Earth. The signal takes between 4 and 24 minutes to arrive (depending on orbital positions). There is no continuous path — the rover might be behind the planet, or a relay satellite might be on the far side of its orbit. Data rates are wildly asymmetric (the rover's uplink is orders of magnitude slower than its downlink). Error rates are high because space is, among other things, a very noisy medium for radio signals. TCP, designed for a world of millisecond round-trips and reliable fiber, simply cannot function here. It will time out before the first acknowledgment even leaves Earth.

The Internet assumes the network is always there. A DTN assumes it is not — and designs accordingly.

A Delay Tolerant Network (DTN) is an intermittent and heterogeneous network in which same and different protocols are used for sending and receiving messages between nodes. It was originally designed to support the InterPlanetary Internet (IPN) — Vint Cerf's vision of an internet that spans planetary distances. But the problem turned out to be far more general than space communication: remote rural areas without continuous connectivity, military networks in hostile terrain where infrastructure is destroyed, disaster recovery where the cellular network has collapsed, sensor networks with limited power that wake up only periodically — all of these are DTN scenarios.

What makes DTNs different from the regular Internet can be summarized as a systematic violation of Internet assumptions:

  • Intermittent connection: End-to-end paths do not always exist. Nodes connect and disconnect unpredictably.
  • Long/High delays: Propagation delays can be minutes or hours, not milliseconds.
  • Asymmetric data rates: Uplink and downlink capacities can differ by orders of magnitude.
  • High error rates: Bit errors are common, especially in wireless and space channels.
  • Lack of end-to-end connectivity: There may never be a moment when a complete path from source to destination exists simultaneously.

That last point is the deepest break from Internet assumptions. The Internet's routing and transport protocols require, at some point, a connected path from A to B. A DTN cannot guarantee this. The fundamental routing mechanism must therefore be something other than "find a path and send along it." It must be something like "carry the data as far as you can, hold it until you can carry it further, and eventually deliver it." This is the store-carry-and-forward paradigm, and it is to DTNs what packet switching is to the Internet: the foundational mechanism on which everything else is built.

Terrestrial Mobile Partitioning due to mobility Frequent disconnect Store-carry-forward
Exotic Media Long delays, connection drop Intermittent communication Scheduled contacts
Sensor-Based Limited power constraints Scheduled intervals Energy-efficient routing

DTN Architecture and the Bundle Protocol

The DTN architecture is an overlay network — a network built on top of other networks. It sits on top of region-specific lower layers (TCP/IP within a well-connected region, some deep-space protocol between planets, a satellite link between ground stations) and provides a uniform messaging service across all of them. The key insight is that different regions of a DTN may use fundamentally different communication protocols internally, and the DTN overlay bridges these regions.

Messages in the DTN architecture are called bundles. The Bundle Protocol, discovered by Vint Cerf in 2003, implements store-and-forward message switching by overlaying a new transmission protocol over lower-layer protocols. The bundle is the unit of transmission — it is what gets stored, carried, and forwarded.

Figure 4 — The DTN overlay sits above regional networks (Internet, deep space, sensor). Bundles are stored at each node and forwarded when a contact becomes available. The store-carry-forward mechanism is illustrated below: Node A stores the bundle, Node B physically carries it, and delivers to Node C when contact is established.

Key Features of the Bundle Protocol

Custody Transfer

This is a reliable handoff mechanism. When a node forwards a bundle, it can transfer custody — meaning the receiving node becomes responsible for that bundle's eventual delivery. The sending node is then free to delete its copy (freeing buffer space), knowing that custody has been assumed. This is somewhat like registered mail: once the post office accepts your letter, they are responsible for delivering it, and you can stop worrying. The comparison breaks down, however, because in a DTN, the "post office" might be a satellite that will not have another contact for six hours. Custody transfer ensures that at least one node is always accountable for each bundle's delivery, even when connections are sporadic.

Bundle Prioritization

Bundles are assigned priority levels: high, medium, and low. When a node has limited buffer space or bandwidth, higher-priority bundles are forwarded first. In a disaster scenario, emergency coordination messages would be high priority; routine data uploads would be low.

Bundle Fragmentation and Reassembly

Large bundles can be split into smaller pieces to handle size limits or short connection times. If a contact window is only long enough to transmit half of a bundle, the bundle can be fragmented, the first half sent, and the remainder sent during the next contact. Fragments are reassembled at the destination or at an intermediate node. This is crucial in DTNs, where contact opportunities are brief and unpredictable — you cannot afford to wait for a contact long enough to send an entire large bundle.

IP fragmentation operates within a single connected network and assumes fragments will arrive at the destination quickly enough for reassembly. In a DTN, fragments might arrive hours apart, through different intermediate nodes, and the destination might not even be reachable when the first fragment arrives. Bundle Protocol fragmentation is designed for this reality: fragments are themselves valid bundles, can be stored and forwarded independently, and carry enough metadata to be reassembled even if they arrive out of order or through completely different paths.

Internet vs. DTN

The contrast between the Internet and DTN is not merely a list of differences — it reflects a fundamentally different design philosophy. The Internet was built on the assumption that the network is generally reliable; DTN was built on the assumption that it is generally not.

Property Internet DTN
Switching Packet switching Store-and-forward message switching
Connection Continuous, end-to-end Intermittent, no guaranteed path
Primary Protocol TCP/IP Bundle Protocol (not necessarily over TCP/IP)
Messages to unavailable host Dropped or error returned Stored and forwarded when possible
Delivery model Real-time or near-real-time Best-effort with potentially long delays
Analogy Telephone call Postal mail / Email

The email analogy is instructive and also limited. Email is store-and-forward, and you can send a message to someone whose mail server is temporarily down — the sending server will retry. But email operates within a well-connected Internet infrastructure where retries happen every few minutes over reliable links. DTN retries might happen over hours or days, over links that were never designed to work together. The Bundle Protocol's custody transfer, fragmentation, and prioritization exist precisely because email's simple retry mechanism is insufficient for environments where a "retry" might mean waiting for a satellite to orbit back into range.

Another way to think about the difference: the Internet assumes the network is a substrate — always present, always working. DTN assumes the network is an opportunity — sometimes present, sometimes not, and you must exploit it when you can. This philosophical inversion drives every architectural decision in DTN design.

Addressing, Nodes, and Security

Nodes in a DTN

There are three types of nodes in a DTN, each with a distinct role:

  • Host: An endpoint — the source or destination of bundles.
  • Router: Forwards bundles within a single DTN region. It does not cross region boundaries.
  • Gateway: Connects neighboring networks (different DTN regions). Gateways are the bridges that allow bundles to traverse heterogeneous environments.

The distinction between routers and gateways matters because routing within a region may use completely different protocols from routing between regions. A router within a terrestrial Internet region might use standard IP forwarding; a gateway connecting that region to a satellite link must translate between the bundle protocol's semantics and the satellite's peculiar transmission characteristics.

Names and Addressing

DTN addressing is based on URIs (Uniform Resource Identifiers), not IP addresses. This is a deliberate design choice. IP addresses assume a fixed, routable topology; URIs are more flexible and can accommodate the heterogeneous, intermittently connected nature of DTNs. An example DTN address: dtn://earth.sol.int/src.someclient.com. This URI identifies a node on Earth within the solar system internet. The hierarchical structure allows routing decisions at multiple levels of granularity.

DTN addressing supports unicast (one-to-one), anycast (one-to-nearest-of-a-group), multicast (one-to-a-group), and broadcast (one-to-all) delivery modes — providing flexibility that a purely unicast Internet model does not natively support.

Security

Security in DTNs is complicated by the same intermittent connectivity that defines the network. Traditional Internet security relies on online authentication servers and real-time certificate verification — both of which may be unavailable in a DTN. DTN security therefore uses a different model: network routers participate in authentication using private/public certificates, and messages contain signatures that are regenerated at each hop. Each hop can independently verify the bundle's authenticity without needing to contact a central authority. This hop-by-hop security model trades the stronger guarantees of end-to-end encryption for the practical necessity of operating without continuous connectivity to a certificate authority.

In the Internet, end-to-end encryption (TLS) is preferred because intermediate nodes might be untrusted. In a DTN, intermediate nodes must be trusted — they have custody of your bundles, and they might modify, fragment, or re-encode them. Hop-by-hop security ensures that each link in the chain is authenticated, even if you cannot verify the entire chain at once. This is a pragmatic compromise: slightly weaker security guarantees in exchange for a system that actually works in disconnected environments.

Routing in DTNs: Taxonomy and Design

Routing in DTNs uses the store-carry-and-forward mechanism: a node receives a bundle, stores it, carries it (potentially while physically moving), and forwards it when a suitable contact becomes available. This is fundamentally different from Internet routing, where packets are forwarded immediately along a pre-computed path. In a DTN, there may be no path — so the routing question becomes: to whom should I give this bundle, and when?

DTN routing protocols can be classified into two broad families, with further subdivisions:

Figure 5 — Refined taxonomy of DTN routing protocols. The updated geometry eliminates node collision by expanding the horizontal gutter between Replication and Forwarding branches.

The taxonomy has four categories, though the first two are the primary families:

  1. Replication/Flooding-based: Messages are copied to reachable neighbors. High resource usage, high delivery probability. Works with no prior knowledge of the network.
  2. Controlled Flooding: A refinement that limits the number of copies to balance delivery probability and resource usage. Spray and Wait is the canonical example.
  3. Forwarding-based: A single copy of the message is forwarded to a "better" node — one that is more likely to reach the destination. Requires some knowledge about the network.
  4. Knowledge-based: Includes scheduled routing (contacts are known in advance), probabilistic/predictable routing (PROPHET — uses history of node encounters to predict future contacts), and context-aware/social routing (uses social relationships between nodes to predict meetings).

Flooding-Based Routing Protocols

Flooding-based protocols share a common strategy: copy the message to as many nodes as possible, increasing the chance that one of them will encounter the destination. They work even with no knowledge about the network topology or contact patterns — which is both their strength and their weakness.

Direct Contact

The simplest possible DTN routing protocol: the source holds the message and waits until it encounters the destination directly. Only one copy of the message exists. This is extremely conservative — minimal resource usage, but potentially enormous delay. If the source and destination never meet, the message is never delivered. The protocol is useful only in scenarios where the source and destination are guaranteed to encounter each other eventually.

Epidemic Routing

At the opposite extreme from Direct Contact. When two nodes meet, they exchange summary vectors — lists of messages they are carrying. Each node then replicates any messages it does not already have. The result is that messages spread through the network like a contagion (hence the name). Every node eventually carries every message. Delivery ratio is very high (assuming sufficient contacts), but resource usage is also very high — buffer space, bandwidth, and energy are all consumed at maximum rates. Epidemic routing generates N-1 copies per message in a network of N nodes.

There is a tempting but slightly wrong intuition here — that epidemic routing is "wasteful" and should never be used. That judgment is incomplete. In a small network with frequent contacts and ample resources, epidemic routing's simplicity and high delivery ratio may be exactly what you need. The waste only becomes unacceptable when the network is large or resources are constrained. Like most engineering choices, it depends on context.

Two-Hop Routing

A middle ground. The source replicates the message to an adequate number of relay nodes, and those relay nodes deliver it directly to the destination (within two hops total: source → relay → destination). Relay nodes do not further replicate the message. This limits the number of copies while still providing better delivery than Direct Contact.

Tree-Based Flooding

The source replicates the message to only two child nodes (forming a binary tree), limiting both the breadth and depth of the replication tree. The total number of copies is approximately 1 + log(N/2), where N is the number of nodes. This significantly reduces resource usage compared to epidemic routing, at the cost of lower delivery probability and higher average delay.

Spray and Wait (Quota-Based)

This protocol has two phases. In the spray phase, the source replicates the message to m distinct relay nodes. In the wait phase, if the destination has not been found, each relay node performs direct transmission — it holds the message until it encounters the destination directly. The number m is the quota; it controls the tradeoff between delivery probability and resource usage. A larger m means higher delivery probability but more resource consumption. Spray and Wait is elegant because it provides a single knob (m) that lets you tune the protocol for your specific constraints.

Read the table carefully and notice the clear tradeoff: protocols that generate more copies achieve higher delivery ratios and lower delays, but consume more resources. This is the fundamental tension in DTN routing design. There is no free lunch — you cannot maximize delivery and minimize resources simultaneously. Every protocol occupies a different point on this tradeoff curve, and the "right" choice depends on the specific deployment scenario: how many nodes, how much buffer, how much energy, how critical is delivery.

Forwarding-Based Routing Protocols

Forwarding-based protocols take a fundamentally different approach: instead of copying the message to many nodes, they forward a single copy to a node that is judged to be "better" — more likely to encounter the destination. This requires some knowledge about the network: contact histories, node relationships, cluster structures, or current connectivity information. The tradeoff is clear: lower resource usage at the cost of requiring information that may be imperfect or stale.

NECTAR (Node Encounter-based Context-aware Routing)

Each node maintains a neighborhood index — a record of how frequently it has encountered other nodes. When a node carrying a message encounters another node, it forwards the message if the encountered node has a higher neighborhood index for the destination (i.e., it meets the destination more often). The intuition is simple: give the message to the node that has the best track record of meeting the destination. NECTAR achieves high delivery ratios with moderate resource usage, because forwarding decisions are informed by actual encounter history rather than blind flooding.

Source Routing

The route is discovered via control packets and specified at the source. The entire path is determined before the data message is sent. If any link along the path fails, route error messages are broadcast and a new route must be discovered. Source routing is straightforward but fragile in a DTN, because the computed path may be invalid by the time the message actually traverses it — links are intermittent, and a path that existed during route discovery may not exist during forwarding.

Per-Hop Routing

Each intermediate node independently decides the next hop. This allows more up-to-date information to be used at each step, because each node makes its decision based on current conditions rather than a path computed at the source. Per-hop routing is more resilient to topology changes than source routing, but requires each node to maintain routing information.

Per-Contact Routing

The most dynamic approach. When a contact becomes available, the node checks current connectivity information to select the best relay. This uses the most up-to-date information possible — it does not rely on historical data or pre-computed routes, but on the actual state of the network right now. Per-contact routing achieves high delivery ratios and low delays when contacts are frequent enough to provide good connectivity information, but may struggle in very sparse networks.

Hierarchical Forwarding and Cluster Control (CRHC)

Nodes are grouped into clusters. A cluster head — the node with the highest stability and/or communication quality — makes routing decisions for the cluster. This reduces the routing overhead because only cluster heads participate in inter-cluster routing; ordinary nodes simply forward to their cluster head. CRHC achieves high delivery ratios with moderate resource usage, but requires a cluster formation and maintenance mechanism, which adds its own overhead.

That explanation about source routing having a low delivery ratio deserves a moment of attention, because it might seem counterintuitive. Source routing computes the entire path upfront; why would that be worse? The answer lies in the nature of DTNs: contact opportunities are ephemeral. A path that existed five minutes ago may not exist now. Source routing locks in a path that may be stale before the message even begins its journey. Per-hop and per-contact routing, by deferring routing decisions to the moment of forwarding, can exploit current information and avoid this trap. The cost is more routing computation at each step, but the benefit is decisions based on reality rather than recollection.

Recent Advancements

DTN routing research is an active field, and the protocols described above represent the foundational approaches. Recent work has focused on making these protocols more adaptive and efficient, particularly by addressing their resource-blindness: most basic protocols do not consider node energy, buffer state, or message urgency when making forwarding decisions.

Adaptive Techniques: EMRT

The Energy-aware Multi-copy Routing Technique (EMRT) dynamically adjusts the number of replicas based on three factors: the node's remaining energy, the available buffer space, and the message's time-to-live (TTL). If a node is low on energy or buffer, it creates fewer replicas, conserving resources for more critical messages. If a message's TTL is about to expire, the node may create more replicas to maximize the chance of delivery before the message becomes invalid. This is a form of quota-based routing where the quota is not fixed (as in Spray and Wait) but adapts to current conditions.

Locking Mechanisms: RBL

The Redundancy-Based Locking (RBL) mechanism uses a locking method to reduce redundant transmissions and prevent network congestion. When a node detects that a message has already been widely disseminated (based on the number of copies it has observed in the network), it "locks" the message, preventing further replication. This prevents the scenario where a popular message floods the entire network, consuming resources that could be used for other messages. RBL is a form of congestion control for DTNs — a problem that did not receive much attention in early DTN research, when networks were assumed to be small and sparse enough that congestion was rare.

If you step back and look at the entire taxonomy — from Direct Contact (no information, one copy) to Per-Contact Routing (maximum information, one copy) to Epidemic Routing (no information, maximum copies) — a pattern emerges. DTN routing quality depends on two variables: how much you know about the network and how many copies you make. These are partially substitutable: more knowledge means you need fewer copies to achieve the same delivery ratio; fewer copies means you need more knowledge to choose wisely. The entire design space of DTN routing can be understood as navigating the tradeoff between information and replication. Adaptive techniques like EMRT and RBL are simply trying to make this navigation more intelligent.

Rapid Revision Notes
  • DTN = intermittent, heterogeneous network. Originally for InterPlanetary Internet (Vint Cerf).
  • Internet assumes: continuous path, short RTT, symmetric rates, low errors. DTN faces: intermittent connections, long delays, asymmetric rates, high errors, no end-to-end connectivity.
  • DTN is an overlay on regional networks. Messages = bundles. Bundle Protocol (2003) implements store-and-forward.
  • Bundle Protocol features: Custody Transfer (reliable handoff), Prioritization (high/medium/low), Fragmentation (split for size/contact limits), Reassembly (at destination).
  • Internet = packet switching, continuous. DTN = store-and-forward message switching, like email but across disconnected regions.
  • Nodes: Host (endpoint), Router (within region), Gateway (between regions). Addressing: URIs (dtn://...). Supports unicast/anycast/multicast/broadcast.
  • Security: hop-by-hop authentication with certificates; signatures regenerated at each hop.
  • Routing paradigm: Store-Carry-Forward.
  • Routing taxonomy: Replication/Flooding (copies, no knowledge), Controlled Flooding (limited copies), Forwarding (single copy, needs knowledge), Knowledge-based (scheduled/PROPHET/context-aware).
  • Flooding protocols: Direct Contact (1 copy, low delivery), Epidemic (N-1 copies, high delivery, high resources), Two-Hop (K relays), Tree-Based (1+log(N/2)), Spray and Wait (m copies, spray then wait).
  • Forwarding protocols: NECTAR (neighborhood index), Source Routing (pre-computed path, fragile), Per-Hop (each node decides), Per-Contact (most current info), CRHC (cluster-based).
  • Recent: EMRT (adaptive replicas based on energy/buffer/TTL), RBL (locking to reduce redundant transmissions).

Common Mistakes
  • Confusing "store-and-forward" (DTN) with "packet switching" (Internet). Store-and-forward in DTN means holding a message for potentially hours; in Internet routers, store-and-forward is measured in milliseconds.
  • Saying DTN uses TCP/IP. It does not necessarily. The Bundle Protocol can run over any lower-layer protocol.
  • Confusing "replication" (copying to multiple nodes) with "forwarding" (passing a single copy). These are fundamentally different strategies.
  • Forgetting to mention the Bundle Protocol's fragmentation and reassembly — these are critical for operation in environments with brief contact windows.
  • Claiming epidemic routing is always the best because of high delivery. It has the highest resource cost and is impractical in resource-constrained networks.
  • Confusing DTN routers (within a region) with DTN gateways (between regions). This distinction matters for the architecture.
  • Forgetting to mention that DTN addressing uses URIs, not IP addresses.
