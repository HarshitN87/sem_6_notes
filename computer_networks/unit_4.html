Part I

Software Defined Networking

Section 1.1

Introduction to Software-Defined Networking

Imagine, for a moment, that you are the network administrator of a mid-sized enterprise. You manage forty-seven switches, twelve routers, and a tangle of firewall rules that nobody fully understands anymore. When a new VLAN needs to be created, you do not simply click a button — you log into each switch individually, type commands in a vendor-specific syntax, and pray that you have not introduced a subtle inconsistency that will bring down a department's connectivity at the worst possible moment. Every device thinks for itself, makes its own decisions, and operates in isolation from the holistic needs of the network. This is the world of traditional networking, and it is precisely the world that Software-Defined Networking was invented to escape.

Software-Defined Networking, abbreviated as SDN, is fundamentally an architectural approach to building networks in which the control plane — the part of the network that decides how traffic should be routed — is physically and logically separated from the data plane — the part that actually moves the packets from one port to another. In traditional networking, every router and switch contains both planes bundled together inside the same box, running proprietary firmware that the network operator cannot easily inspect or modify. SDN proposes that these two functions should be disaggregated, with the control plane extracted into a centralized software controller that programs the data plane devices through well-defined, open interfaces.

Intuitive Analogy Think of a traditional network as a restaurant where every waiter independently decides which kitchen station to send an order to, based on their personal judgment and a small rulebook they carry in their pocket. SDN is like installing a head chef who sees the entire restaurant, knows which stations are busy, and directs every waiter accordingly. The waiters no longer decide — they simply follow instructions. The head chef is the controller; the waiters are the switches.

The historical motivation for SDN arose from several converging frustrations. First, network operators found themselves locked into vendor ecosystems — a Cisco switch spoke a slightly different language than a Juniper switch, and neither was eager to make their firmware programmable by competitors' tools. Second, the pace of innovation in networking hardware was glacial compared to software: deploying a new routing protocol required firmware upgrades across hundreds of devices, a process that could take months. Third, the rise of cloud computing and massive data centers demanded a level of network flexibility and automation that traditional architectures simply could not provide. When you need to spin up ten thousand virtual machines and reconfigure the network in seconds, logging into individual switches with a command-line interface becomes a parody of engineering.

The core idea behind SDN, then, is that networks have these two distinct planes of operation, and the separation between them should be codified not as an internal implementation detail but as an open, standardized interface. The control plane determines how the network should behave — it runs routing protocols, computes forwarding paths, and enforces policies. The data plane implements that behavior on individual packets — it reads the forwarding table and sends each packet out the appropriate port. By extracting the control plane into a centralized, programmable entity, SDN transforms the network from a collection of independent, opaque devices into a coherent system that can be managed holistically, automated, and innovated upon at the speed of software rather than the speed of hardware procurement.

Section 1.2

Centralized and Distributed Control & Data Planes

To understand SDN deeply, we must first understand the two fundamental planes of network operation — the control plane and the data plane — and then examine how each can be organized in either a centralized or distributed fashion. This four-quadrant analysis (centralized control, distributed control, centralized data, distributed data) is essential for university examinations because it reveals why SDN chose its particular combination and what tradeoffs were involved.

The Control Plane

The control plane is the decision-making layer of the network. Its job is to determine the route that packets should follow through the network topology. In practical terms, the control plane runs routing protocols — BGP for inter-domain routing, OSPF or RIP for intra-domain routing — and populates the forwarding tables that the data plane consults. The control plane does not touch individual packets; it computes the rules by which packets will be forwarded. Think of it as the legislative branch of the network: it writes the laws, but it does not enforce them on a case-by-case basis.

The Data Plane

The data plane, sometimes called the forwarding plane, is the execution layer. It is responsible for receiving each incoming packet, consulting the forwarding table that the control plane has installed, and sending the packet out through the correct port. This happens at line rate — meaning millions of packets per second — and therefore must be implemented in specialized hardware (typically ASICs, Application-Specific Integrated Circuits) for speed. The data plane does not ask questions about whether a route is optimal; it simply follows the rules it has been given. It is the executive branch: it enforces the law as written, without interpretation.

Centralized vs. Distributed Control Plane

In a distributed control plane, which is the architecture of traditional networking, every router runs its own instance of the routing protocol. Each router independently discovers its neighbors, exchanges routing information, and computes its own forwarding table. This is how the Internet has historically operated — no single entity has a complete view of the network, and routing decisions emerge from the collective behavior of thousands of independent routers running distributed algorithms. The advantage of this approach is resilience: if one router fails, the others reconverge and find alternative paths. The disadvantage is that no router has a global view, which means routing can be suboptimal, policy enforcement is inconsistent, and troubleshooting is a nightmare of cross-referencing logs from dozens of devices.

In a centralized control plane, a single logical entity — the SDN controller — maintains a complete, global view of the entire network topology and computes forwarding paths for all devices. Instead of each switch running OSPF and making independent decisions, the controller tells every switch exactly what to do. This enables globally optimal routing, consistent policy enforcement, and rapid adaptation to changes. The tradeoff is that the controller becomes a single point of failure, which is why production SDN deployments use clusters of controllers for redundancy. But logically, the control plane remains centralized: there is one brain, not dozens.

Centralized vs. Distributed Data Plane

The data plane is almost always distributed in practice, because the very nature of packet forwarding requires physical devices at different locations — a switch in Building A cannot forward packets that arrive at a switch in Building B. However, it is useful to distinguish between a data plane that consists of programmable but autonomous forwarding devices (distributed data plane with local intelligence) and a data plane that consists of simple, programmable devices with no autonomous decision-making capability (distributed data plane with centralized programming, which is the SDN model). In the SDN model, the data plane devices are deliberately kept "dumb" — they contain forwarding tables but no routing logic. They cannot compute paths; they can only follow instructions from the controller.

Common Student Confusion

Students often confuse "centralized data plane" with "centralized control plane." The data plane is always distributed in practice — packets must be forwarded by physical devices at different locations. What SDN centralizes is the control — the decision-making about how packets should be forwarded. The data plane devices (switches) still exist at every hop; they simply follow the controller's instructions rather than making their own routing decisions.

Advantages of Centralized Control (SDN)

  • Global network visibility enables optimal routing decisions
  • Consistent policy enforcement across the entire network
  • Programmability allows rapid innovation and automation
  • Open interfaces reduce vendor lock-in
  • Simplified management — one controller instead of hundreds of CLI sessions
  • Enables network slicing, traffic engineering, and dynamic resource allocation

Disadvantages of Centralized Control (SDN)

  • Controller is a potential single point of failure
  • Scalability challenges as network size grows
  • Latency between controller and switch can delay rule installation
  • Security risk — compromising the controller compromises the entire network
  • Transition from legacy infrastructure is complex and expensive
  • Requires new skill sets (programming, API interaction) from network engineers

Section 1.3

SDN Architecture Layers

The SDN architecture is organized into three distinct layers, each with a clearly defined role and separated from the others by well-specified interfaces. This layered approach is not merely a theoretical abstraction — it maps directly to the physical and logical organization of a working SDN deployment, and understanding it at a granular level is essential for both conceptual clarity and examination performance.

Figure 1.2 — SDN Three-Layer Architecture
Figure 1.2 — The three-layer SDN architecture with Northbound and Southbound APIs as interfaces.

Application Layer

The application layer sits at the top of the SDN architecture and is where network applications reside. These are not end-user applications like web browsers or email clients — they are network applications that define how the network should behave. A traffic engineering application computes optimal paths for different classes of traffic. A security application installs firewall rules across all switches. A load balancer application redirects flows to less-loaded servers. A monitoring application collects statistics and raises alerts. The critical insight is that these applications do not directly configure switches — they communicate their requirements to the SDN controller through the Northbound API, and the controller translates those requirements into specific forwarding rules that are pushed down to the infrastructure layer.

This separation is architecturally significant. In traditional networking, every application that needed to influence network behavior (quality of service, access control, traffic shaping) had to be configured directly on each network device. In SDN, the application layer provides a single, programmable interface for expressing network-wide policies, and the controller takes responsibility for implementing those policies across all devices consistently. This is why SDN is often described as making the network "programmable" — software developers can write applications that control network behavior without knowing the details of individual switch hardware.

Control Layer (SDN Controller)

The control layer is the central brain of the SDN network, embodied in the SDN Controller. The controller maintains a global, real-time view of the entire network topology — which switches exist, how they are connected, what hosts are attached, and how much traffic is flowing on each link. Using this global view, the controller makes all routing and forwarding decisions, implements policies received from the application layer, and pushes specific forwarding rules down to individual switches through the Southbound API (most commonly OpenFlow).

The controller is not a monolithic entity. As we will see in the next section, it contains multiple internal components — topology managers, host trackers, slicing managers, orchestration functions — that work together to provide the intelligence that the network requires. The controller also exposes a northbound interface (typically RESTful APIs) that allows applications to request network services without needing to understand the internal complexity of the controller's operation. Notable open-source controller implementations include OpenDaylight and ONOS (Open Network Operating System).

Infrastructure Layer (Data Plane)

The infrastructure layer, also known as the data plane, consists of the physical and virtual network devices that actually forward packets — switches, routers, access points, and virtual switches (vSwitches). These devices are deliberately simple in the SDN model: they contain forwarding tables that the controller populates, and they follow those tables to make packet-by-packet forwarding decisions. They do not run routing protocols, they do not make autonomous decisions about path selection, and they do not hold any global knowledge about the network. Their role is purely executive — receive a packet, look up the forwarding table, send it out the correct port.

This deliberate simplicity is what makes SDN switches cheaper and faster than traditional routers. A traditional router must contain a general-purpose processor to run OSPF, BGP, and management software alongside its forwarding hardware. An SDN switch needs only the forwarding hardware and a communication channel to the controller. The result is lower cost, lower power consumption, and higher forwarding performance for the same silicon budget.

Key Interface Definitions

Northbound API: The interface between the Application Layer and the Control Layer. Typically implemented using RESTful APIs. Allows applications to request network services (e.g., bandwidth allocation, path computation) from the controller without knowing internal details.

Southbound API: The interface between the Control Layer and the Infrastructure Layer. The most widely used southbound protocol is OpenFlow. It allows the controller to install forwarding rules on switches, collect statistics, and manage device behavior.

Memory Anchor

"Apps North, Switches South, Controller in the Middle" — Application layer is at the top (North), Infrastructure at the bottom (South), and the Controller sits between them. Northbound API goes up (toward apps), Southbound API goes down (toward switches). Like a compass: N = Apps, S = Devices.

Section 1.4

SDN Architecture — Detailed Component Breakdown

The professor's slides present a detailed internal architecture of the SDN controller that goes well beyond the simple three-layer model. This expanded view reveals the internal components that make the controller function as a coherent system. Understanding these components is essential for examination purposes because questions frequently ask students to explain the role of specific elements like the Service Abstraction Layer, protocol plug-ins, or the slicing manager. Let us walk through each component systematically, from the top of the architecture to the bottom.

Figure 1.3 — Detailed SDN Controller Architecture
Figure 1.3 — Complete SDN controller internal architecture with all eleven numbered components.

1. Northbound APIs

Northbound APIs serve as the communication interface between network applications and the SDN controller. They are typically implemented as RESTful APIs (Representational State Transfer), which means applications interact with the controller using standard HTTP methods — GET to retrieve network state, POST to request services, PUT to modify configurations, and DELETE to remove policies. The significance of RESTful northbound APIs cannot be overstated: they allow any application that can speak HTTP to interact with the SDN controller, regardless of the programming language or platform the application uses. This openness is what makes SDN truly programmable.

For example, a traffic management application might send a POST request to the controller's API endpoint requesting that 10 Gbps of bandwidth be allocated for a video streaming service. The controller receives this request, computes which switches and links need to be configured, installs the appropriate forwarding rules, and returns a confirmation to the application. The application never needs to know which switches are involved, what protocol they speak, or how the rules were installed — the northbound API abstracts all of that away.

2. Network Service Functions

These are applications that run on top of the SDN controller and provide essential network services. They are not end-user applications but rather infrastructure-level services that the controller itself needs to function effectively.

Slicing Manager: The slicing manager divides the physical network into multiple virtual networks, called slices. Each slice can serve different users, departments, or applications with isolated resources and independent policies. For instance, a university might create one slice for research traffic (high bandwidth, low security) and another for administrative traffic (moderate bandwidth, high security). Network slicing is a foundational concept in 5G mobile networks as well, where different slices serve different service categories — enhanced mobile broadband, ultra-reliable low-latency communication, and massive machine-type communication.

Topology Manager: This component maintains a real-time map of the entire network topology. It tracks which switches exist, how they are interconnected through links, what the capacity and current utilization of each link is, and how the topology changes over time as devices are added, removed, or fail. Without an accurate topology map, the controller cannot compute valid forwarding paths. The topology manager typically discovers the network by instructing switches to send LLDP (Link Layer Discovery Protocol) packets and analyzing the results.

Host Tracker: The host tracker maintains information about all end hosts connected to the network — their IP addresses, MAC addresses, and which switch port they are attached to. When a new host sends its first packet, the switch forwards it to the controller (as a "packet-in" message in OpenFlow), and the host tracker records the host's location. This information is essential for the controller to install forwarding rules that direct traffic to the correct destination.

3. Network Orchestration Function

The orchestration function manages the overall coordination of network services and resources. It automates network configuration, allocates resources dynamically, and coordinates multiple network services to work together. For example, when a new server is added to a data center, the orchestrator automatically configures the surrounding switches with appropriate VLANs, access control lists, and QoS policies — without human intervention. Orchestration is what makes SDN networks truly dynamic rather than merely centralized.

4. Management Function

The management function handles the ongoing monitoring and administration of the network. Its responsibilities include performance monitoring (tracking throughput, latency, and packet loss on each link), fault management (detecting device failures and triggering recovery procedures), security management (auditing access control policies and detecting anomalous traffic patterns), and configuration management (maintaining backups of device configurations and managing updates). This function provides the operational backbone that keeps the network running reliably.

5. Controller API (Java / REST)

This is the programmatic interface that application developers use to interact with the SDN controller. It provides methods for programming network behavior, querying network state, and receiving event notifications. Many SDN controllers (like OpenDaylight) are written in Java and expose both Java-native APIs for applications running on the same platform and REST APIs for remote applications. This dual interface model allows high-performance local applications to use the Java API directly, while external tools and services interact through REST over HTTP.

6. Controller Core

The controller core is the central decision-making engine. It maintains the global network view, computes routing and forwarding decisions, and generates the specific instructions that are sent to network devices. When a new flow arrives at a switch and no matching rule exists, the switch forwards the first packet to the controller core, which determines the optimal path, installs forwarding rules on all switches along that path, and returns the result. Prominent open-source controller implementations include OpenDaylight (Linux Foundation project, widely used in enterprise and carrier networks) and ONOS (Open Network Operating System, designed for service providers with emphasis on high performance and scalability).

7. Service Abstraction Layer (SAL)

The Service Abstraction Layer is one of the most architecturally important components of the SDN controller, yet it is also one of the most frequently misunderstood by students. SAL acts as a bridge between the controller core and the various southbound protocols used to communicate with network devices. Its purpose is to hide the complexity of different protocols from the controller core and from applications. Without SAL, the controller core would need to contain separate logic for speaking OpenFlow to switches, BGP to routers, XMPP to messaging systems, and so on — a maintenance nightmare that would make adding new protocols extremely difficult.

With SAL in place, the controller core issues generic commands like "install forwarding rule on device X" or "query statistics from device Y," and SAL translates these commands into the specific protocol messages required by each device. If device X speaks OpenFlow, SAL uses the OpenFlow plug-in. If device Y speaks BGP, SAL uses the BGP plug-in. The controller core does not need to know which protocol each device speaks — that is SAL's responsibility. This abstraction is what makes the controller extensible: adding support for a new protocol requires only a new plug-in, not changes to the core.

8. Protocol Plug-ins

Protocol plug-ins are the concrete implementations that allow the controller to speak specific networking protocols. The most important plug-in is OpenFlow, which is the primary southbound protocol for controlling switches. However, real SDN deployments often need to communicate with legacy or specialized devices that speak other protocols, so additional plug-ins are provided for BGP (Border Gateway Protocol, used for inter-domain routing), XMPP (Extensible Messaging and Presence Protocol, used for messaging and configuration), and others. Each plug-in translates the abstract commands from SAL into the specific message format and transport mechanism required by its protocol.

9. Southbound Protocols

Southbound protocols connect the SDN controller to the network devices in the infrastructure layer. Their primary functions are to send forwarding rules to switches and to collect network statistics (throughput, packet counts, error counts). OpenFlow is the most widely used southbound protocol and is the de facto standard for SDN. It defines a precise message format for the controller to install, modify, and delete flow entries in a switch's forwarding table, and for the switch to report events and statistics back to the controller.

10. Network Elements

These are the physical or virtual network devices that constitute the infrastructure layer — switches, routers, and access points. Their function is straightforward: forward packets according to the rules given by the controller. They do not run routing protocols, they do not make independent forwarding decisions, and they do not maintain a global view of the network. When they encounter a packet that does not match any existing rule, they forward it to the controller for instructions (a "packet-in" event in OpenFlow terminology).

11. Overlay Tunnels

Overlay technologies create virtual networks on top of physical networks by encapsulating traffic in tunnels that run between endpoints. The two most common overlay protocols in SDN environments are VXLAN (Virtual eXtensible LAN) and NVGRE (Network Virtualization using Generic Routing Encapsulation). These technologies enable network virtualization — the creation of multiple isolated virtual networks that share the same physical infrastructure. They are heavily used in cloud data centers, where each tenant (customer) needs their own isolated network, but building separate physical networks for each tenant would be prohibitively expensive. VXLAN, for instance, encapsulates Layer 2 Ethernet frames within Layer 4 UDP packets, allowing virtual Layer 2 networks to span across Layer 3 physical boundaries.

Section 1.5

OpenFlow Protocol in SDN

OpenFlow is the protocol that gives teeth to the SDN vision. Without a standardized southbound interface, the separation of control and data planes would remain a theoretical exercise — each controller vendor would develop proprietary protocols to communicate with switches, and we would simply replace hardware vendor lock-in with software vendor lock-in. OpenFlow was created to prevent this outcome by defining an open, standardized protocol through which any SDN controller can program any compliant switch, regardless of the manufacturer.

The protocol was originally developed at Stanford University by Nick McKeown and his research group around 2008, as part of the Clean Slate program. The motivation was both practical and academic: researchers wanted to experiment with new routing algorithms and network protocols on real campus networks, but they could not modify the firmware on production switches. OpenFlow provided a way to add a small, safe "hook" into switches — a standardized interface that allowed an external controller to install forwarding rules — without requiring changes to the switch's core operating system. From this modest beginning, OpenFlow grew into the foundational protocol of the entire SDN movement.

How OpenFlow Works

At its core, OpenFlow defines a communication channel between the controller and each switch. Over this channel, the controller can perform several key operations. First, it can install flow entries into the switch's flow table. A flow entry consists of a match pattern (which packets does this rule apply to?), a set of actions (what should be done with matching packets?), and counters (how many packets and bytes have matched this rule?). When a packet arrives at the switch, the switch searches the flow table for the highest-priority matching entry. If a match is found, the switch executes the specified actions — typically forwarding the packet out a specific port, but also possibly modifying the packet header, dropping the packet, or sending it to the controller.

If no matching entry exists in the flow table, the switch must decide what to do with the packet. In OpenFlow, the default behavior is to send the packet to the controller as a packet-in message. The controller examines the packet, determines how it should be handled, installs the appropriate flow entry (or entries) on the switch, and then either tells the switch to forward the original packet or drops it. This is the "reactive" mode of operation, where flow entries are installed in response to new traffic. OpenFlow also supports a "proactive" mode, where the controller pre-populates flow entries before any traffic arrives, based on its knowledge of the network topology and policies.

Figure 1.4 — An OpenFlow flow table with match fields, actions, counters, and priority. The table-miss entry (priority 0, wildcard match) sends unmatched packets to the controller.

OpenFlow Message Types

The OpenFlow protocol defines several categories of messages that flow between the controller and switches. Understanding these message types is essential for explaining how the controller-switch interaction works in examinations.

Controller-to-Switch Messages: These are initiated by the controller and include: Flow-Mod (modify a flow entry — add, delete, or modify), Packet-Out (send a packet out through a specific switch port), Port-Mod (modify the configuration of a switch port), and Stats-Request (query flow, port, or table statistics from the switch).

Switch-to-Controller Messages (Asynchronous): These are initiated by the switch without a prior request from the controller. The most important are: Packet-In (the switch forwards a packet to the controller because no matching flow entry exists, or because a flow entry explicitly instructs it to do so), Flow-Removed (a flow entry has been deleted, either because it timed out or because the controller requested it), and Port-Status (a change in the state of a switch port — link up, link down, etc.).

Symmetric Messages: These can be initiated by either side and include Hello (connection establishment), Echo Request/Reply (latency measurement and keepalive), and Features Request/Reply (query the capabilities of a switch).

OpenFlow Workflow — Step by Step

  1. Connection Establishment: The switch connects to the controller over a TLS-secured TCP channel (typically on port 6653). Both sides exchange Hello messages to negotiate the OpenFlow version.
  2. Feature Discovery: The controller sends a Features Request to the switch, which replies with its capabilities — number of ports, supported actions, buffer sizes, and flow table specifications.
  3. Pipeline Configuration: The controller may pre-install flow entries (proactive mode) or wait for traffic to arrive (reactive mode). In proactive mode, the controller populates the switch's flow table based on its global view before any packets are processed.
  4. Packet Arrival: When a packet arrives at a switch port, the switch searches the flow table for the highest-priority matching entry. Match fields include ingress port, Ethernet source/destination, IP source/destination, TCP/UDP ports, and more.
  5. Match Found: If a matching entry exists, the switch executes the specified actions (forward, drop, modify, etc.) and updates the counters.
  6. No Match (Table-Miss): If no entry matches, the switch sends the packet (or a truncated version) to the controller in a Packet-In message.
  7. Controller Decision: The controller examines the packet, determines the appropriate forwarding path using its global network view, and installs Flow-Mod entries on all switches along the path.
  8. Packet-Out: The controller may also send a Packet-Out message to instruct the switch to forward the original packet out a specific port, so that the packet is not lost while the flow entries are being installed.
  9. Subsequent Packets: All subsequent packets in the same flow now match the installed entries and are forwarded at line rate without controller involvement.
Intuitive Explanation Think of the OpenFlow workflow like visiting a new restaurant where you have never been before. Your first time, you ask the waiter (Packet-In to controller) what they recommend. The waiter thinks about it (controller computes path) and gives you a recommendation (Flow-Mod installed). But the waiter also writes down your preference on a card (flow table entry). The next time you visit, you don't need to ask — you just follow the card, and service is instant (line-rate forwarding). The controller does the heavy thinking once; the switch follows the rules millions of times.

Advantages of OpenFlow

  • Open standard — vendor-neutral, prevents lock-in
  • Granular control over forwarding (match on multiple header fields)
  • Supports both proactive and reactive flow installation
  • Enables network-wide policy enforcement through centralized control
  • Allows experimentation with new protocols on production networks
  • Well-documented with multiple versions (1.0 through 1.5+)

Disadvantages of OpenFlow

  • Controller-switch latency can be significant for reactive flows
  • Flow table size is limited on hardware switches (TCAM is expensive)
  • Not all features are consistently implemented across vendors
  • Complexity increases with multi-table pipelines in later versions
  • Scalability — controller must handle Packet-In events for all new flows
  • Security concerns — TLS is optional in some implementations
Common Student Confusion

Students frequently confuse the OpenFlow flow table with a traditional routing table. They are fundamentally different. A routing table matches only on destination IP prefix and produces a next-hop output. A flow table can match on any combination of header fields (source IP, destination IP, protocol, source port, destination port, VLAN, etc.) and can specify any action (forward, drop, modify, enqueue, send to controller). Flow tables are far more expressive and flexible than routing tables — they are closer to ACLs (Access Control Lists) in their matching capability, but with forwarding actions rather than just permit/deny decisions.

OpenFlow Quick Revision

  • OpenFlow = southbound protocol between controller and switches
  • Flow entry = Match Fields + Actions + Counters + Priority
  • Packet-In = switch sends unmatched packet to controller
  • Flow-Mod = controller installs/modifies/deletes flow entry
  • Packet-Out = controller tells switch to send packet out a port
  • Table-miss entry (priority 0, wildcard match) = default action for unmatched packets
  • Proactive mode = pre-install entries; Reactive mode = install on first packet
  • Connection: TLS-secured TCP, port 6653

Part II

Delay Tolerant Networks

Section 2.1

Introduction to Delay-Tolerant Networks

The Internet works remarkably well — when you have a continuous, low-latency, bidirectional connection between source and destination. Send a packet, receive an acknowledgment, send the next one. The entire TCP/IP protocol stack is predicated on the assumption that an end-to-end path exists between communicating parties, that round-trip times are measured in milliseconds, and that packet loss is an occasional anomaly rather than a routine condition. But what happens when these assumptions collapse? What happens when you are trying to send data from a Mars rover to Earth through a chain of satellites, and each link in the chain is available for only fifteen minutes per day? What happens when you are a disaster relief coordinator trying to coordinate supplies across a region where every cell tower has been destroyed and the only communication devices are mobile phones that occasionally come within Bluetooth range of each other?

These scenarios describe the domain of Delay-Tolerant Networks (DTNs) — networks where the assumptions underlying the Internet's protocol stack simply do not hold. In DTNs, end-to-end connectivity cannot be guaranteed, round-trip times may be measured in minutes or hours rather than milliseconds, and the topology of the network changes unpredictably as nodes move, connect, and disconnect. Traditional Internet protocols fail catastrophically in these environments: TCP times out waiting for acknowledgments that will not arrive for hours, IP routing cannot compute paths through a network where links appear and disappear, and applications that assume synchronous request-response interaction simply hang.

Formal Definition A Delay-Tolerant Network (DTN) is an overlay network built on top of region-specific lower layers, designed to provide communication in environments where end-to-end connectivity cannot be assumed, latency may be extremely high, and links may be intermittently available. DTNs use store-carry-and-forward message switching rather than the packet-switching model of the Internet.

DTNs were originally conceived to support the InterPlanetary Internet (IPN) — a vision of extending Internet-like communication to space missions involving satellites, lunar bases, and eventually Mars colonies. In interplanetary communication, the speed-of-light delay between Earth and Mars ranges from 4 to 24 minutes depending on orbital positions, and direct line-of-sight may be blocked by celestial bodies for extended periods. The IPN researchers quickly realized that TCP/IP was fundamentally unsuitable for this environment, and they developed a new architectural approach that eventually became the DTN framework. Over time, it became clear that the same architecture applied equally well to terrestrial "challenged networks" — military ad-hoc networks, disaster response communication, rural connectivity in developing regions, vehicular networks, and wildlife tracking systems.

The most illuminating analogy is to think of the Internet as a telephone conversation — both parties must be present simultaneously, and communication is real-time. DTNs, by contrast, operate more like a postal mail system: you write a letter (bundle), hand it to a postman (next hop), who carries it physically to the next post office, where it is held until a delivery route becomes available. Each step of the journey is reliable (the postman gives you a receipt), but the overall delivery time is unpredictable and may be very long. This store-carry-and-forward mechanism is the defining characteristic of DTNs.

Where DTNs Are Used

The professor's slides highlight several application domains where DTNs are essential. Space communication (satellites, Mars missions) is the original use case, where propagation delays are measured in minutes and line-of-sight is intermittent. Remote and rural areas with poor connectivity benefit from DTN's ability to operate with sporadic connections — a health clinic in a remote village can store patient data locally and transmit it when a satellite passes overhead once per day. Military networks operate in environments where infrastructure is destroyed or jammed, and soldiers must communicate through mobile ad-hoc networks with unreliable links. Disaster recovery scenarios involve collapsed communication infrastructure where first responders rely on DTN-enabled devices that form temporary networks through physical proximity. In each case, the common thread is that traditional Internet protocols simply cannot function.

Key Features of DTNs

The professor's slides list several defining features of DTNs that distinguish them from conventional networks:

Intermittent connectivity: Links between nodes appear and disappear unpredictably. There is no guarantee that a path from source to destination exists at any given moment.

Opportunistic contacts: Some connections form spontaneously when two nodes come within communication range — for example, two mobile phones detecting each other via Bluetooth. These contacts are unplanned and unpredictable in both timing and duration.

Scheduled contacts: Some connections are predictable based on known schedules — for example, a satellite that passes over a ground station at known times each day. These scheduled contacts allow for more efficient routing planning.

Non-conversational protocol: DTN protocols do not assume a request-response interaction pattern. Sending a message does not require the receiver to be simultaneously present. This is fundamentally different from TCP's three-way handshake model.

Security: DTNs require security mechanisms at every hop, because messages pass through potentially untrusted intermediate nodes. Network routers participate in authentication, and each message carries a "postage stamp" signature from the sending node that is refreshed at each hop.

Section 2.2

DTN Architecture

The DTN architecture is designed around the concept of regions — administratively and technologically distinct network domains that are connected by gateways. The Internet itself is a single region running TCP/IP. A satellite network might be another region running a specialized link-layer protocol. A Bluetooth-based mobile ad-hoc network might be a third region. The DTN architecture does not attempt to make all regions speak the same protocol — instead, it provides an overlay layer that sits on top of each region's native protocols, allowing bundles to traverse from one region to another through gateways that understand both the DTN overlay and the region-specific protocols below it.

Node Types in DTN

The DTN architecture defines three types of nodes, each with a distinct role in the network. Understanding the difference between them is crucial for examinations because questions frequently ask about the role of gateways and how inter-region communication works.

Host: A host is an end-point in the DTN — it is the source or destination of bundles. Hosts operate within a single DTN region and do not forward bundles on behalf of other nodes. Examples include a sensor collecting weather data, a laptop in a remote clinic, or a Mars rover generating telemetry.

Router: A DTN router operates within a single region and forwards bundles between hosts and other routers. Unlike an IP router, a DTN router may need to store bundles for extended periods (hours or days) while waiting for the next contact opportunity. This storage requirement is a fundamental difference from Internet routers, which forward packets immediately and keep minimal buffering.

Gateway: A gateway connects two or more DTN regions. It is the most complex node type because it must understand the protocols and addressing schemes of each region it connects, and it must translate between them. For example, a gateway between the Internet region and the Space region must speak TCP/IP on one side and the space communication protocol on the other, while using the DTN Bundle Protocol as the common overlay that enables bundles to traverse both regions.

DTN Addressing

DTN uses a URI-based addressing scheme that differs fundamentally from IP addressing. Node names are based on URIs (Uniform Resource Identifiers) and consist of a region identifier and an entity identifier within that region. The general format is:

dtn://region/node/application

For example, the address dtn://earth.sol.int/src.someclient.com identifies an application running on a node called src.someclient.com within the earth.sol.int region. Similarly, dtn://mars/base1/weatherApp identifies a weather application on a base station on Mars. The region-based addressing allows bundles to be routed first to the correct region (via gateways) and then to the specific node within that region.

DTN supports four types of addressing: unicast (one specific destination), anycast (any one node matching a pattern), multicast (all nodes matching a pattern), and broadcast (all nodes in a region). The use of wildcards enables flexible addressing patterns — for example, dtn://earth.sol.int/*.someclient.* matches any entity containing "someclient" in the Earth region.

DTN Security

Security in DTNs presents unique challenges because bundles pass through multiple regions and potentially untrusted intermediate nodes. The DTN security model operates at the bundle layer and involves several mechanisms. Network routers participate in authentication, verifying that bundles are legitimate and that the sender is authorized to use the network. Private and public certificates are used for identity verification — each node holds a certificate that can be validated by other nodes. Each message contains a "postage stamp" that carries a digital signature from the sending node, and a new signature is generated every time the message arrives at the next node. This hop-by-hop signature chain creates an auditable trail that allows detection of tampering or injection at any point in the delivery path. Unlike the Internet's end-to-end security model (exemplified by TLS), DTN security must operate hop-by-hop because the end-to-end principle itself breaks down when end-to-end connectivity cannot be assumed. A bundle may pass through a dozen intermediate nodes over the course of several days, and each node must be able to verify the bundle's integrity before accepting custody of it. The postage-stamp mechanism also enables accounting and resource management — nodes can track which bundles they have handled and attribute costs to the originating region, which is particularly important in inter-planetary communication where bandwidth is an extraordinarily scarce and expensive resource.

Section 2.3

Bundle Protocol

The Bundle Protocol is to DTNs what IP is to the Internet — the foundational protocol that defines how data is packaged, addressed, and transported across the network. It sits at the bundle layer, which operates as an overlay above the transport layers of whatever regional networks the DTN spans. The protocol's primary data unit is called a bundle, which is a self-contained message that carries not only the application data but also all the metadata needed to route it through a network where connections are intermittent and delivery may take hours or days. Understanding the Bundle Protocol in depth is essential for examinations because it is the single most examined topic in the DTN portion of the syllabus.

Key Mechanisms of the Bundle Protocol

The Bundle Protocol incorporates several mechanisms that have no direct equivalent in the Internet protocol stack, each designed to address the specific challenges of delay-tolerant communication.

1. Custody Transfer: This is perhaps the most important and most frequently examined concept in the Bundle Protocol. Custody transfer is a reliable handoff mechanism that shifts responsibility for a bundle from one node to the next as the bundle moves through the network. When a node forwards a bundle to the next hop, it can transfer custody — meaning the receiving node accepts legal responsibility for ensuring that the bundle is delivered to its destination (or to the next custodian). Once custody is accepted, the sending node is relieved of its obligation and can delete its copy. If the receiving node later fails to deliver the bundle, it — not the original sender — bears responsibility. This mechanism is crucial because it prevents the unbounded accumulation of bundles in the network. Without custody transfer, every node that has ever handled a bundle would need to keep a copy indefinitely, since it could never be certain that the bundle had reached its destination. With custody transfer, at any given moment only one node — the current custodian — is responsible for a particular bundle.

The custody transfer process involves explicit signaling: the receiving node sends a Custody ACK (acknowledgment) back to the sending node to confirm that it has accepted custody. Only after receiving this ACK does the previous custodian delete its copy. If the ACK is not received within a timeout period, the previous custodian retains the bundle and may attempt to forward it again through a different path or at a different time. This hop-by-hop reliability model is fundamentally different from TCP's end-to-end acknowledgment, and it exists because end-to-end acknowledgments are impractical when the destination may not be reachable for hours.

2. Bundle Prioritization: Not all data is equally important, especially in resource-constrained DTN environments where bandwidth and storage are limited. The Bundle Protocol allows bundles to be assigned priority levels — typically classified as high, medium, and low. High-priority bundles, such as emergency alerts or critical telemetry data, are transmitted before lower-priority bundles when contact opportunities arise. When buffer space is limited and a node must discard some bundles to make room for new arrivals, lower-priority bundles are dropped first. This class-of-service mechanism ensures that the most important information gets through even when the network is congested or resources are scarce.

3. Bundle Fragmentation: Large bundles can be split into smaller fragments, which is essential in DTN environments for two reasons. First, network links often have maximum transmission unit (MTU) limits — a satellite link might only support messages up to a certain size, and a Bluetooth connection has even tighter constraints. Second, contact opportunities may be brief: if a satellite is overhead for only ten minutes and a bundle would take fifteen minutes to transmit at the available data rate, the entire bundle would be lost. Fragmentation allows the bundle to be split into pieces that can each be transmitted within the available contact window, and the fragments can be reassembled at the destination or at an intermediate custodian.

4. Bundle Reassembly: At the destination (or at an intermediate node that accepts custody of fragments), the individual fragments are reassembled into the original bundle. The Bundle Protocol ensures that reassembly produces the exact original data, even if fragments arrived out of order, through different paths, or at different times. This is analogous to IP fragmentation and reassembly, but operating at the bundle layer rather than the network layer, and with potentially much longer delays between fragment arrivals.

Intuitive Analogy for Custody Transfer Imagine sending a valuable package through a series of couriers. Each courier signs a receipt when they accept the package — that signature is the custody ACK. Once Courier B signs the receipt, Courier A is no longer responsible. If the package is lost after that point, Courier B bears the liability, not Courier A or the original sender. This is exactly how custody transfer works in DTN: each node that accepts custody signs for the bundle and takes responsibility, while the previous custodian is freed from obligation. The chain of receipts creates an auditable trail of who was responsible at each stage.
Common Student Confusion — Custody Transfer vs. End-to-End ACK

Students frequently confuse custody transfer with end-to-end acknowledgment. They are fundamentally different. Custody transfer is a hop-by-hop reliability mechanism — it ensures that each individual link in the chain is reliable, but it does not guarantee that the bundle has reached its final destination. The Custody ACK merely confirms that the next node has taken responsibility; it says nothing about whether that node will successfully deliver the bundle further. End-to-end acknowledgment is a separate mechanism — the destination sends an application-layer ACK that confirms actual delivery. Both mechanisms operate independently: custody transfer ensures reliability at each hop, while application ACKs confirm end-to-end delivery. In exams, clearly distinguish between these two levels of acknowledgment.

Summary Vectors and Node Encounters

When two DTN nodes come within communication range of each other (a "contact" or "encounter"), they need to efficiently determine which bundles to exchange. Sending all bundles to the other node would be wasteful if the other node already carries copies of some of them. To solve this problem, DTN nodes use summary vectors. A summary vector is a compact list of bundle IDs that a node currently stores in its buffer. When two nodes encounter each other, they first exchange summary vectors, compare them to identify which bundles the other node lacks, and then transmit only the missing bundles. This mechanism dramatically reduces redundant transmissions and conserves the limited bandwidth that typically characterizes DTN contacts.

The summary vector approach is particularly important in flooding-based routing protocols like Epidemic Routing, where the goal is to ensure that every node carries a copy of every bundle. Without summary vectors, nodes would waste precious contact time retransmitting bundles that the other node already has. With summary vectors, the exchange is efficient: only genuinely novel bundles are transmitted.

Bundle Protocol — Quick Revision

  • Bundle = DTN's fundamental data unit (like a packet in IP, but self-contained with metadata)
  • Custody Transfer = hop-by-hop responsibility handoff with ACKs
  • Bundle Prioritization = class of service (high/medium/low)
  • Bundle Fragmentation = split large bundles for limited links or brief contacts
  • Bundle Reassembly = recombine fragments at destination
  • Summary Vector = list of bundle IDs a node carries; exchanged at encounter
  • Custody ACK ≠ End-to-end ACK (hop-by-hop vs. destination confirmation)

Section 2.4

Routing in DTNs — Taxonomy and Design

Routing in Delay-Tolerant Networks is a problem of a fundamentally different nature than routing in the Internet. In the Internet, routing protocols like OSPF and BGP assume that the network topology is relatively stable, that links exist continuously, and that a path from source to destination can be computed at any time. In DTNs, none of these assumptions hold. The topology changes constantly as nodes move and links appear and disappear. End-to-end paths may not exist at any given moment. The very concept of a "shortest path" becomes ambiguous when the network itself is intermittent — what does "shortest" mean when some links will not exist for another six hours?

DTN routing therefore uses the store-carry-and-forward paradigm instead of the store-and-forward paradigm used in Internet routers. In store-carry-and-forward, a node receives a bundle, stores it in its buffer, carries it physically as the node moves (this is the "carry" phase, which has no equivalent in Internet routing), and forwards it to another node when a contact opportunity arises. The mobility of nodes is not a problem to be overcome — it is the fundamental mechanism by which bundles make progress toward their destination.

Intuitive Analogy Internet routing is like a postal service with fixed routes: trucks follow predetermined paths between fixed post offices. DTN routing is like giving a letter to a traveler who is heading in roughly the right direction: the traveler carries the letter, meets other travelers along the way, and passes the letter to someone who is heading closer to the destination. There are no fixed routes, no guaranteed schedules, and no certainty — only probabilities and opportunities.

DTN Routing Taxonomy

The professor's slides present a taxonomy that classifies DTN routing protocols along two major dimensions: knowledge-based classification (based on what the protocol knows about future contacts) and replication-based classification (based on how many copies of a message are created).

Knowledge-Based Classification

Scheduled Contacts: In some DTN environments, contact opportunities are known in advance because they follow predictable schedules. The classic example is satellite communication: a low-Earth orbit satellite passes over a ground station at precisely known times, and the duration and bandwidth of each contact can be calculated from orbital mechanics. When contact schedules are known, routing can be formulated as a constrained optimization problem — the routing algorithm computes the best sequence of contacts that will deliver a bundle from source to destination with minimum delay. This is analogous to planning a journey using a bus schedule: you know exactly when each bus arrives and departs, and you can plan your route accordingly.

Probabilistic / Predictable Contacts: When contacts cannot be scheduled but follow statistical patterns, routing protocols can use historical encounter data to estimate the likelihood of future contacts. For example, if Node A and Node B have encountered each other frequently in the past, the protocol estimates a high probability of future encounters and may choose Node B as a relay for bundles destined for nodes that B frequently meets. PRoPHET is the canonical example of this approach, maintaining a "delivery predictability" metric for each destination that is updated based on encounter history.

Context-Aware / Social Routing: This approach uses additional contextual information — particularly social metrics like node centrality (how well-connected a node is within the network), community membership (which group of nodes a node interacts with most frequently), and similarity (whether two nodes share common contacts) — to make routing decisions. The intuition is that socially central nodes (analogous to popular people in a social network) are more likely to encounter many other nodes and therefore make effective relay points for bundles. Context-aware routing is particularly useful in human-carried device networks, where social behavior patterns create predictable contact structures.

Replication-Based Classification

Flooding-Based (Unlimited Replication): These protocols spread copies of a bundle to every node they encounter, without strict limits on the number of replicas. The philosophy is simple: the more copies exist in the network, the higher the probability that at least one copy will reach the destination. Epidemic Routing is the purest example — every node shares every bundle with every other node it meets. The advantage is maximum delivery probability and minimum latency; the disadvantage is catastrophic resource consumption — every node's buffer fills with copies of every bundle, and contact bandwidth is wasted on redundant transmissions. MaxProp and RAPID refine this approach by prioritizing which bundles to transmit or drop based on delivery likelihood, but they remain fundamentally flooding-based.

Controlled Flooding / Quota-Based (Limited Replication): These protocols limit the number of replicas to balance delivery probability with resource efficiency. Spray-and-Wait is the most straightforward example: exactly L copies of each bundle are created (the "spray" phase), and once all L copies have been distributed to L different relay nodes, each relay simply waits until it encounters the destination directly (the "wait" phase). By controlling L, the protocol designer can tune the tradeoff between delivery probability and resource consumption. PRoPHET also falls into this general category: it replicates bundles selectively — only to nodes with a higher delivery predictability for the destination — which implicitly limits the number of copies without a hard quota.

Forwarding-Based (Single Copy): These protocols maintain only a single copy of each bundle and forward it to a "better" node — one that is more likely to deliver the bundle to its destination. The advantage is minimal resource consumption (one copy, one buffer slot per bundle); the disadvantage is that if the single relay node fails, loses the bundle, or takes a suboptimal path, the bundle may never be delivered. Forwarding-based protocols are suitable only for DTN environments where some reliable prediction of node mobility is possible, because without prediction, there is no basis for deciding which node is "better."

Section 2.5

Replication-Based Routing Protocols

Having established the taxonomy, we now examine the specific replication-based routing protocols identified in the syllabus in detail. Each protocol embodies a different philosophy about how to manage the fundamental tradeoff between delivery probability and resource consumption, and understanding these differences at a granular level is essential for both descriptive exam answers and analytical comparison questions.

Epidemic Routing

Epidemic Routing is the simplest and most aggressive DTN routing protocol. Its operation is straightforward: whenever two nodes come within communication range, they exchange summary vectors to identify which bundles the other node lacks, and then transmit all missing bundles. The result is that every bundle eventually spreads to every node in the network — exactly like a virus spreading through a population, which is why the protocol is named "Epidemic."

The algorithm operates in two phases during each node encounter. In the summary exchange phase, each node sends its summary vector — the list of bundle IDs it currently carries. In the bundle transfer phase, each node identifies which bundles from the other node's summary vector it does not already have, requests those bundles, and receives them. This process is symmetric: both nodes may receive new bundles from each other during a single encounter.

The theoretical appeal of Epidemic Routing is compelling: if any node in the network ever encounters the destination, the bundle will be delivered. Under ideal conditions (infinite buffer space, infinite bandwidth, unlimited contact duration), Epidemic Routing achieves the optimal delivery ratio and minimum latency of any DTN routing protocol. The practical reality, however, is devastating. Real DTN nodes have limited buffer space, and when buffers fill (as they rapidly do under Epidemic Routing), the oldest bundles must be dropped — potentially including bundles that were the only copy of a message. Real contacts have limited bandwidth, and spending that bandwidth on redundant copies of already-widespread bundles means that unique, critical bundles may never be transmitted. Real nodes have limited energy, and the continuous transmission of bundles drains batteries rapidly. In practice, Epidemic Routing performs well only in small networks with light traffic loads, and even then only as a benchmark against which more efficient protocols are measured.

Advantages of Epidemic Routing

  • Highest delivery probability under ideal conditions
  • Minimum delivery latency (bundles spread fastest)
  • Simple to implement — no prediction or history needed
  • Robust to topology changes (every path is explored)
  • Serves as upper-bound benchmark for other protocols

Disadvantages of Epidemic Routing

  • Catastrophic buffer consumption — every node carries every bundle
  • Extreme bandwidth waste — most transmissions are redundant
  • High energy consumption from constant transmission
  • Buffer overflow leads to bundle dropping and lost messages
  • Does not scale to large networks or heavy traffic

MaxProp

MaxProp addresses the primary weakness of Epidemic Routing — its indiscriminate flooding — by introducing a prioritization mechanism for both transmission and deletion decisions. When two nodes encounter each other and the contact duration is insufficient to transmit all bundles in their buffers, MaxProp must decide which bundles to send first. Similarly, when a node's buffer is full and a new bundle arrives, MaxProp must decide which existing bundle to drop. Both decisions are guided by a priority score that is computed based on the likelihood of a future delivery path.

The priority computation in MaxProp works as follows. Each node maintains a vector of encounter probabilities with every other node in the network. When two nodes meet, they exchange their encounter vectors and update them based on the meeting. The probability of a bundle reaching its destination via a particular path is estimated by multiplying the encounter probabilities along that path. Bundles with a lower estimated delivery probability are given higher priority for transmission (because they are less likely to reach the destination through other means) and lower priority for deletion (because losing them is more costly). MaxProp also uses acknowledgments to remove delivered bundles from buffers, and it prioritizes bundles that have been forwarded fewer times (on the reasoning that bundles with many copies are more likely to reach the destination without additional help).

In practical terms, MaxProp performs significantly better than pure Epidemic Routing in resource-constrained environments because it makes intelligent decisions about which bundles deserve bandwidth and buffer space. However, it retains the fundamental flooding philosophy — it still replicates bundles broadly — and its overhead is only marginally lower than Epidemic's in dense networks.

RAPID

RAPID (Resource Allocation Protocol for Intentional DTN routing) takes a fundamentally different approach to the prioritization problem. Instead of heuristic priority scores, RAPID explicitly treats DTN routing as a resource allocation problem. The protocol defines a specific metric — such as average delivery delay, maximum delivery delay, or delivery probability — and then replicates packets in a way that directly optimizes that metric.

When two nodes encounter each other, RAPID performs three steps. First, it estimates the utility of replicating each bundle in its buffer — the expected improvement in the optimization metric if an additional copy is created. Second, it sorts bundles by their utility values. Third, it transmits bundles in order of decreasing utility, starting with the bundle that would benefit most from replication, until the contact ends or all bundles have been transmitted.

The key innovation of RAPID is that the utility function is directly tied to the performance metric the network operator cares about. If the goal is to minimize average delay, RAPID replicates the bundle with the highest expected remaining delay. If the goal is to maximize delivery probability, RAPID replicates the bundle with the lowest current delivery probability. This intentional, metric-driven approach makes RAPID more principled than MaxProp's heuristic prioritization, though it also requires more computational overhead and more accurate network state estimation.

Spray-and-Wait

Spray-and-Wait is the most important quota-based protocol for examination purposes, and it is frequently the subject of detailed questions because of its elegant two-phase design. The protocol operates in exactly two phases:

Spray Phase: The source node creates exactly L copies of the bundle (where L is a protocol parameter chosen by the network designer). As the source node encounters other nodes, it distributes these copies — one copy per encountered node — until all L copies have been distributed. The key constraint is that the total number of copies in the network never exceeds L. If L = 6, then at most six nodes (including the source) will ever carry a copy of the bundle.

Wait Phase: Once a relay node has received its single copy during the spray phase, it does not forward it to any other intermediate node. Instead, it simply waits until it encounters the destination node directly, at which point it delivers the bundle. The relay does not spread the bundle further — it holds its copy and waits for a direct encounter with the destination.

The simplicity of Spray-and-Wait is deceptive. By controlling L, the protocol provides a clean tradeoff between delivery performance and resource consumption. With L = 1, the protocol degenerates to direct delivery (the source waits to meet the destination itself). With L equal to the total number of nodes, the protocol approximates Epidemic Routing. For intermediate values, Spray-and-Wait achieves delivery ratios close to Epidemic Routing but with dramatically lower resource consumption — often an order of magnitude fewer transmissions per delivered bundle.

A variant called Spray-and-Focus relaxes the wait phase by allowing relay nodes to forward their copy to another node that is "closer" to the destination according to some utility metric, rather than waiting for a direct encounter. This improves delivery performance without significantly increasing resource consumption.

PRoPHET (Probabilistic Routing Protocol using History of Encounters and Transitivity)

PRoPHET occupies a unique position in the DTN routing landscape because it combines elements of both replication-based and knowledge-based approaches. It maintains a delivery predictability metric for each known destination — a value between 0 and 1 that represents the probability that the current node will encounter that destination in the future. When two nodes meet, they exchange their delivery predictability tables, and bundles are replicated only to nodes that have a higher delivery predictability for the bundle's destination than the current holder.

The delivery predictability metric is updated using three rules. The encounter rule states that whenever two nodes meet, their mutual delivery predictability increases — if A meets B, then P(A,B) increases because A now has evidence that it can reach B. The aging rule states that delivery predictability decreases over time if nodes do not meet — P(A,B) decays exponentially, reflecting the decreasing confidence that A will encounter B again. The transitivity rule captures the intuition that if A frequently meets B, and B frequently meets C, then A has an indirect path to C through B — so P(A,C) should increase based on P(A,B) × P(B,C). This transitive property allows PRoPHET to discover multi-hop delivery opportunities without explicit path computation.

The key advantage of PRoPHET over Epidemic Routing is that it avoids wasting resources on nodes that are unlikely to help deliver a bundle. A bundle is only replicated to a node that has a higher delivery predictability for the destination, which means the replication is always "useful" in a probabilistic sense. This selective replication dramatically reduces the number of copies in the network compared to Epidemic Routing, while maintaining comparable delivery ratios in many realistic scenarios. However, PRoPHET requires state maintenance (the predictability tables must be stored and updated) and computational overhead (the transitive updates), and its performance depends on the accuracy of the predictability estimates — in highly unpredictable environments, the history-based predictions may be no better than random guessing.

Encounter-Based Routing (EBR)

EBR takes a different approach to quota-based replication by using the rate of node encounters as the metric for deciding how many copies of a bundle to give to each relay. Nodes that encounter many other nodes (high encounter rate) are better connected to the network and therefore more likely to deliver bundles to their destinations. EBR allocates more copies to these well-connected nodes and fewer copies to poorly-connected nodes.

When Node A encounters Node B, EBR calculates the number of copies to give B based on B's encounter rate relative to A's encounter rate. If B encounters twice as many nodes as A, B receives a proportionally larger share of the remaining copies. This adaptive allocation ensures that copies flow toward the most mobile and well-connected nodes, which statistically have the highest probability of encountering the destination. EBR thus avoids the rigid fixed-copy allocation of Spray-and-Wait while still maintaining a bound on the total number of replicas.

Recent Advancements

The professor's slides briefly mention two recent developments in DTN routing that represent the cutting edge of the field. These are likely to appear as short-answer or viva questions rather than full-length descriptive questions, but understanding them demonstrates depth of knowledge.

Enhanced Message Replication Technique (EMRT): EMRT dynamically adjusts the number of replicas based on real-time network conditions, including node energy levels, buffer availability, and remaining message Time-To-Live (TTL). Unlike Spray-and-Wait's fixed L parameter, EMRT recognizes that the optimal number of copies depends on the current state of the network — more copies are beneficial when energy and buffer space are abundant, but fewer copies are appropriate when resources are scarce. This adaptive approach aims to achieve the delivery performance of aggressive replication during favorable conditions while avoiding resource exhaustion during unfavorable periods.

Replication-Based Locking (RBL): RBL introduces a "locking" mechanism to reduce redundant transmissions. When a node determines that a particular bundle has been sufficiently replicated in its neighborhood (based on encounter history or explicit notifications), it "locks" the bundle, preventing further replication of that bundle by nodes in the locked region. This prevents the common scenario in flooding-based protocols where multiple nodes waste bandwidth transmitting the same bundle to the same encounter. RBL thus reduces network congestion without significantly impacting delivery probability, because the locked bundles have already achieved sufficient replication for likely delivery.

Common Student Confusion — MaxProp vs. RAPID

Students often struggle to distinguish MaxProp from RAPID because both prioritize bundles for transmission and both address the same basic problem (Epidemic Routing's indiscriminate flooding). The key difference lies in how they compute priorities. MaxProp uses a heuristic scoring system based on encounter probabilities and forwarding counts — it is a rule-based approach that approximates good decisions. RAPID explicitly formulates routing as an optimization problem: it defines a specific metric (e.g., average delay) and computes the utility of replicating each bundle as the expected improvement in that metric. RAPID is more principled and potentially more optimal, but also more computationally expensive. Think of MaxProp as an experienced driver who knows the roads, and RAPID as a GPS that calculates the mathematically optimal route.

Replication Protocols — Quick Revision

  • Epidemic = flood everything to everyone (simple but wasteful)
  • MaxProp = flood with priority (heuristic scoring based on delivery likelihood)
  • RAPID = flood with utility optimization (metric-driven resource allocation)
  • Spray-and-Wait = spray L copies, then wait for direct delivery
  • PRoPHET = replicate only to nodes with higher delivery predictability
  • EBR = allocate copies based on encounter rate (well-connected nodes get more)
  • EMRT = adaptive replica count based on energy/buffer/TTL
  • RBL = lock bundles to prevent redundant replication

5-Mark Answer Template: Custody Transfer

Definition (1 mark): Custody transfer is a hop-by-hop reliability mechanism in the Bundle Protocol where a node accepts responsibility for delivering a bundle further.

Process (2 marks): Node A sends bundle to Node B. Node B accepts custody and sends Custody ACK. Node A deletes its copy. Node B is now responsible.

Significance (1 mark): Prevents unbounded accumulation of bundles; ensures at least one node is always responsible for delivery.

Distinction (1 mark): Different from end-to-end ACK. Custody ACK confirms hop-level handoff, not final delivery.

  3. Draw a line between Application and Control labeled "Northbound API (REST)"
  4. Draw a line between Control and Infrastructure labeled "Southbound API (OpenFlow)"

  6. Inside Control: write "SDN Controller — Global View, Routing, Policy"
  7. Inside Infrastructure: write "Switches, Routers, Access Points"
  8. Add a small note: "Controllers: OpenDaylight, ONOS"

DTN Custody Transfer Diagram — What to Draw

  1. Draw 4 boxes in a horizontal line: Source → Node 1 → Node 2 → Destination
  2. Draw forward arrows (solid) between them, labeled "Bundle"
  3. Draw backward arrows (dashed) between them, labeled "Custody ACK"
  4. Mark Node 1 accepting custody with a note "Custody Accepted"
  5. Mark Node 2's custody decision with "Accept / Deny"
  6. Add a note: "Node 1 deletes copy after ACK from Node 2"
  7. Add final note: "Destination sends App ACK (end-to-end)"

Spray-and-Wait Diagram — What to Draw

  1. Draw Source box with "L copies" written inside
  2. Draw 3-4 relay boxes radiating from Source (spray phase)
  3. Label arrows "1 copy each" from Source to relays
  4. Draw a Destination box on the right
  5. Draw dashed arrows from each relay to Destination labeled "Wait for direct encounter"
  6. Clearly label "SPRAY PHASE" on the left and "WAIT PHASE" on the right
